# CleanStart CMS — database migrations

Baseline established **2026-05-12**.

## Files in this directory

- `20260512_120000_baseline.ts` — the baseline. Full schema (every collection, global, enum, foreign key, index) as it stands the day migrations went live. Generated by `pnpm migrate:create` against the development database after `push: true` had auto-synced the schema through Phases A–J.
- `20260512_120000_baseline.json` — Payload's internal schema-state snapshot. Used by `migrate:create` to compute future deltas. **Do not edit by hand** — regenerated when you create the next migration.
- `index.ts` — the ordered list Payload reads at boot to decide which migrations to apply.

## Day-to-day workflow

```bash
# Generated migration after a schema change:
pnpm --filter @cleanstart/cms migrate:create <descriptive_name>

# Review the generated SQL, commit it.

# On dev databases that already have the schema (via push: true),
# nothing to do — the new migration is empty if you're caught up.

# On fresh databases / CI / staging / production:
pnpm --filter @cleanstart/cms migrate
```

The production Dockerfile `CMD` runs `pnpm migrate && pnpm start`, so the GitHub Actions deploy workflow gets schema-current behavior for free — every container boot runs migrations before the app listens.

## One-time setup: existing environments

For databases that pre-date the baseline (the dev DB on every laptop, plus the existing staging droplet), the schema is already correct because `push: true` synced it. Don't try to run the baseline migration — it has no `IF NOT EXISTS` guards and will fail on the first `CREATE TYPE`.

Instead, mark the baseline as already applied:

```sql
INSERT INTO payload_migrations (name, batch, created_at, updated_at)
VALUES ('20260512_120000_baseline', 1, now(), now());
```

After this, `pnpm migrate` is a no-op until the next delta lands, and `migrate:create` produces clean diffs.

For **brand-new databases** (a fresh staging cutover, a CI run, prod's first deploy onto a clean droplet), don't insert the row — run `pnpm migrate` and the baseline creates everything from scratch.

## `push: true` vs migrations

The `postgresAdapter` in `payload.config.ts` defaults to `push: true` in development. From this baseline forward, the recommended pattern is:

| Environment | `push` | Migrations |
|-------------|--------|------------|
| Local dev   | `true` | optional — your migrations folder is the source of truth for the next deploy |
| CI tests    | `false` | run `pnpm migrate` in setup |
| Staging     | `false` | run `pnpm migrate` on deploy |
| Production  | `false` | run `pnpm migrate` on deploy |

Keep `push: true` in dev so you can iterate on schema changes without churning migration files; when the change is settled, run `migrate:create` to capture it.

## Rollback

Every migration ships an `up` and a `down`. To roll back the latest:

```bash
pnpm --filter @cleanstart/cms migrate --down
```

The `down` block in the baseline drops every table and enum — only useful on a database that you genuinely want to flatten. For real-world rollbacks of a single deploy, prefer rolling forward with a corrective migration rather than running `--down` against staging or prod.

See `docs/cleanstart-cms-architecture.html` §migration for the broader migration + rollback strategy and `docs/RESTORE-LOG.md` for the documented restore runbook.

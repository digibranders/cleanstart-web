JSON-LD Schema System

How CleanStart generates, audits, and lets admins extend the Schema.org JSON-LD emitted on every published page — what is automatic, what is editable, what is hard-blocked, and the security boundaries in between.

1. Why JSON-LD matters at all

Search engines and LLMs read structured data to understand what a page is: an article, a job posting, a software product, an FAQ. Good structured data feeds:

  • Google Rich Results (FAQ accordions, video carousels, jobs, breadcrumb crumbs) — visible SERP enhancements that raise CTR.
  • Knowledge Graph entity attribution — who owns the page, who wrote it, what software it describes.
  • LLM citation — Perplexity, ChatGPT search, Claude, Gemini all consume Schema.org markup when summarising or citing pages.

Bad structured data costs us: missing required fields means Google ignores the blob; spammy markup triggers manual actions (named penalties). The system in this doc is designed so the easy path produces correct markup automatically and the hard path (manual override) is gated on every dangerous shape.

2. The three layers

Every published page emits a graph of one or more <script type="application/ld+json"> tags. The graph is composed top-down through three layers, in this order:

LayerSourceWho controls itCommon types
Layer 1 — AutoDispatcher reads doc fieldsEngineering (code)Organization, WebSite, Article, Person, BreadcrumbList, JobPosting, Event, WebPage, DigitalDocument, FAQPage
Layer 2 — Add-onsschemaAddons blocks fieldEditors (UI)HowTo, VideoObject, Review, SoftwareApplication, manual FAQ entries, breadcrumb replace/suppress
Layer 3 — Customseo.additionalSchema JSON fieldAdmin only (via picker modal)Any allowlisted type not already covered (e.g. FAQPage with edge-case Qs on a non-blog page, ProfilePage on authors, Course)

The dispatcher runs Layer 1 first, then Layer 2 merges/replaces specific entries, then Layer 3 is appended last. Order matters: later layers can add to the graph but never silently overwrite the canonical Layer-1 entity ids.

The append-only contract. No layer ever replaces the Layer-1 graph wholesale. This is the single most important invariant in the system: one bad paste must never blank out the page's Organization, WebSite, Article, or Breadcrumb blobs.

4. Layer 2 — schemaAddons blocks

Editors who need a richer graph than the auto-emitter produces (a HowTo on a blog, a SoftwareApplication on a page) reach for the schemaAddons[] blocks field. Each block is a typed form an editor fills in with structured fields; the dispatcher builds a valid Schema.org blob from the block data.

Block typeBuildsTypical use
howToAddonHowToStep-by-step content not modelled as a guide
videoAddonVideoObjectEmbedded videos on any page
faqAddonAdds entries to the page's FAQPageEditor-curated FAQs without using the dedicated faqs[] field
reviewAddonReviewProduct / resource reviews
softwareAddonSoftwareApplicationSoftware product pages
breadcrumbAddonReplaces / suppresses Layer 1 BreadcrumbListAtypical IA where the auto-derived trail is wrong

Why use Layer 2 over Layer 3? Layer 2 keeps editors away from raw JSON. The block form enforces required fields, validates URLs, and never lets the editor break the JSON syntax.

5. Layer 3 — admin custom additions

Some shapes don't fit Layer 1 or Layer 2: a paste from a third-party generator, a one-off FAQPage on a pages doc (which has no auto FAQ), a ProfilePage on an author detail page. For these, admins use the Custom additions modal on the Schema (JSON-LD) sidebar card.

The underlying field is seo.additionalSchema (a Payload JSON field, admin-only via isAdminFieldLevel). It accepts a single Schema.org blob or an array of blobs. The dispatcher appends them after Layer 2.

What the admin sees

The Schema (JSON-LD) sidebar card has, in order:

  1. A severity chip (Valid / Invalid / Draft / Unverified) for the whole page.
  2. Expanded view: one row per blob currently in the graph, each with its own severity chip and a "Custom" pill if it came from additionalSchema.
  3. A "Show raw JSON-LD" details block (the exact text the public site will emit).
  4. Three buttons: Copy JSON-LD, Test in Rich Results ↗, and (admin-only) Add custom overrides / Edit custom overrides (N).

Clicking the Edit button opens the modal — that is the only entry point. There is no inline editor in the sidebar; the modal exists to make every paste go through the ingest classifier (next section).

6. The override allowlist

Schema.org has 800+ types. Most are dangerous on a B2B marketing site (medical, legal, governmental, e-commerce). The admin override is restricted to a small allowlist of types we have committed to keeping correct: ALLOWED_OVERRIDE_TYPES in override-validator.ts.

CategoryAllowedExcluded by design
Article variants Article, NewsArticle, TechArticle, BlogPosting, CreativeWork —
WebPage variants WebPage, AboutPage, ContactPage, CollectionPage —
Editorial / rich-result HowTo, FAQPage, QAPage, VideoObject —
Education Course, Dataset —
Product / app SoftwareApplication, WebApplication, Service Product, Offer, MobileApplication no surface
Speakable SpeakableSpecification —
Per-collection-gated ProfilePage, Review, AggregateRating restricted —
Auto-emitted by code — Organization, WebSite, Person, BreadcrumbList, JobPosting, Event, BusinessEvent @id collision risk
Off-surface / risky — MedicalCondition, LegalService, Drug, GovernmentService, Recipe, Book, AudioObject, PodcastEpisode, PodcastSeries, Movie, VacationRental never
Adding to the allowlist is a code change. Every entry is a maintenance commitment — we have to keep emitting valid markup for that type as Schema.org evolves. New types are added in override-validator.ts and a corresponding spec rule is added to spec/required-fields.ts.

7. Per-collection restrictions

Three allowlisted types are gated to specific collections via COLLECTION_RESTRICTED_TYPES. Rationale: a Review blob on a blog page is a documented manual-action trigger; ProfilePage only makes semantic sense on author pages.

TypeAllowed onBlocked onReason
ProfilePage authors only everything else Google's 2024 author-profile rich-result type. Pointless and misleading on non-profile pages.
Review resources, events, webinars blogs, news, guides, knowledgeBase, authors, pages, jobs Top manual-action trigger ("structured data manipulation"). Allowed only where a reviewable subject genuinely exists.
AggregateRating resources, events, webinars same as Review Same reason. Google's March 2026 enforcement threshold is ≥5 verifiable open-system reviews.

The collection gate is enforced in three places (defence in depth):

  1. Picker UI shows a hard-disabled "Wrong collection" row.
  2. Field validate hook on additionalSchema rejects the save with a line-item error.
  3. Dispatcher re-runs validateOverrideForCollection before emitting, so a row written before the rule existed still gets dropped from the public output.

8. The validator pipeline

Every override save runs through validateOverride (or its collection-aware sibling validateOverrideForCollection) in override-validator.ts. The pipeline is a sequence of cheap, deterministic gates:

1
Null short-circuit. Unset field → valid. Cheap.
2
Size guard (16 KB). JSON.stringify + Buffer.byteLength. Done before Zod so a 5 MB blob doesn't DoS the save handler.
3
Zod schema. @context must be exactly "https://schema.org" (no http, no array). @type must be on the global allowlist, single string or non-empty array.
4
Nested-@id scan. Recursive walk; top-level @id is allowed (legitimate self-id), nested @id is rejected (schema-injection vector).
5
(collection-aware variant only) Per-collection gate for ProfilePage / Review / AggregateRating.

The same validator runs on the server (validate hook + dispatcher re-check) and on the client (live red error in the picker). One source of truth.

Tolerant parser — parseLenient / parseLenientMulti

Pastes from external generators (Webflow, Rank Math, ChatGPT) come with garbage. Before validation runs, the parser:

  • Strips wrapping <script type="application/ld+json">…</script> tags.
  • Normalises "http://schema.org" → "https://schema.org" (only at the @context position).
  • Removes JSON5-style trailing commas as a fallback.
  • Reports a line/column on parse failure so the editor can find the problem.

The "multi" variant extracts every <script> block from a single paste independently — the shape SEO generators emit, with comments separating multiple blobs. Each block parses on its own; one bad block doesn't poison the whole paste.

9. Multi-blob ingestion & the picker UI

When the admin pastes a file with several @type blobs, the modal classifies each one against four buckets via buildIngestPlan:

ReasonDefault actionOverridable?Meaning
allowed mergeMergeYesOn the allowlist, not auto-emitted, no off-domain @id → safe to append.
duplicates-auto-emitSkipOnly if type is also on user allowlist (e.g. FAQPage on guides)The dispatcher already generates this blob from doc fields. Letting the paste in adds a second, possibly diluting the canonical shape.
off-domain-idSkipYesTop-level @id points at a domain other than the site origin. Forcing this in splits Google's knowledge-graph entity between domains.
off-allowlist hardSkipNo@type is not on ALLOWED_OVERRIDE_TYPES.
collection-restricted hardSkipNoType is gated to a different collection (Review on a blog).
nested-id hardSkipNoSchema-injection vector (nested @id pulling external graphs).
oversize hardSkipNoSingle blob exceeds the 16 KB cap.
invalid-shape hardSkipNoBlock is not a JSON object.

The picker renders one row per blob with a checkbox. Rows marked overridable have an enabled checkbox the admin can flip. Rows marked hard have a disabled checkbox — no UI gesture can save them, and even if the request was hand-crafted the field validator would reject it.

On Apply, only the checked blobs are written to seo.additionalSchema. If exactly one blob remains, it's stored as a single object; multiple blobs are stored as an array. The dispatcher handles both shapes transparently.

Why every row defaults to skip. Pasting a five-block generator file should produce zero unintended writes until the admin explicitly opts each one in. The opt-in cost is one click per intended row; the opt-out cost of getting it wrong is a brand-attribution split that takes months to unwind.

10. JSON-LD endpoints

Two HTTP endpoints, both at /api/jsonld/<collection>/<id>:

GET Public

  • Open access (matches each collection's read rule).
  • Published docs only — drafts return 404.
  • Returns { blobs } ordered as the public renderer should emit them.
  • Cache-Control: public, max-age=60.

POST Admin draft preview

  • Admin role required (hasRole(req.user, 'admin')) — anything else returns 403.
  • Body: { additionalSchema?: unknown } — re-validated server-side via validateOverrideForCollection before merging.
  • Includes drafts so editors can preview changes before publishing.
  • Cache-Control: no-store.
  • Used by the sidebar card to render a live "Preview only — applies on publish" merge of the unsaved override.

11. Audit logging

Every change to seo.additionalSchema writes one row to the audit-log collection via the schemaOverrideAuditHook (apps/cms/src/payload/hooks/schema-override-audit.ts):

{
  action: "schema_override_changed",
  targetCollection: "blogs",
  targetId: "13",
  actorUserId: 1,
  requestIp: "...", userAgent: "...",
  metadata: {
    before: { /* previous additionalSchema value */ },
    after:  { /* new value */ },
    operation: "created" | "updated" | "cleared"
  }
}

Capped by the field's 16 KB Zod limit so the row stays small. Audit-log write failures never block the parent save — they log and move on, matching the lead-deletion hook pattern.

12. Spec audit & severity badges

The badges in the sidebar (Valid / Invalid / Unverified) come from a separate audit pass that compares each blob's properties to a per-@type required/recommended table in apps/cms/src/payload/lib/jsonld/spec/required-fields.ts:

  • Valid — all required fields present.
  • Valid (amber underneath) — required fields present, some recommended fields missing.
  • Invalid — one or more required fields missing. Search engines will reject the blob.
  • Unverified — @type not in SCHEMA_SPEC. We treat the blob as informational only.

The spec audit is separate from the override validator: a paste that's structurally OK but missing recommended fields will save (it just shows amber). This matches how editors work — saving slightly-incomplete blobs is fine; the recommended-fields nudge appears in the card as a list under the blob.

13. Security boundaries

RiskMitigation
Schema spam / manual actionTight @type allowlist (22 entries). Per-collection gates for Review / AggregateRating / ProfilePage. Default-skip on every paste. Audit log captures author + diff.
Knowledge-graph entity split (off-domain @id)Picker detects mismatched origin and defaults that row to skip with an explanatory message.
Schema-injection (nested @id pulling external graphs)Hard-block in the validator; rejected at field-save, dispatcher, and picker.
Permission escalationseo.additionalSchema field-level access locked to admin role. Picker UI gated via useAuth(). POST preview endpoint checks role before accepting body.
DoS via huge paste16 KB cap enforced before Zod runs; 64 KB upload cap before parse runs.
Payload-side </script> escapePublic-site responsibility: when apps/web returns, its <script type="application/ld+json"> serializer must escape the four-character </ sequence to <\/ in any user-supplied string. Documented as a Phase-A launch blocker.

14. How to paste a custom JSON-LD file

Walking through the typical SEO-team workflow (a generator output file like cleanstart-foo-schema.txt):

1
Open the document in the CMS. Expand the Schema (JSON-LD) sidebar card.
2
Click Add custom overrides (or Edit custom overrides (N)). The modal opens.
3
Either paste the whole file into the textarea or click Choose File and pick the .txt / .json / .jsonld.
4
The picker appears under Ingest plan. Each <script> block becomes one row with a checkbox and a reason badge. Read the reasons; everything defaults to skip.
5
Check only the boxes you want. Disabled rows are hard-blocked — flip the off-domain @id, edit the @id to point at cleanstart.com, or just live with the auto-emit version.
6
Click Apply. The modal closes; the sidebar now shows a "Custom additions: N blob(s)" pill on each merged row in the live preview.
7
Save the document. The audit log gets one row; the next publish emits the merged graph to the public site.

For most SEO-generated files (which include Organization / WebSite / WebPage / BreadcrumbList that we already auto-emit), the realistic merge count is 1 — usually the FAQPage on a page where the auto-emitter doesn't generate one.

15. How to add a new auto-emitted type

Engineering task. Roughly:

  1. Write a builder under apps/cms/src/payload/lib/jsonld/<type>.ts following the existing pattern ((ctx, source) => JsonLdBlob | null).
  2. Wire it into dispatch.ts for the collections that should emit it.
  3. Add the type to AUTO_EMITTED_TYPES_BY_COLLECTION in override-validator.ts so the picker default-skips duplicates.
  4. Add a row to SCHEMA_SPEC in spec/required-fields.ts with the required + recommended properties (cross-check against schema.org and Google's structured-data docs).
  5. Write a Vitest spec next to the builder. The existing dispatcher tests are good templates.
  6. Run the four pre-completion checks: pnpm --filter @cleanstart/cms lint && pnpm --filter @cleanstart/cms typecheck && pnpm --filter @cleanstart/cms test && pnpm --filter @cleanstart/cms build.

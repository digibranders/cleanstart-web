# Partner portal contracts

This file is the single source for every interface that more than one area plan or coding track depends on: the database schema, the shared types, the permission matrix, the errors, the repository and action conventions, the outbox, the interface registry (every repo module and cross-area module with exact signatures and DTOs), the environment, the test infrastructure, the module map and the route map. It sits beside `2026-11-11-partner-portal-master-plan.md` (what to build) and `2026-11-11-partner-portal-hubspot-integration.md` (HubSpot internals) and resolves every place where the two disagree (section M). Written 12 November 2026 against the mock at commit `58747992`; reviewed together with the six area plans and amended on 13 November 2026 (`docs/partner-portal/PLAN-REVIEW.md` lists every change).

**Contract Change rule.** An area plan that needs a new cross-area export, or a change to anything defined here, must list it in its own final section titled "Contract change requests" and must not redefine it, copy it with edits, or code against a changed version. The orchestrator folds approved changes back into this file and tells the affected tracks. A track that finds this file wrong or silent about something it needs writes a `blocked` line (BUILD-HANDOFF, "When to stop and ask") and carries on with a task that does not need it.

**How to read the code blocks.** A block that starts with `export` and contains no function bodies (`export declare function ...`) is a signature: the owning task implements it exactly, and callers may rely on it exactly. A block with bodies is the implementation to copy. Paths are relative to `apps/portal` unless they start with `docs/`, `infra/` or `.github/`. Task ids use the handoff prefixes: `M` for the master plan, `H` for the HubSpot plan. `W0-a` to `W0-g` are the Wave 0 steps of the handoff.

## B. Conventions

### B.1 Naming

| Thing | Rule | Example |
|---|---|---|
| Files and folders | kebab-case | `src/server/repo/integration-health.ts` |
| React components | PascalCase file named after the component, as the mock does. The mock's existing kebab-case files (`partners-table.tsx`, `add-partner-drawer.tsx`) keep their names | `Deals.tsx`, `RegisterDeal.tsx` |
| Database tables and columns | snake_case, tables plural | `registration_contacts.hubspot_contact_id` |
| Drizzle exports | camelCase, tables plural, columns camelCase | `registrationContacts.hubspotContactId` |
| Enum values | lower snake_case codes, never display labels. Display labels live in `src/lib/domain.ts` label maps | `middle_east`, `solution_sheet` |
| Types and interfaces | PascalCase; DTOs end in `Dto`, list rows in `Row` or `Item` | `RegistrationDetailDto` |
| Server actions | camelCase verb phrase ending in `Action`, one file per area in `src/server/actions/`; the repo function it calls has the same name without the suffix | `acceptRegistrationAction` calls `acceptRegistration` |
| Audit events | `noun.past_tense` | `registration.accepted` |

### B.2 Ids

All primary keys are `uuid` with `default gen_random_uuid()` (built into Postgres 16, no extension). UUID v4, not v7: nothing sorts by id (lists sort by a timestamp), and v4 needs no library. Ids are generated by the database on insert. Better Auth is configured not to generate ids (section M item 3) so that its tables follow the same rule. The only non-uuid keys are `hubspot_sync_state.key` (text), `partner_checklist (partner_id, step)` and `notification_prefs (user_id, category)` (composite). Foreign ids that point at external systems (`hubspot_company_id`, `hubspot_deal_id`, `hubspot_contact_id`) are `text`. `hubspot_outbox.subject_id` and `audit_log.subject_id` are `text`, not `uuid`, because the HubSpot plan's tests use ids such as `'r1'` and the audit subject may be a non-uuid.

### B.3 Time

- Every timestamp column is `timestamptz`, stored and compared in UTC. Drizzle mode is `date` (a JS `Date`).
- A calendar date with no time (`registered_on`, `protection_end`, `closed_on`, `resubmitted_on`) is `date`, Drizzle mode `string`, format `YYYY-MM-DD`, and is a UTC date. The portal has one business calendar: UTC. Known limit: a registration submitted between 00:00 and 05:30 IST is stamped with the previous Indian calendar day. Reconsider if partners complain.
- Code never calls `Date.now()` or `new Date()` inside a pure function or a repo function. It receives a `Clock` (section D.5, file `src/lib/clock.ts`) and calls `clock.now()` or `clock.today()`. Entry points (server actions, jobs, pages) create `systemClock`. Tests create `fixedClock('2026-11-06T14:02:00Z')`. This implements handoff amendment 6.
- DTOs carry timestamps as ISO 8601 strings (`2026-11-06T14:02:00.000Z`) and dates as `YYYY-MM-DD`. Display formatting (`6 Nov 2026`) is done by the pure helpers in `src/lib/dates.ts`, which take the server-supplied `today` as an argument. No component calls `new Date()` to decide what to show, which also keeps hydration stable (the mock already follows this rule).

### B.4 Money

None. Money is not stored in v1.

### B.5 Enums

Postgres `text` plus a `CHECK` constraint, with the allowed values defined once as a `const` tuple in `src/lib/domain.ts` and imported by both `schema.ts` (type and constraint) and the UI. Not `pgEnum`: adding a value to a text check is one reviewed migration line, `ALTER TYPE ... ADD VALUE` cannot run inside a migration transaction, and the HubSpot plan inserts plain strings.

### B.6 Deletion

| Record | Policy |
|---|---|
| `partners` | Never deleted. Status `inactive` or `suspended`. |
| `users` | Never deleted. Removal sets `status = 'disabled'` and `removed_at`. Their registrations, messages and audit entries stay with the company ("Removed users keep their deals with the company"). The person's Better Auth sessions are deleted by the action right after the repo transaction commits (`revokeAllSessions(userId)`), because `auth_session` is system-only under row level security and a viewer transaction deletes nothing. Access is cut at once either way, since `getViewer()` returns null for a disabled user. |
| `registrations` and its child tables | Never deleted by the app. The retention job (M5.3, system only) deletes rejected registrations older than 365 days. |
| `documents` | Soft: `deleted_at` is set, partners lose access immediately (RLS and repo both filter on it), the file is purged by `jobs/document-purge.ts` 30 days later. |
| `document_versions` | Hard delete by the purge job when `purge_after` has passed. |
| `applications` | Hard delete by the retention job after 365 days for `declined`. Approved ones stay. |
| `invites` | Never deleted; `revoked_at` or `accepted_at` closes them. |
| `notifications` | Never deleted in v1. |
| `audit_log` | Append only, never updated or deleted by anyone through the app role. |

### B.7 How Server Components, server actions and repos relate

```
page.tsx (Server Component)
   viewer = await requireCan(action)            src/server/auth/viewer.ts
   data   = await withViewer(viewer, (tx) => repo.fn(tx, viewer, input))
   return <ExistingClientScreen {...data} today={clock.today()} />

client component (existing mock markup)
   calls a server action from src/server/actions/*  ->  ActionResult<T>

server action (src/server/actions/*.ts, 'use server')
   runViewerAction(spec, raw, handler)           src/server/actions/run.ts
      Zod parse -> viewer -> withViewer(tx) {
         load record (repo)  ->  assertCan(viewer, action, subject)
         repo write  ->  recordAudit  ->  enqueue (outbox)  ->  notifyUsers
      } -> afterCommit effects (emails, revalidatePath) -> ActionResult

repo (src/server/repo/*.ts)
   (tx: Tx, viewer: Viewer, ...args) => DTO     never imports 'next/*', never sends email, never calls assertCan
                                                (it may call assertStaff(viewer) as a guard, see F.3)
```

Rules:

1. Pages and actions are the only callers of `withViewer`. Repo functions receive the `tx`; they never open their own transaction (they may use a savepoint through `tx.transaction`).
2. Repo functions return DTOs from `src/lib/dto.ts`, never Drizzle rows. A client component never imports from `@/db/schema`.
3. Authorisation is `assertCan` in the action or `requireCan` in the page. Isolation between partners is RLS plus repo filters, tested by the matrix. The two are separate layers and both must hold.
4. Public flows (apply, accept invite, request access, password reset, website intake) have no viewer. They call repo functions that take a `SystemActor` through `withSystem`, are registered in the isolation registry with scope `public`, and validate everything with Zod first.
5. Nothing in a request ever calls HubSpot, Brevo or R2 inside a database transaction. Emails and revalidation run after commit. File upload and download use presigned URLs.
6. Postgres applies SELECT policies to `RETURNING`. A repo that inserts a row another user owns (a notification for a staff user, a message) must not use `.returning()`. Generate the id with `crypto.randomUUID()` in the repo when it is needed afterwards (the column default still applies to every other insert).

### C.2 `src/db/client.ts` (W0-b, M0.3)

Two pools, one role (decided at the integration review: request 6, system 8, 14 connections in all, each with a 30 second connection timeout so a starved caller fails and is reported instead of waiting for ever). The system pool needs the larger share because `runLocked` holds one pooled connection for a whole job (the advisory lock is session level), `drainOutbox` holds a second inside its transaction and the handlers use a third through `db`, while the outbox, poll and intake jobs start together. The request pool never carries a session-level identity; every request sets its identity inside its transaction (F.1). The system pool is created with the startup option `-c app.kind=system`, so every connection it hands out is a system connection. System scope is used only by jobs, the HubSpot code, Better Auth, the public intake flows and tests. The HubSpot plan imports `db`, `pool` and `Db` from this file; those exports are the system scope.

```ts
import { drizzle, type NodePgDatabase } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import { env } from '@/env';
import * as schema from './schema';

export type Db = NodePgDatabase<typeof schema> & { $client: Pool };

const REQUEST_POOL_MAX = 6;
const SYSTEM_POOL_MAX = 8;
/** A caller that cannot get a connection within this time fails (and is reported) instead of waiting for ever. */
const CONNECTION_TIMEOUT_MS = 30_000;

const globalForDb = globalThis as unknown as { portalPools?: { app: Pool; system: Pool } };

const createPools = (): { app: Pool; system: Pool } => ({
  app: new Pool({ connectionString: env.DATABASE_URL, max: REQUEST_POOL_MAX, connectionTimeoutMillis: CONNECTION_TIMEOUT_MS }),
  system: new Pool({
    connectionString: env.DATABASE_URL,
    max: SYSTEM_POOL_MAX,
    connectionTimeoutMillis: CONNECTION_TIMEOUT_MS,
    options: '-c app.kind=system',
  }),
});

// Next dev reloads modules; keep one pair of pools per process so the role's connection limit is not exhausted.
const pools = globalForDb.portalPools ?? createPools();
globalForDb.portalPools = pools;

/** Request scope. Import only from src/server/repo/context.ts (enforced by src/server/repo/imports.test.ts). */
export const appDb: Db = drizzle(pools.app, { schema });
/** System scope: app.kind = 'system' on every connection. Jobs, HubSpot, auth, public intake, test helpers. */
export const db: Db = drizzle(pools.system, { schema });
export const systemDb: Db = db;
/** The system pool, for advisory locks (src/server/jobs/lock.ts). */
export const pool: Pool = pools.system;
```

### C.3 `src/db/rls.sql` (W0-b, M0.3)

Applied by `scripts/migrate.ts` after the Drizzle migrations, as `portal_owner`, on every run. It is idempotent (`CREATE OR REPLACE`, `DROP POLICY IF EXISTS`, grants repeat safely), so adding a table later means adding it to the lists below in the same Wave 0 or orchestrator migration batch. A table missing from the lists has no grants for `portal_app`, so the failure is loud (permission denied), not silent.

Three settings carry identity, all set with `set_config(name, value, true)` inside the request transaction (section F.1): `app.kind` is `partner`, `staff` or `system`; `app.partner_id` is the viewer's partner uuid or the empty string; `app.user_id` is the viewer's user uuid (decision 12 in section M: the master plan names two settings, the third makes notifications and preferences private to the user by RLS rather than by repo discipline).

Policy classes:

| Class | Tables | Partner viewer | Staff and system |
|---|---|---|---|
| Partner scoped (own `partner_id`) | `registrations`, `registration_contacts`, `registration_messages`, `registration_events`, `document_opens`, `access_requests`, `partner_checklist` | select, insert, update where `partner_id` is their own | all rows; delete only for system |
| Partner row | `partners` | select and update only their own row; no insert | all rows; insert staff and system |
| People | `users` | rows of their own partner, their own row, and every active partner manager row (name and email shown as the manager contact) | all rows |
| Invites | `invites` | rows of their own partner (`partner_id` not null) | all rows |
| Documents | `documents`, `document_audience` | audience rule (below), never soft-deleted | all rows, write staff and system |
| User private | `notifications`, `notification_prefs` | own `user_id` only; insert any (to notify another user) | own rows only; system all |
| Staff only | `applications`, `document_versions`, `registration_reminders`, `hubspot_sync_state` | none | all |
| Staff write, partner read of managers | `staff_scopes` | select rows of active partner managers only | all rows |
| Write only for everyone, read for staff | `audit_log`, `hubspot_outbox` | insert only | select; outbox update for staff and system |
| System only | `auth_session`, `auth_account`, `auth_verification`, `auth_two_factor` | none | system only (not even staff viewers) |

```sql
-- src/db/rls.sql. Run as portal_owner. Idempotent.

-- ---------------------------------------------------------------- identity helpers
CREATE OR REPLACE FUNCTION app_kind() RETURNS text LANGUAGE sql STABLE AS

### C.4 Role bootstrap, `scripts/db-bootstrap.sql` (W0-b, M0.3)

Run once per database as a Postgres superuser with `psql -v ON_ERROR_STOP=1 -v dbname=cleanstart_portal -v owner_password=... -v app_password=... -v conn_limit=20 -v allow_createdb=off -f scripts/db-bootstrap.sql`. On the droplet this is the "read the SQL first, needs the operator's approval" step (M0.3, M0.6). Locally `scripts/db-create.sh` (C.5) supplies development passwords, `conn_limit=-1` and `allow_createdb=on`.

`CONNECTION LIMIT` is cluster-wide per role. On a developer machine with several worktrees and test workers the production value of 20 is exhausted by design, which is why it is a variable. On the droplet the portal uses at most 14 (6 request, 8 system), leaving 6 for operators and the migration run at container start.

**Droplet capacity, OPEN DECISION FOR THE USER.** The droplet's Postgres `max_connections` is 20 today (`docs/operations/INCIDENTS.md`, 14 October), the CMS pool takes 15 and the portal needs 14. The sum of the CMS pool, the portal pools and 3 reserved superuser slots must stay under `max_connections`: 15 + 14 + 3 = 32, so `max_connections` has to be raised before launch (suggested value 50). That is a change to `postgresql.conf` and a Postgres restart on the droplet shared with the production CMS, so it needs the operator's approval and is a step of the handover checklist (plan 06, item 1.3); no agent runs it. If the operator declines, lower the pools instead (system 4, request 3, `CONNECTION LIMIT` 8) and accept slower jobs.

```sql
-- scripts/db-bootstrap.sql
\set ON_ERROR_STOP on

-- Cluster-wide roles, created once.
SELECT format('CREATE ROLE portal_owner LOGIN PASSWORD %L NOSUPERUSER NOBYPASSRLS NOREPLICATION', :'owner_password')
WHERE NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'portal_owner') \gexec

SELECT format('CREATE ROLE portal_app LOGIN PASSWORD %L NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION', :'app_password')
WHERE NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'portal_app') \gexec

SELECT format('ALTER ROLE portal_owner %s', CASE WHEN :'allow_createdb' = 'on' THEN 'CREATEDB' ELSE 'NOCREATEDB' END) \gexec
ALTER ROLE portal_app CONNECTION LIMIT :conn_limit;
ALTER ROLE portal_app SET statement_timeout = '15s';
ALTER ROLE portal_app SET lock_timeout = '10s';

-- The database, owned by portal_owner.
SELECT format('CREATE DATABASE %I OWNER portal_owner', :'dbname')
WHERE NOT EXISTS (SELECT 1 FROM pg_database WHERE datname = :'dbname') \gexec

SELECT format('REVOKE ALL ON DATABASE %I FROM PUBLIC', :'dbname') \gexec
SELECT format('GRANT CONNECT ON DATABASE %I TO portal_app', :'dbname') \gexec

\connect :dbname

-- Extensions need a superuser; pg_trgm powers the search indexes.
CREATE EXTENSION IF NOT EXISTS pg_trgm;

ALTER SCHEMA public OWNER TO portal_owner;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO portal_app;

-- Nothing is granted by default. rls.sql grants table by table.
ALTER DEFAULT PRIVILEGES FOR ROLE portal_owner IN SCHEMA public REVOKE ALL ON TABLES FROM PUBLIC;
ALTER DEFAULT PRIVILEGES FOR ROLE portal_owner IN SCHEMA public REVOKE ALL ON SEQUENCES FROM PUBLIC;
ALTER DEFAULT PRIVILEGES FOR ROLE portal_owner IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM PUBLIC;
ALTER DEFAULT PRIVILEGES FOR ROLE portal_owner IN SCHEMA public REVOKE ALL ON TABLES FROM portal_app;
ALTER DEFAULT PRIVILEGES FOR ROLE portal_owner IN SCHEMA public REVOKE ALL ON SEQUENCES FROM portal_app;
```

### C.5 `scripts/db-create.sh` and migrations (W0-b, M0.3)

`scripts/db-create.sh <database-name>` (handoff amendment 3): idempotent. It reads the superuser connection from `PORTAL_PG_ADMIN_URL` (default `postgresql://postgres@localhost:5432/postgres`, the password coming from `PGPASSWORD`), runs `db-bootstrap.sql` with development values (`owner_password=portal_owner_dev`, `app_password=portal_app_dev`, `conn_limit=-1`, `allow_createdb=on`), and prints the three URLs to put in `.env`. `db-create.sh <name> --recreate` first drops the database (and, for a `*_test` database, its four worker clones `_w1` to `_w4`) and creates it again; it is needed whenever `0000_init.sql` is regenerated, because the Drizzle migrator re-applies a changed first migration. Use it only on a worktree's own databases. `scripts/contract-block.sh` (W0-a) prints the Nth fenced code block under a contracts heading, which is how W0 copies the code blocks of this file mechanically. The development role passwords are constants in the script because the role names and passwords exist only on the developer's own Postgres, never on the droplet.

Migration scheme:

| File | Content | Writer |
|---|---|---|
| `drizzle/0000_init.sql` | Generated by `drizzle-kit generate` from `schema.ts`, then reviewed by hand. Its first line is `CREATE EXTENSION IF NOT EXISTS pg_trgm;` (a no-op where the bootstrap ran). It already includes the three extra `auth_two_factor` columns of C.1; there is no separate auth migration. | W0-b only |
| `drizzle/meta/*` | drizzle-kit journal and snapshots. Committed. | W0-b only |
| `drizzle/0001_*.sql` and later | One numbered file per batch of schema changes, hand-checked, written by the orchestrator when a track writes a `blocked` line asking for a schema change (handoff amendment 4). | orchestrator only |
| `src/db/rls.sql` | Re-applied after every migration run by `scripts/migrate.ts`. A schema change that adds a table also edits the lists in this file in the same commit. | W0-b, then orchestrator |

`package.json` scripts added by W0-b (the dependencies are added once by W0-a): `db:generate` (`drizzle-kit generate`), `db:migrate` (`tsx --env-file=.env scripts/migrate.ts`), `db:seed` (`tsx --env-file=.env scripts/seed-dev.ts`), `test` (`vitest run`). `scripts/migrate.ts` connects with `DATABASE_OWNER_URL`, runs the Drizzle migrator on `drizzle/`, then executes `src/db/rls.sql` in one transaction. Running it twice must succeed and change nothing (acceptance of M0.3). In production it runs on container start before `next start`.

**Only Wave 0 (W0-b) writes `drizzle/0000_init.sql` and `src/db/schema.ts`.** No other track edits either file or adds a migration. A track that needs a column writes `blocked`.

### D.3 Subject type and the permission matrix

```ts
import type { DealRegion, PartnerRegion } from '@/lib/domain';

/**
 * What an action is about. Every field is optional: an omitted field means "not specified" and the check
 * passes on that dimension (list screens pass no subject; the repo then scopes the rows). A present field
 * is checked. null means "specified and unknown", which fails the check.
 */
export interface PolicySubject {
  /** The partner that owns the record. */
  partnerId?: string | null;
  /** Region of the record (a deal's region, or a partner's region). */
  region?: PartnerRegion | DealRegion | null;
  /** The user who created the record (registrations.registered_by). */
  ownerUserId?: string | null;
  /** The user being acted on (account actions must target the viewer; team actions may not target the viewer's own role). */
  targetUserId?: string | null;
}
```

Legend for the table. `Y` yes with no condition on the subject. `own` yes when the record belongs to the viewer's own company (`subject.partnerId` equals `viewer.partnerId`, or is omitted). `mine` yes only when the viewer created the record (`subject.ownerUserId` equals `viewer.id`, or is omitted on a list, where the repo filters `registered_by`), and the record is the viewer's own company's. `region` yes when the record's region is inside the viewer's staff scope (`viewer.region` is `all`, or equals the record's region; an omitted region passes and the repo filters). `-` no. Columns: PA partner admin, PS partner sales, PT partner technical, SM staff partner manager, SS staff sales, SK staff marketing.

// src/lib/dates.ts. Pure. Moved from the mock's components/deals/dates.ts with the clock made explicit.
const MONTHS = ['Jan', 'Feb', 'Mar', 'Apr', 'May', 'Jun', 'Jul', 'Aug', 'Sep', 'Oct', 'Nov', 'Dec'] as const;
const DAY_MS = 86_400_000;

const parse = (iso: string): number => {
  const [year = 1970, month = 1, day = 1] = iso.slice(0, 10).split('-').map(Number);
  return Date.UTC(year, month - 1, day);
};

export const daysBetween = (fromIso: string, toIso: string): number => Math.round((parse(toIso) - parse(fromIso)) / DAY_MS);
export const addDays = (iso: string, days: number): string => new Date(parse(iso) + days * DAY_MS).toISOString().slice(0, 10);
/** "4 Nov" */
export const fmtShort = (iso: string): string => `${new Date(parse(iso)).getUTCDate()} ${MONTHS[new Date(parse(iso)).getUTCMonth()] ?? ''}`;
/** "4 Nov 2026" */
export const fmtLong = (iso: string): string => `${fmtShort(iso)} ${new Date(parse(iso)).getUTCFullYear()}`;
/** Days from `today` to `endIso`; negative once the date has passed. */
export const daysLeft = (endIso: string, today: string): number => daysBetween(today, endIso);
export const plural = (count: number, word: string): string => `${count} ${word}${count === 1 ? '' : 's'}`;
/** Weekdays in the half open range (from, to]. Saturdays and Sundays do not count; no holiday calendar. */
export const businessDaysBetween = (fromIso: string, toIso: string): number => {
  let count = 0;
  for (let cursor = addDays(fromIso, 1); cursor <= toIso; cursor = addDays(cursor, 1)) {
    const weekday = new Date(parse(cursor)).getUTCDay();
    if (weekday !== 0 && weekday !== 6) count += 1;
  }
  return count;
};
/** "Today, 14:02" style labels for timestamps, in UTC. */
export const fmtTimestamp = (iso: string, today: string): string => {
  const date = iso.slice(0, 10);
  const time = iso.slice(11, 16);
  const lead = date === today ? 'Today' : date === addDays(today, -1) ? 'Yesterday' : fmtShort(date);
  return `${lead}, ${time}`;
};

```ts
export type ErrorCode =
  | 'validation'
  | 'unauthenticated'
  | 'forbidden'
  | 'not_found'
  | 'conflict'
  | 'rate_limited'
  | 'integration'
  | 'dependency_pending'
  | 'internal';

  /** Dot path into the input, e.g. "contacts.0.email". Empty string for a form level issue. */
  path: string;
  message: string;
}

  /** Internal message for logs; defaults to safeMessage. Never shown to a user. */
  message?: string;
  cause?: unknown;
}

/**
 * Base class. safeMessage is the only text that may reach a user or a client component.
 * httpStatus is used by route handlers; server actions map the code to ActionResult.
 */

  readonly code: ErrorCode;
  readonly httpStatus: number;
  readonly safeMessage: string;

  constructor(code: ErrorCode, httpStatus: number, safeMessage: string, options: PortalErrorOptions = {}) {
    super(options.message ?? safeMessage, options.cause === undefined ? undefined : { cause: options.cause });
    this.name = 'PortalError';
    this.code = code;
    this.httpStatus = httpStatus;
    this.safeMessage = safeMessage;
  }
}

export class ValidationError extends PortalError {
  readonly issues: FieldIssue[];

  constructor(issues: FieldIssue[], safeMessage = 'Check the highlighted fields.') {
    super('validation', 400, safeMessage);
    this.name = 'ValidationError';
    this.issues = issues;
  }
}

/** Authentication is missing or the session is gone. Pages redirect to /sign-in; actions return code "unauthenticated". */
export class UnauthenticatedError extends PortalError {
  constructor(message = 'Sign in to continue.') {
    super('unauthenticated', 401, message);
    this.name = 'UnauthenticatedError';
  }
}

/** The viewer is known but may not do this. Never used to hide existence: use NotFoundError for that. */
export class ForbiddenError extends PortalError {
  constructor(internalMessage?: string) {
    super('forbidden', 403, 'You do not have access to this.', internalMessage ? { message: internalMessage } : {});
    this.name = 'ForbiddenError';
  }
}

/**
 * The record does not exist or is not visible to the viewer. Both cases look identical on purpose (a non-audience
 * partner gets 404, not 403, so ids cannot be probed).
 */

  readonly resource: string;

  constructor(resource: string, internalMessage?: string) {

    this.name = 'NotFoundError';
    this.resource = resource;
  }
}

export class ConflictError extends PortalError {

  readonly upstreamStatus: number | null;

  constructor(service: IntegrationService, message: string, options: { status?: number; cause?: unknown } = {}) {
    super('integration', 502, 'A connected service is not responding. Try again in a moment.', {
      message: `${service}: ${message}`,
      ...(options.cause === undefined ? {} : { cause: options.cause }),

    this.name = 'IntegrationError';
    this.service = service;

  if (error instanceof RateLimitError) return { code: error.code, message: error.safeMessage, retryAfterSeconds: error.retryAfterSeconds };
  if (error instanceof PortalError) return { code: error.code, message: error.safeMessage };

};

### F.1 `src/server/repo/context.ts` (W0-d, M1.2)

```ts
import { sql } from 'drizzle-orm';
import { appDb, type Db, systemDb } from '@/db/client';
import type { SystemActor, Viewer } from '@/server/auth/types';
import { ForbiddenError } from '@/server/errors';
import { log } from '@/server/log';

/** The transaction handle every repo function receives. */
export type Tx = Parameters<Parameters<Db['transaction']>[0]>[0];

/** Anything that can run a query: the system `db` (jobs, tests) or a transaction. Used by helpers shared with the HubSpot code. */
export type Queryable = Db | Tx;

/**
 * Runs `fn` in one transaction on the request pool with the viewer's identity set for row level security.
 * set_config(..., true) is transaction local: the settings vanish at commit or rollback, so a pooled connection
 * never carries one request's identity into the next. Pages and server actions are the only callers.
 */
export const withViewer = <T>(viewer: Viewer, fn: (tx: Tx) => Promise<T>): Promise<T> =>
  appDb.transaction(async (tx) => {
    await tx.execute(
      sql`select set_config('app.kind', ${viewer.kind}, true),
                 set_config('app.partner_id', ${viewer.partnerId ?? ''}, true),
                 set_config('app.user_id', ${viewer.id}, true)`,
    );
    return fn(tx);
  });

/**
 * Runs `fn` in one transaction on the system pool (app.kind = 'system' on every connection, set at connect).
 * For code with no viewer. The actor is for logging and for audit entries the callee writes; it grants nothing.
 * Public repo functions (scope "public" in the isolation registry) are the only repo functions called through this.
 */
export const withSystem = <T>(actor: SystemActor, fn: (tx: Tx) => Promise<T>): Promise<T> =>
  systemDb.transaction(async (tx) => {
    await tx.execute(sql`select set_config('app.kind', 'system', true), set_config('app.user_id', '', true), set_config('app.partner_id', '', true)`);
    log.debug({ actor: actor.label }, 'withSystem');
    return fn(tx);
  });

/** Throws ForbiddenError unless the viewer is CleanStart staff. Cheap guard for staff only repo functions. */
export const assertStaff = (viewer: Viewer): void => {
  if (viewer.kind !== 'staff') throw new ForbiddenError('staff only');
};

The first rule exempts `*.test.ts` files, because `context.test.ts` must use `appDb` to prove that a request identity does not leak into the next transaction. The jobs, the HubSpot folder, `src/server/auth/**`, `src/server/intake/**`, `scripts/**` and test files may import `db` and `pool`.

### F.2 System jobs and the HubSpot code

Jobs and everything under `src/server/hubspot/` run on the system pool directly: they import `db` (type `Db`) from `@/db/client` and pass it into the functions the HubSpot plan already defines (`drainOutbox({ db, ... })`, `buildHandlers(db, hs, pipelineId)`, `pollDeals({ db, ... })`). ### F.3 Repo function shape

```ts

export declare function viewerFn(tx: Tx, viewer: Viewer, input: unknown, clock?: Clock): Promise<unknown>;   // scope: tenant | staff-only | own-user

```

1. Order of parameters: `tx`, then `viewer` or `actor`, then one `input` object (when more than one value is needed), then `clock` when time matters.
2. Single record getters throw `NotFoundError` when the row does not exist or is not visible. List functions return an empty array or an empty page. A write by id that affects zero rows throws `NotFoundError`.
3. A staff only function calls `assertStaff(viewer)` first, so a partner viewer gets `ForbiddenError` before RLS even runs.
4. A function that creates a row for another user (a notification, a thread message to staff) does not use `.returning()` (B.7 rule 6).
5. Every write function is idempotent where the caller can retry, or throws `ConflictError` with a `reason`.
6. No repo function sends email, calls `revalidatePath`, calls HubSpot, or imports from `next/*`.

/**
 * Call after commit (inside ctx.afterCommit). Reads in system scope, drops disabled users and the users who
 * switched the category off, and returns who should get an email. Staff notifications (category null) always email.
 */
export async function resolveEmailRecipients(items: readonly NewNotification[]): Promise<EmailRecipient[]> {
  if (items.length === 0) return [];
  const ids = [...new Set(items.map((i) => i.userId))];
  const people = await db.select({ id: users.id, email: users.email, name: users.name, status: users.status }).from(users).where(inArray(users.id, ids));
  const prefs = await db.select().from(notificationPrefs).where(inArray(notificationPrefs.userId, ids));
  const out: EmailRecipient[] = [];
  for (const item of items) {
    const person = people.find((p) => p.id === item.userId);
    if (!person || person.status === 'disabled') continue;
    const category = NOTIFICATION_CATEGORY_OF[item.kind];
    const stored = category ? prefs.find((p) => p.userId === item.userId && p.category === category) : undefined;
    const wanted = category === null ? true : (stored?.email ?? NOTIFICATION_PREF_DEFAULTS[category]);
    if (wanted) out.push({ userId: person.id, email: person.email, name: person.name, kind: item.kind, notification: item });
  }
  return out;

### F.6 The isolation registry (`src/server/repo/isolation.registry.ts`, W0-d, M1.2)

Each repo module ends with an `isolation` export that lists every function it exports, with how to probe it. One central test loads every module under `src/server/repo/`, and fails when an exported function is not in that module's `isolation` or a registered name is not exported. This keeps the registry distributed (no track edits a shared file) and makes a missing entry a red build. The central test `isolation.test.ts` imports repo modules with `import(/* @vite-ignore */ <absolute path>)` (Vite warns on a computed relative import inside its own directory), imports `sql` from `drizzle-orm`, and starts with a test that seeds two tenants and proves they cannot see each other through `withViewer`, so the file has a real test before the first repo module exists (Vitest fails a file whose only suite is empty).

```ts
// src/server/repo/isolation.registry.ts
import type { PartnerViewer, StaffViewer } from '@/server/auth/types';
import type { Tx } from './context';

/** Ids and viewers of two seeded partners plus a staff viewer. Built by seedTwoTenants() in src/db/test-helpers.ts. */
export interface TenantFixture {
  partnerId: string;
  viewer: PartnerViewer;
  adminViewer: PartnerViewer;
  salesViewer: PartnerViewer;
  userId: string;
  registrationId: string;
  messageId: string;
  contactId: string;
  inviteId: string;
  accessRequestId: string;
  documentId: string;
  openId: string;
}

export interface IsolationContext {
  a: TenantFixture;
  b: TenantFixture;
  staff: StaffViewer;
  /** A document restricted to partner B by audience; partner A must not see it. */
  documentForBOnly: string;
  /** An application, a staff user, an audit row: staff only data. */
  applicationId: string;
  staffUserId: string;
  auditId: string;
}

export type IsolationExpect =
  | 'empty'       // result is [], null, 0, an empty page, or an object whose every array is empty
  | 'not_found'   // throws NotFoundError
  | 'forbidden'   // throws ForbiddenError
  | 'unchanged';  // returns normally and the targeted rows are byte-for-byte unchanged afterwards

export type IsolationEntry =
  | {
      /** Call as partner A with partner B's ids. Must leak nothing and change nothing. */
      scope: 'tenant';
      probe: (tx: Tx, viewer: PartnerViewer, ctx: IsolationContext) => Promise<unknown>;
      expect: IsolationExpect;
      /** Rows (table and id) that must be unchanged afterwards. */
      untouched?: (ctx: IsolationContext) => Array<{ table: string; id: string }>;
    }
  | {
      /** Staff only. Called as a partner viewer, must throw ForbiddenError (assertStaff) or return nothing. */
      scope: 'staff-only';
      probe: (tx: Tx, viewer: PartnerViewer, ctx: IsolationContext) => Promise<unknown>;
      expect: 'forbidden' | 'empty';
    }
  | {
      /** The row belongs to a user. Called as another user of the same partner, must see nothing of the first user. */
      scope: 'own-user';
      probe: (tx: Tx, viewer: PartnerViewer, ctx: IsolationContext) => Promise<unknown>;
      expect: 'empty' | 'not_found';
    }
  | {
      /** Takes (db or tx) only and relies on RLS (integrationHealth). Called with a partner A transaction, must return zeros. */
      scope: 'rls-only';
      probe: (tx: Tx, ctx: IsolationContext) => Promise<unknown>;
      check: (result: unknown) => void;
    }
  | {
      /** No viewer: a public flow taking a SystemActor. Validated by its own unit test, not probed here. */
      scope: 'public';
      reason: string;
    }
  | {
      /** A pure helper that does no data access (a row to DTO mapper). */
      scope: 'exempt';
      reason: string;
    };

export type IsolationMap<Names extends string> = { [K in Names]: IsolationEntry };

/**
 * Usage, at the bottom of a repo module:
 *   export const isolation = defineIsolation<keyof typeof exportedFns>({ ... });
 * `exportedFns` is a local object literal that groups the module's exported functions. The central test
 * compares Object.keys(isolation) with the module's function exports (excluding `isolation` itself).
 */
export const defineIsolation = <Names extends string>(entries: IsolationMap<Names>): IsolationMap<Names> => entries;
```

Probe conventions: a `tenant` probe passes partner B's ids (`ctx.b.registrationId`, `ctx.b.partnerId`, `ctx.documentForBOnly`) while running as `ctx.a.viewer`. ```ts
// src/server/actions/run.ts
import * as Sentry from '@sentry/nextjs';
import { revalidatePath } from 'next/cache';
import { headers } from 'next/headers';
import type { z } from 'zod';
import { type Clock, systemClock } from '@/lib/clock';
import { log } from '@/server/log';
import { requireActionViewer } from '@/server/auth/viewer';
import type { Viewer } from '@/server/auth/types';
import { describeError, isPortalError, ValidationError } from '@/server/errors';
import { type ActionResult, fail, ok } from './result';

export interface ActionSpec<S extends z.ZodType> {
  /** Stable name for logs and Sentry, e.g. "registration.accept". */
  name: string;
  schema: S;
}

export interface ActionContext {
  viewer: Viewer;
  clock: Clock;
  /** Runs after the handler returns successfully, outside any transaction. Failures are logged, never thrown. */
  afterCommit(effect: () => Promise<void>): void;
  /** Shorthand for afterCommit(() => revalidatePath(path)). */
  revalidate(path: string): void;
}

export interface PublicActionContext {
  clock: Clock;
  /** First address in x-forwarded-for, or null. For rate limiting and Turnstile. */
  ip: string | null;
  afterCommit(effect: () => Promise<void>): void;
  revalidate(path: string): void;
}

const parseInput = <S extends z.ZodType>(schema: S, raw: unknown): z.output<S> => {
  const parsed = schema.safeParse(raw);
  if (!parsed.success) {
    throw new ValidationError(parsed.error.issues.map((i) => ({ path: i.path.join('.'), message: i.message })));
  }
  return parsed.data;
};

const collector = (): { effects: Array<() => Promise<void>>; afterCommit: (e: () => Promise<void>) => void; revalidate: (p: string) => void } => {
  const effects: Array<() => Promise<void>> = [];
  return {
    effects,
    afterCommit: (effect) => void effects.push(effect),
    revalidate: (path) => void effects.push(async () => revalidatePath(path)),
  };
};

const flush = async (name: string, effects: Array<() => Promise<void>>): Promise<void> => {
  for (const effect of effects) {
    try {
      await effect();
    } catch (error) {
      log.error({ action: name, err: error }, 'after-commit effect failed');
      Sentry.captureException(error, { tags: { action: name, phase: 'after_commit' } });
    }
  }
};

const toFailure = (name: string, error: unknown): ActionResult<never> => {
  if (!isPortalError(error)) {
    log.error({ action: name, err: error }, 'action failed unexpectedly');
    Sentry.captureException(error, { tags: { action: name } });
  }
  return fail(describeError(error));
};

/** The only way a signed-in server action runs. See the worked example in F.8. */
export async function runViewerAction<S extends z.ZodType, T>(
  spec: ActionSpec<S>,
  raw: unknown,
  handler: (ctx: ActionContext, input: z.output<S>) => Promise<T>,
): Promise<ActionResult<T>> {
  const { effects, afterCommit, revalidate } = collector();
  try {
    const input = parseInput(spec.schema, raw);
    const viewer = await requireActionViewer();
    const data = await handler({ viewer, clock: systemClock, afterCommit, revalidate }, input);
    await flush(spec.name, effects);
    return ok(data);
  } catch (error) {
    return toFailure(spec.name, error);
  }
}

/** For actions with no session: apply, accept invite, request access, forgot password. Rate limit and Turnstile run inside the handler. */
export async function runPublicAction<S extends z.ZodType, T>(
  spec: ActionSpec<S>,
  raw: unknown,
  handler: (ctx: PublicActionContext, input: z.output<S>) => Promise<T>,
): Promise<ActionResult<T>> {
  const { effects, afterCommit, revalidate } = collector();
  try {
    const input = parseInput(spec.schema, raw);
    const forwarded = (await headers()).get('x-forwarded-for');
    const ip = forwarded ? (forwarded.split(',')[0]?.trim() ?? null) : null;
    const data = await handler({ clock: systemClock, ip, afterCommit, revalidate }, input);
    await flush(spec.name, effects);
    return ok(data);
  } catch (error) {
    return toFailure(spec.name, error);
  }
}
```

`log` is the small JSON logger in `src/server/log.ts` (W0-c, M0.4; there is no `pino` dependency): it exports `log`, `createLogger` and `redact`, writes one JSON line per entry, keeps the call shape `log.info(obj, msg)`, `log.warn`, `log.error`, and redacts keys matching `authorization|password|token|cookie|secret`. Server action files start with `'use server'`, and each exported action is an `export async function` that calls `runViewerAction` or `runPublicAction` (not an `export const` wrapper; section M item 9).

import { assertCan } from '@/server/auth/policies';
import { buildDealAccepted } from '@/server/email/templates';
import { sendEmail } from '@/server/email/send';
import { enqueue } from '@/server/hubspot/outbox';
import { notifyUsers, resolveEmailRecipients } from '@/server/notify';
import { acceptRegistration, lockRegistration } from '@/server/repo/registrations';
import { withViewer } from '@/server/repo/context';
import { absoluteUrl } from '@/server/urls';
import { ROUTES } from '@/lib/routes';
import { type ActionResult } from './result';
import { runViewerAction } from './run';
import type { RegistrationDetailDto } from '@/lib/dto';

const acceptSchema = z.object({ id: z.string().uuid() });

export async function acceptRegistrationAction(raw: unknown): Promise<ActionResult<RegistrationDetailDto>> {
  return runViewerAction({ name: 'registration.accept', schema: acceptSchema }, raw, async (ctx, input) => {
    const decision = await withViewer(ctx.viewer, async (tx) => {
      // 1. Load inside the transaction and lock the row, so two staff clicking Accept at once decide it once.
      const current = await lockRegistration(tx, ctx.viewer, input.id);
      // 2. Authorise against the record, not against the request.
      assertCan(ctx.viewer, 'registration.decide', { partnerId: current.partnerId, region: current.region });
      // 3. Write. The repo throws ConflictError('already_decided') unless status is pending.
      const result = await acceptRegistration(tx, ctx.viewer, { id: current.id }, ctx.clock);
      // 4. One audit entry, same transaction.
      await recordAudit(tx, ctx.viewer, {
        event: 'registration.accepted',
        target: `${result.registration.customer}, ${PRODUCT_LABEL[result.registration.product]}, from ${result.partnerName}`,
        note: `Protected until ${result.registration.protectionEnd}. HubSpot deal queued.`,
        partnerId: result.registration.partnerId,
        subject: { type: 'registration', id: result.registration.id },
      });
      // 5. Outbox, same transaction. The version is the decision time so an undo followed by a new accept enqueues again.
      await enqueue(tx, {
        op: 'registration.create',
        subjectId: result.registration.id,
        version: String(Date.parse(result.decidedAt)),
      });
      // 6. In-app notifications, same transaction.
      const items = result.recipientUserIds.map((userId) => ({
        userId,
        kind: 'registration_accepted' as const,
        title: `${result.registration.customer} was accepted`,
        body: `${PRODUCT_LABEL[result.registration.product]}, protected until ${result.registration.protectionEnd}`,
        link: ROUTES.partner.deal(result.registration.id),
      }));
      await notifyUsers(tx, items);
      return { result, items };
    });

    // 7. After commit: revalidate, then email the people whose preferences allow it. A failure here never fails the action.
    ctx.revalidate(ROUTES.admin.approvals);
    ctx.revalidate(ROUTES.partner.deals);
    ctx.revalidate(ROUTES.partner.deal(decision.result.registration.id));
    ctx.afterCommit(async () => {
      for (const to of await resolveEmailRecipients(decision.items)) {
        await sendEmail(
          buildDealAccepted({
            to: { email: to.email, name: to.name },
            recipientName: to.name,
            customer: decision.result.registration.customer,
            productLabel: PRODUCT_LABEL[decision.result.registration.product],
            partnerName: decision.result.partnerName,
            protectionEnd: decision.result.registration.protectionEnd ?? '',
            dealUrl: absoluteUrl(ROUTES.partner.deal(decision.result.registration.id)),
          }),
        );
      }
    });
    return decision.result.registration;
  });
}
```

The client calls `await acceptRegistrationAction({ id })`, reads `result.ok`, shows `result.error.message` inline or in a toast, never `window.alert`. The action never calls HubSpot; the outbox row it wrote is drained by the scheduled job.

## G. The outbox contract (HubSpot plan 4.4, copied so other plans need not read it)

Every state change that HubSpot must learn about writes one `hubspot_outbox` row in the same transaction as the change. Nothing in a request calls HubSpot. The job `hubspot-outbox` (every minute, H4.4) drains the table through the `HubspotApi` interface. Verified against HubSpot plan 4.4, 4.5, 4.6, 4.8 and 5; the edits needed are in section M.

```ts
// src/server/hubspot/outbox.ts (H4.4). The only part other plans call is `enqueue`.
import type { Db } from '@/db/client';
import type { Tx } from '@/server/repo/context';
import type { OutboxOp } from '@/lib/domain';

export type { OutboxOp };

export declare function enqueue(
  tx: Pick<Db | Tx, 'insert'>,
  input: { op: OutboxOp; subjectId: string; version: string; payload?: Record<string, unknown> },
): Promise<void>;
```

Behaviour: inserts `{ op, subjectId, payload: payload ?? {}, idempotencyKey: `${op}:${subjectId}:${version}` }` with `ON CONFLICT (idempotency_key) DO NOTHING`. Status starts `pending`, `attempts` 0, `next_attempt_at` now. It never throws on a duplicate. It is safe to call inside `withViewer` because `hubspot_outbox` allows INSERT for every identity (C.3).

The ops, who enqueues them, and the exact `version` each caller must pass (the version is what makes a legitimate second operation different from a duplicate):

| Op | `subjectId` | `version` | Enqueued by | Handler effect |
|---|---|---|---|---|
| `partner.upsert` | partner id | `'1'` on application approval and on Add partner; after a profile edit `String(updatedAt.getTime())` of the row `updateCompanyProfile` returns, and after a category, manager, status or re-approval edit `String(clock.now().getTime())` (`PartnerListRow` carries no `updatedAt`; still a fresh key per edit) | `actions/applications.ts` (M1.4), `actions/partners.ts` (M1.7, M4.1) | create or update the HubSpot company with `cleanstart_partner = true`; stores `partners.hubspot_company_id` |
| `user.upsert` | user id | `'1'` | `actions/invites.ts` when an invite is accepted (M1.5) | upsert the contact and associate it with the partner company; stores `users.hubspot_contact_id`. Waits (`DependencyPending`) until the partner company exists |
| `registration.create` | registration id | `String(Date.parse(decidedAt))`, the decision time as milliseconds (section M, inconsistency 4: the HubSpot plan says `'1'`) | `actions/decisions.ts` on accept (M2.2) | create the deal, associate partner company, customer company and contacts; stores `hubspot_deal_id`, `hubspot_stage_id`. No-op unless status is `accepted` and no deal id is stored |
| `registration.update_end` | registration id | the new `protection_end` (`YYYY-MM-DD`) | `actions/extension.ts` when an extension is granted (M2.4) | write `protection_end_date` on the deal. Waits until the deal exists |
| `registration.expire` | registration id | the date it expired (`YYYY-MM-DD`) | `jobs/expiry.ts` (H4.8) | move the deal to the stage "Registration expired" |

`payload` is not used in v1: callers omit it and the handlers ignore it (`Handlers = Record<OutboxOp, (subjectId, payload) => Promise<void>>`). A future op that needs data adds a typed payload through a contract change request.

Retry rules (H4.3 `nextDelayMs`, H4.4 `drainOutbox`): attempts 1 to 5 back off 1 minute, 5 minutes, 30 minutes, 2 hours, 12 hours; the sixth failure sets `status = 'failed'` and reports to Sentry. `DependencyPending` reschedules in one minute without counting an attempt. A batch is at most 20 rows, taken with `FOR UPDATE SKIP LOCKED` inside a transaction on the system `db`. Staff can set `failed` rows back to `pending` with `attempts = 0` from the health card (`integration.retry_failed`).

The handlers and the drain read and write `registrations`, `partners`, `users`, `registration_contacts`, `registration_events`, `hubspot_outbox` and `hubspot_sync_state` as the system role; they are unaffected by tenant policies.

| `PartnerReportRow`, `ProductReportRow`, `FollowUp` (`data/reports.ts`) | same names in `dto.ts` | `FOLLOW_UPS`, `PARTNER_ROWS`, `PRODUCT_ROWS` become the output of `getAdminReports`; `filterPartnerRows` and `partnersToCsv` stay client side as pure functions moved to `src/lib/report-view.ts` (R) |
| `Persona` (`shell/personas.ts`) | `ShellDto` | loaded once per request by the layout through `getShell` |

Notes on the DTOs (decided at the integration review): (1) **Invite only rows.** The Team, partner detail and staff lists show a person who has only been invited as a row whose `id` is the invite id (`inviteId` equals `id`, and the DTO carries no user id); `removeStaff` accepts such an id and withdraws the invite. A `TeamMemberDto` whose invite and `users` row (status `invited`) both exist keeps its user id. Consumers (R, A) must not assume every `TeamMemberDto.id` or `StaffMemberDto.id` is a user id. (2) `PartnerListRow.won` is deals won this calendar year (`closed_on`, else `registered_on`), computed against the database date, to match the "Won YTD" column header. (3) Three mock details are dropped on purpose because the schema has no source for them and a migration is not worth it in v1: the Company screen's "Accepted by" row, the staff list's "Invited 5 Nov" date (it reads "Invite pending") and the two partners KPIs `usersActiveThisMonth` and `dealsThisQuarter` (the screen shows "partners signed in this month" and "protected deals" instead); an `invites.invitee_name` column is not added, so the accept page derives a colleague's or staff member's name from the email. (4) `previewInvite` fills `agreementVersion` only from the partner row; the server's `loadInvitePreview` overrides it with `PARTNER_AGREEMENT_VERSION` when the agreement is needed, since a new partner has none stored yet.

## J. Test infrastructure

### J.1 Strategy

- Vitest 2 (`environment: 'node'`), co-located `*.test.ts`. Repo, outbox, poll, intake and policy tests run against a real Postgres 16.
- **One database per Vitest worker**, not one transaction per test. The HubSpot plan's code opens its own transactions (`drainOutbox`), takes advisory locks on other connections (`runLocked`) and uses `FOR UPDATE SKIP LOCKED`; none of that works inside a wrapping rolled back transaction. Each test file resets its own database with `resetDb` in `beforeEach` (TRUNCATE of every table, a few milliseconds on an empty schema).
- **Parallel files.** `globalSetup` migrates the base database `PORTAL_TEST_DATABASE_URL` (as owner, through the same `scripts/migrate.ts` code path), then clones it into `<name>_w1` to `<name>_w4` with `CREATE DATABASE ... TEMPLATE`. Vitest runs `maxWorkers: 4` with `pool: 'forks'`, and every file in worker `n` connects to `<name>_wn` (the setup file derives the name from `VITEST_POOL_ID`). Two test files therefore never share rows, while files in the same worker run one after the other. Concurrency tests (advisory locks, skip locked) open their second connection inside the same test on the worker's database, which is what the handoff requires.
- The test role is `portal_app` with a system connection (`options: '-c app.kind=system'`), so fixtures can insert anything, and `withViewer` is exercised for real with RLS on. `resetDb` uses the owner URL because the app role has no TRUNCATE.
- HubSpot, Brevo, R2 and Turnstile are always faked in tests (`FakeHubspot` from H4.2, `FakeEmailTransport`, `FakeFileStorage`, the Turnstile always-pass keys).

## M. Known unknowns, inconsistencies and decisions

### M.1 Known unknowns (library behaviour not verifiable without installing packages)

M.5 is the consolidated list of every known unknown of the contracts and of the six area plans, de-duplicated and ordered by the Wave 0 task that must verify each first; this section keeps the contracts' own items under the numbers other documents cite. Each item is verified by the Wave 0 agent named first, as the first step of that task, in a scratch file before relying on it. A failed check is fixed with the stated fallback and recorded in the progress log; if the fallback also fails the task is `blocked`.

1. **Drizzle on node-postgres: `set_config` in a transaction, the `Tx` type, and `Pick<Db | Tx, 'insert'>`.** W0-b, W0-d. Verify: `appDb.transaction` runs `select set_config(..., true)` and a following query in the same transaction sees it through `current_setting`; `Tx` as derived in F.1 has `select`, `insert`, `update`, `execute`; a `Tx` and a `Db` are both assignable to `Pick<Db | Tx, 'insert'>`. Fallback: a local `type Writer = Pick<Tx, 'insert'>` used by `enqueue`, `recordAudit` and `notifyUsers`, and `Tx` declared as `PgTransaction<NodePgQueryResultHKT, typeof schema, ExtractTablesWithRelations<typeof schema>>`.
2. **Better Auth with the portal's `users` table as its user model.** W0-e. Verify the config (`user: { modelName: 'users' }`, `fields` mapping if column names differ, `additionalFields` for `kind`, `role`, `partnerId`, `status`, `twoFactorEnabled`) against the installed version, and that the Drizzle adapter accepts a `schema` map of our tables. Fallback: Better Auth gets its own `auth_user` table and `users.auth_user_id uuid references auth_user(id)`; `getViewer` joins. Wave 0 owns `schema.ts` and `drizzle/0000_init.sql` until the `portal-w0` tag and the database holds no data yet, so W0-e may amend both and regenerate `0000_init.sql`; this is the one exception to "only W0-b writes the schema", and it ends at the tag.

### M.2 Inconsistencies found and how each is resolved

The HubSpot plan wins for HubSpot internals, the master plan for everything else (the user's rule). Where a resolution edits a plan, the owning task makes the stated edit as its first step and notes it in the progress log.

1. **`DependencyPending` and `RegistrationStatus` are defined in the HubSpot plan's `hubspot/types.ts`; the contracts define the error hierarchy and the domain enums.** Resolution: `hubspot/types.ts` keeps `STAGE_LABELS`, `StageLabel`, `StageIds`, `HsDeal`, `HsCompany`, `DealSearchPage`, `AssociationRole`, `HubspotApi` and `HubspotError` exactly as written, and replaces the two definitions with `export { DependencyPending } from '@/server/errors';` and `export type { RegistrationStatus } from '@/lib/domain';`. `HubspotError` stays a plain `Error` subclass (the outbox treats every error as retryable). Edit by H4.2.
2. **Product and region are stored as codes (`libraries`, `middle_east`) by the master plan; the HubSpot plan's tests and mappers use display labels (`'Clean Libraries'`, `'India'`) and expects HubSpot values `clean_libraries` and `cleanstart_images`.** `slug('libraries')` would give `libraries`, not `clean_libraries`. Resolution: the database keeps codes. `dealProperties` keeps taking labels. In `handlers.ts` `registration.create`, the call becomes `dealProperties({ id: reg.id, customerName: reg.customerName, product: PRODUCT_LABEL[reg.product], region: REGION_LABEL[reg.region], protectionEnd: reg.protectionEnd }, ...)` with `REGION_LABEL = PARTNER_REGION_LABEL`. The test helper `makeRegistration` accepts either form (J.3). Edit by H4.6.
3. **The HubSpot poll inserts into `audit_log` directly (`tx.insert(auditLog).values({ actorLabel, who, kind, text, subjectType, subjectId })`), which omits the NOT NULL `event` column.** Resolution: `poll.ts` calls `recordAudit(tx, SYSTEM_ACTORS.hubspot, { event: 'registration.stage_changed' or 'registration.protection_end_changed', source: 'crm', target: <customer and product>, note: change.eventText, partnerId: reg.partnerId, subject: { type: 'registration', id: reg.id } })`. ### M.3 Decisions made by the contracts author

Each is the simplest option that fits both plans and the mock. The orchestrator can overturn any of them through a contract change.

1. IDs are uuid v4 from `gen_random_uuid()`; enums are text plus CHECK (B.2, B.5).
2. The business calendar is UTC for every date, with no holiday calendar (B.3, `businessDaysBetween`).
3. The partner `technical` role has no deal access at all (matrix), so Deals, Register and Overview are hidden from it and it lands on Documents.
4. No `AppError` alias; the hierarchy is `PortalError` (E).
5. The report column `accepted` means "ever accepted" (status accepted, won, lost or expired); `protectedNow` is status `accepted`; the acceptance rate is computed in the client as accepted over accepted plus rejected, as the mock does.
6. A partner manager may decide any registration in any region (cover for a colleague); the approvals queue opens on "mine" (the viewer's region) with "all" one click away; staff sales decide only in their region.
7. Staff marketing may upload and edit documents (the proposal's cell for marketing is blank; the mock's audit log shows marketing uploading).
8. Only partner managers may add, change or remove CleanStart teammates (the proposal lists it as open; the mock lets any admin).
9. One extension, 30 days, requested with a reason and decided by staff; granting moves `protection_end` by 30 days (`EXTENSION_DAYS`, `MAX_EXTENSIONS`, in `deal-rules.ts`, to be confirmed).
10. Reopening an approved application never deletes the partner: the partner becomes `inactive`, the invite is revoked, and a second approval reuses it. Only possible while the partner is `onboarding` with no agreement accepted.
11. `Viewer` has an extra field `partnerName` (null for staff).
12. A third transaction setting, `app.user_id`, carries the user id so `notifications` and `notification_prefs` are private to the user by RLS.
13. Two pools on one role: request scope (6) and system scope (8), the latter marked by a connection startup option; `portal_app` has `CONNECTION LIMIT` 20.
14. Rate limiting is an in-process fixed window (`src/server/rate-limit.ts`). shortcut: one container only, counters reset on restart; move to a Postgres counter table if the portal ever runs more than one instance.
15. Emails are sent best effort after commit with no email outbox. A crash between commit and send loses that email; invites and password resets have a resend path, deal emails have the in-app notification as the record.
16. `/apply/done` reads a short-lived signed HttpOnly cookie set by `submitApplicationAction`, not the database or the query string, so the receipt page cannot be used to read someone else's application.
17. The 2 business day review target counts Monday to Friday between the registration (or resubmission) date and today; the mock counted calendar days.
18. Undo of a decision is limited to the person who decided, within 10 minutes (`UNDO_WINDOW_MINUTES`), and only while no HubSpot deal exists.
19. Added tables and columns beyond the master plan: `partner_checklist`, `registration_reminders`, `document_versions`, the four `auth_*` tables, and the columns listed in inconsistency 12.
20. Child tables of `registrations` copy `partner_id` from the parent through a trigger, so every insert (including the HubSpot poll's) is correct without the caller passing it.
21. `registrations.product` and `region` are codes; display labels live in `domain.ts`.
22. Passwords are hashed with scrypt through our own `hashPassword`, and Better Auth is configured to use it.
23. Partners can read the active partner managers' user rows and their `staff_scopes`, so the Register deal form can offer the manager for each region.
24. A registration is unique per (partner, lower(customer), product) while pending or accepted: a hard block, as the master plan states, with the mock's "already protected" hint shown before submit.
25. `IntegrationHealthDto.lastPollAt` is a `Date`, the one DTO field that is not a string, because the HubSpot plan's test fixes it.
26. The dev port is a command line flag, not an environment variable (I).
27. A partner sales user's "own deals only" is enforced in the repo (a `registered_by = viewer.id` filter) and in `can`, not in RLS, because RLS here is the cross-company backstop.
28. The Ctrl K "Pages" group is static client data (`src/lib/search-pages.ts`, filtered by `navFor`); only the data groups come from `searchAll`.
29. `registration_messages` and `registrations` copy the author and registrant names at write time; a removed user's name keeps showing on their deals.
30. In-app notifications are written in the action's transaction; whether an email goes is decided after commit in system scope (F.5), because a staff viewer cannot read a partner user's preferences under RLS.
31. Stage change, changed end date and expiry notifications belong to track R: `announceRegistrationChange` (`src/server/registrations/announce.ts`, W0-c stub, body in M2.3). The HubSpot poll and the expiry job call it after commit (a failure only logs), and the email it sends is `buildDealStageChanged` (W0-g). Rejected: a `notifyStageChange(tx, ...)` inside the poll's transaction (HubSpot plan CCR 4), because it would make H depend on R's repo and send email inside a transaction.
32. The poll never moves a granted extension's end date backwards and ignores HubSpot's end date while a `registration.update_end` write is pending or failed (H4.8, tested there).
33. No QR code for two-step enrolment in v1: the setup dialog shows the key and an "Open in your authenticator app" link. Adding `qrcode` to the dependency list and rendering `totpURI` is a small follow-up if the pilot asks (plan 03 CCR 16, rejected for scope).
34. Declined access requests are not purged by the retention job in v1 (plan 06 CCR-8, rejected); `DATABASE_OWNER_URL` stays in the production container's environment so the container can migrate on start (plan 06 CCR-5b, deferred to a person; see the review report).
35. Inline video playback, a sweep of abandoned uploads, a configurable `PUBLIC_SITE_URL` and hard deletion of documents (plan 05 CCR 2 to 5) are rejected for v1: videos download, abandoned uploads stay in the private bucket, the site URL is a constant, and a deleted document is a tombstone.

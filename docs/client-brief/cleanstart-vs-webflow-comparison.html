01 · Executive summary

What changed, and why it matters

Webflow gave CleanStart a fast start: a hosted, visual site builder with a usable CMS. But a security product's marketing platform eventually hits Webflow's ceilings — a fixed performance floor, a closed extensibility model, per-seat/per-item pricing, no server-side logic, and SEO/compliance automation that has to be hand-bolted via embeds. The new platform is a code-first Next.js 16 front end backed by a self-hosted, custom Payload 3 CMS — owning the full stack from Postgres to CDN.

Faster, measurably

Mobile Lighthouse more than doubled (32 → 84) and desktop went from 61 → 98. The Webflow Website carries a desktop TBT of 3,150 ms and a mobile LCP of 42.2 s — structural costs no optimization can remove while Webflow's jQuery runtime stays.

Automated, end-to-end

Ten scheduled jobs, a three-layer JSON-LD engine, automatic image derivatives, IndexNow pings, auto 301 redirects on slug changes, nightly broken-link scans, GDPR PII purges, a self-healing search index, and a resilient lead pipeline — none of which Webflow can do natively.

Owned & cheaper to scale

No per-seat editor fees, no CMS item caps, no API quotas. Media on Cloudflare R2 with zero egress fees. Full control of security headers, CSP, caching strategy and data — and a real migration path instead of vendor lock-in.

Honesty up front. This is not a hit piece on Webflow — it's a fast, well-built platform and the right call for many sites. Where the new build has trade-offs (no drag-on-canvas WYSIWYG, ops burden of self-hosting, a single mobile LCP weak spot), this document says so plainly. Every performance number is a real PageSpeed measurement; every capability claim is tied to a source file or a cited source; anything illustrative is badged estimate.

03 · Performance architecture & rendering

Why the numbers differ — by design

The score gap is not luck; it is two different delivery architectures. Webflow renders pages from its own runtime and ships a fixed JS payload you cannot remove. The new site pre-renders HTML and revalidates it incrementally, with per-route rendering chosen deliberately.

● Webflow Website
  • Fixed client runtime. Every page loads jQuery + an underscore lib + webflow.js bundled together — render-blocking, non-removable on any plan, including Enterprise.
  • Interactions are JS. Animations/IX run on the main thread, inflating Total Blocking Time — measured at 3,150 ms desktop / 1,890 ms mobile in the fresh lab run.
  • Publish = full re-publish. No incremental regeneration, no per-route cache control, no on-demand revalidation you own.
  • Cache opacity. CDN behaviour is the platform's; you can't set route-level revalidation.
● New · Next.js 16 App Router
  • Static-first + ISR. Pages pre-render and revalidate incrementally — proven live by the response header x-nextjs-stale-time: 300 on staging.
  • Per-route rendering chosen deliberately: SSG via generateStaticParams() for blog/guide/resource/event/job detail pages; force-dynamic only where needed (/podcast, /preview/*).
  • No forced runtime. Code-split React 19; JS ships only where interactivity is used.
  • On-demand revalidation via revalidateTag()/revalidatePath() — CMS publishes purge exactly the affected pages.

08 · Extensibility & the "plugin" question

Webflow has no real plugin model — the new stack is the plugin layer

A common misconception is that Webflow has a WordPress-style plugin marketplace. It doesn't. Extensibility runs through four constrained channels, all client-side, with hard character limits and no backend runtime.

● Webflow extensibility — four channels
  • Custom-code embeds — but capped: ~10,000 chars site-level, ~5,000 page-level (the cap applies on every plan, Enterprise included).
  • Webflow Apps marketplace — vetted integrations (Finsweet, Jetboost, Memberstack, Weglot…), not server plugins.
  • Zapier / Make — the official automation path now that Webflow Logic was sunset (27 Jun 2025).
  • Third-party JS libraries for CMS filtering, search, gating — each another external dependency and subscription.
  • No backend. All custom code is client-side; there is no server runtime, no database logic, no scheduled jobs.
● New stack — full backend ownership
  • Arbitrary server logic — custom Payload collections, hooks, endpoints and access rules in TypeScript.
  • Scheduled jobs — ten cron tasks running real server-side work (see §11).
  • First-party integrations — Teams, HubSpot, GA4, GSC, Clarity, Cloudflare, Meilisearch, Cal.com, generic signed webhooks — configured in an admin dashboard, no code deploy.
  • No character limits, no client-only ceiling — the platform is the extension surface.
  • Trade-off: this power requires engineering ownership; Webflow's ceiling is also its simplicity.
09 · Cost model & vendor lock-in

Stacking fees & caps vs owned infrastructure

Webflow's real cost is a site plan + per-seat editor fees, stacked — plus paid add-ons for localization and (historically) automation. The new stack trades that for infrastructure you own.

Site plan and seats are billed separately and stack. CMS items, collections and API calls are hard-capped by tier.

New stack economics

  • No per-seat fees, no item caps, no API quotas — Payload is MIT-licensed and self-hosted.
  • Runs on a single Linode droplet (Postgres + Meilisearch + CMS via Docker), front end on Vercel.
  • R2 zero egress keeps media-heavy traffic cheap as it scales.
  • Typical ongoing cost for this class of self-host: ~$0–$50/mo infra vs $39+/seat stacking on Webflow.
  • Trade-off: you carry ops, backups, patching and uptime — covered by GitHub Actions deploys, backup-cron heartbeats and health probes.
Lock-in. Webflow code export ships static HTML/CSS/JS only — it excludes all CMS content and Collection-bound functionality (lists render empty, template pages don't generate). CMS data comes out only via the rate-limited API. Leaving Webflow is a rebuild. The new stack is plain TypeScript + Postgres + S3-compatible storage — portable by construction, which is exactly how the Webflow→Payload migration (§12) was even possible.

12 · Webflow → Payload migration

A repeatable 4-stage ETL — with URL parity

Because Webflow code-export drops CMS content, the migration pulled data through the Webflow Data API and rebuilt it in Payload — idempotently, with redirects to preserve every indexed URL.

H1 · EXPORT

Pull from Webflow API

12 collections, token-bucket throttled (50/min), checkpointed JSONL, resumable.

→
H2 · TRANSFORM

Map & convert

15 per-collection mappers; HTML body → Lexical; SEO fields rebuilt; relationships marked.

→
H3 · ASSETS

Upload to R2

Hash-dedup media to R2, folder-tagged; builds Webflow-URL → CDN-URL map.

→
H4 · IMPORT

Load via Local API

Dependency-ordered, idempotent (lookup-by-slug), rewrites IDs, logs every row.

SEO continuity built in. A URL-parity step emits redirects rows for any changed path, so indexed Webflow URLs keep resolving — no ranking loss handed to a 404. Acceptance checks verify row counts and body conversion post-import.

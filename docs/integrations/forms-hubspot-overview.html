6Forms strategy — DECIDED: Option B (Forms API)

Decision: build fresh HubSpot forms in the new website folder. The site renders its own UI (Payload-defined) and the backend relays each submission to the matching HubSpot form via the Forms Submissions API (by form GUID).
Each HubSpot form carries its own follow-up email (to the user) and notification emails (to the team) — configured natively on the form, no workflows to build. We still never embed the HubSpot <script>/iframe — submission is server-side, so the lead pipeline stays intact.

✓ Forms API + new folder forms CHOSEN

  • Build all forms fresh in the website folder; old forms untouched
  • Per-form follow-up + notification emails live on the form — marketing self-serve, no workflows
  • Still flows through /api/leads/submit → keeps R2 queue, Turnstile, consent snapshot, lead row
  • No embedded script → clean CSP & cookies
  • Backend posts to hsforms.com/submissions/v3/integration/submit/:portalId/:formGuid

✗ Contacts API + workflows

  • Viable (handler already coded) but HubSpot forms go unused
  • Confirmation/team emails require building workflows (dev-led)
  • More control over marketing status, but more dev effort
  • Not chosen — doesn't match the folder/self-serve goal

✗ HubSpot embedded forms / collected Webflow

  • Embedding injects HS script → CSP / cookie issues, bypasses LeadHandler
  • Collected Webflow forms only work via tracking-script on HTML forms
  • Next.js posts JSON — retire all collected forms when new site is live

Two places define a form, by design: Payload owns the rendered UI + validation; the matching HubSpot form (same field internal names) owns the GUID + emails. The existing HubSpot-native Book-a-demo / Contact-Us forms stay as a field-name reference; the new canonical forms live in your website folder.

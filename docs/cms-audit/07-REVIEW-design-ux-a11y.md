# CleanStart CMS Review — Design, UX Consistency & Accessibility

Visual & interaction design quality, component-state & pattern consistency, microcopy/guidance, and accessibility posture across the custom admin.

## Scorecard

| Area | Score | Takeaway |
|---|---|---|
| Visual & Interaction Design — Custom Admin SCSS System | 8/10 | A genuinely well-engineered, layered design system; held back by thin light-mode theming, dead code, and cascade pressure. |
| UX Consistency, Component States & Interaction Patterns | 7/10 | Strong shared primitives undermined by two competing toast systems and scattered bespoke/native fallbacks. |
| Microcopy, labels, help text & editor guidance/safety | 8/10 | Above-average, substantive guidance; weakened by leaked developer jargon, missing descriptions, and stale phase-tracking language. |

## Visual & Interaction Design — Custom Admin SCSS System

**Score: 8/10**

This is a genuinely well-engineered admin theme — not a skin slapped over Payload defaults but a deliberate, layered design system. The token architecture is sound: a three-tier elevation ramp, a clean primitive-to-semantic separation, a 4-pt grid, explicit radius steps, and named motion tokens. Brand application is restrained and purposeful — brand cyan appears only for action, focus, and the active-item indicator, never as decoration. Both themes are substantively addressed. The filing/module structure (40 focused partials, one concern each, loaded in correct cascade order) is exemplary for a project of this scope. Where it falls short of a 9 or 10: the light-mode theming is thin compared to dark (a 19-line safety net file versus a full dark palette), the saved-state indicator component was built and then fully hidden, creating a dead-code liability, pixel values and !important overrides accumulate in later partials suggesting the cascade is under pressure in spots, and the font-loading strategy relies on a Google Fonts @import (render-blocking in non-cached loads). The design language reads as intentional, cohesive, and brand-appropriate — it would feel at home next to Webflow, Linear, or Retool admin UIs.

**Strengths**

- Three-tier token system (primitives in _tokens, theme remapping in _themes, semantic intent in _semantics) means light/dark inversion happens automatically for virtually every component — no per-theme overrides on individual rules.
- Brand cyan (#06c7f2) is used with restraint: active nav stripe, focus rings, primary action button, selected states. It never appears decoratively, which keeps it meaningful as a signal.
- Motion is codified at three explicit levels (micro 120ms ease-out, macro 200ms cubic-bezier, modal 240ms spring), honors prefers-reduced-motion globally in _a11y.scss, and high-contrast mode also gets its own @media block there — accessibility posture is first-class, not bolted on.
- The doc-controls button hierarchy flip (Save Draft promoted to primary cyan, Publish demoted to outlined) is a genuinely correct editorial UX decision backed by a well-reasoned comment — rare to see that level of intentionality in admin CSS.
- Leave-without-saving modal button swap (Stay on page = primary, Leave = subdued) correctly applies the safety-first modal pattern; the inline rationale is clear.
- The dashboard SCSS is fully composed — timeline with hairline vertical thread, pulse KPI cards with left-accent color coding, analytics snapshot grid, quick-links, all using the token system consistently. Reads as a product screen, not a scaffolded prototype.
- Overflow safety on the dual-pane edit view (_chrome.scss) is sophisticated: the entire :has() chain correctly threads overflow: hidden and min-height: 0 down the flex tree so main and sidebar scroll independently without the page scrolling, a notoriously hard layout problem.
- Empty-state design (_empty-state.scss) is thorough: masked SVG icon injected via ::before, filtered vs unfiltered variants swap glyph to a magnifier, the CTA gets primary button treatment with white-space: normal so long collection names wrap cleanly.
- The _paper-cuts.scss chip system covers every known select-field value (lifecycle status, HTTP status codes, SEO indexable, boolean cells) with semantic color-coding — green/amber/red/cyan matched to severity, not random brand colors.
- Scrollbars use a floating-thumb style (2px border on the bg color, transparent track) that matches the Webflow designer aesthetic without browser-default intrusion.

**Findings**

### [MODERATE] Light mode is a thin safety net, not a complete theme  (visual-design · small)
**Where:** `apps/cms/src/app/(payload)/styles/_light-mode.scss` — **What:** _light-mode.scss is 19 lines covering only pills, table row hover, and tooltip shadow. The full light theme relies on the elevation ramp defined in _themes.scss, which is sound in principle, but several components use hardcoded rgba values optimized for dark (e.g. '.drawer backdrop rgba(0,0,0,0.45)', box shadows throughout _overlays.scss at '0 12px 32px -12px rgba(0,0,0,0.45)'). On a white background these dark box-shadows produce large dark halos that are far too heavy, and the blurred backdrop behind drawers reads as nearly opaque rather than a light overlay. The light theme has never been the primary development context. — **Recommendation:** Introduce a --cs-shadow-overlay-backdrop token (dark: rgba(0,0,0,0.45); light: rgba(0,0,0,0.2)) and replace hardcoded shadow rgba values in _overlays.scss and _dashboard.scss with the token. Add a dedicated light-mode audit pass targeting the drawer backdrop, confirmation modal shadow, command palette backdrop, and tooltip halos.

### [MODERATE] Google Fonts @import is render-blocking and single-point-of-failure  (performance-scale · small)
**Where:** `apps/cms/src/app/(payload)/styles/_fonts.scss` — **What:** _fonts.scss uses @import url('https://fonts.googleapis.com/...') which is synchronous and render-blocking. It also loads six font families (Plus Jakarta Sans weights 400–800, Manrope 400–700, Sora 500–700, JetBrains Mono 400–600) including font-weight 800 for Plus Jakarta Sans that the design system explicitly forbids in CLAUDE.md. If the Google CDN is slow or blocked (corporate proxies, China), the entire admin UI renders in system fonts until the import resolves. An admin tool, unlike a marketing page, is used repeatedly by the same people — a local bundle is appropriate. — **Recommendation:** Convert to next/font or self-hosted fonts using the @font-face format from the web fonts package. Drop the Plus Jakarta Sans 800 weight (forbidden in the design system). This also eliminates the privacy implication of a third-party request on every admin page load.

### [MODERATE] !important density is high in later partials, signaling cascade pressure  (visual-design · medium)
**Where:** `apps/cms/src/app/(payload)/styles/_density.scss` — **What:** _density.scss alone uses !important 7 times, _user-menu.scss uses it 10+ times on .nav__scroll, .nav__wrap, .nav__controls, and .app-header. _sidebar-header.scss uses it 8 times for the NavToggler overrides. The root cause is that Payload ships its own @layer payload-default rules and Payload's component CSS has high specificity or source-order advantage. While each !important has a rationale comment, the cumulative count (estimated 40+ across all partials) means any future Payload upgrade could silently break the admin if the underlying Payload classes change, since our cascade then has no fallback. — **Recommendation:** Audit the !important uses and where possible replace with higher-specificity selectors or @layer declarations that establish a predictable cascade position (e.g. @layer cleanstart { } above Payload's layer). This is a maintenance investment, not a visual change, but it insulates the theme from Payload minor-version upgrades.

### [MODERATE] Cyan #06c7f2 on dark background fails WCAG AA for text use in select menus  (accessibility · small)
**Where:** `apps/cms/src/app/(payload)/styles/_paper-cuts.scss` — **What:** The react-select option hover and selected states set color: var(--cs-cyan-500) (#06c7f2) on var(--theme-elevation-150) background (dark theme: approximately #2a2c33). The contrast ratio of #06c7f2 on #2a2c33 is approximately 3.8:1 — passes for large UI (3:1 threshold) but fails the 4.5:1 requirement for normal text. The same cyan-on-dark pairing appears in the audit-log .cell-action[data-action='update'] chip (cyan text on --cs-tint-brand-soft), the dashboard status pills, and anywhere var(--cs-text-accent) is used as text color on an elevated surface. On the light theme the _light-mode.scss safety net is not present for these contexts. — **Recommendation:** Replace cyan as a text color for normal-weight 13px text with a slightly darker tint: var(--cs-cyan-600) (#04a3c8) achieves ~5.2:1 on dark elevation surfaces. Keep cyan-500 for large UI elements (28px+ numbers, pill dots, icons, focus rings). The _semantics.scss --cs-text-accent token is the right place to make this change — switch it to var(--cs-cyan-600) in dark theme.

### [MINOR] SavedIndicator component fully built then entirely hidden — dead code  (value-vs-complexity · trivial)
**Where:** `apps/cms/src/app/(payload)/styles/_saved-indicator.scss` — **What:** _saved-indicator.scss is 91 lines of complete, working component CSS — pulsing dot animation, saving state, error state, prefers-reduced-motion guard — topped by a comment saying the component is unmounted and all rules are set to display:none !important. The animation keyframes (cs-saved-dot-pulse, cs-saved-dot-spin) still compile and ship. This is maintenance debt: any future change to the component UI requires working around the !important suppressors. — **Recommendation:** Either delete _saved-indicator.scss entirely and remove it from the @use manifest in custom.scss, or restore the component (it is a genuinely good affordance — 'Saved 2s ago' visible on the edit bar reduces editor anxiety). If the decision to remove was intentional, delete the file now rather than leaving suppressed code.

### [MINOR] Lexical toolbar sticky positioning conflicts with fullscreen toolbar reservation  (authoring-ux · trivial)
**Where:** `apps/cms/src/app/(payload)/styles/_lexical-toolbar.scss` — **What:** The .fixed-toolbar rule reserves padding-right: 124px to avoid the fullscreen toggle pill overlapping the rightmost toolbar button. This is a fragile magic number: if the fullscreen pill text changes length, or if Payload adds a button to that cluster, the overlap either returns or a gap of dead space appears. The 124px was derived by computing pill width (110px) + right offset (8px) + breathing room (6px) but is hardcoded without a comment. — **Recommendation:** Convert to a CSS custom property: --cs-fullscreen-toggle-width: 124px on .rich-text-lexical__wrap, then use padding-right: var(--cs-fullscreen-toggle-width) on .fixed-toolbar. When fullscreen is active, override the var to 8px in _editor-fullscreen.scss. This makes the value a single source of truth.

### [MINOR] embed dialog uses --cs-red-500 / --theme-error-500 which are not defined in the token system  (consistency-states · trivial)
**Where:** `apps/cms/src/app/(payload)/styles/_lexical-toolbar.scss` — **What:** The cs-embed-dialog and cs-embed-action-btn rules reference --cs-red-500, --theme-error-500, and color-mix(in srgb, var(--theme-error-500)...) — none of which exist in _tokens.scss or _semantics.scss. Actual error colors are --color-error-500 and --cs-status-error. These unresolved vars silently fall back to transparent or the browser default (in color-mix), making embed error states potentially invisible. — **Recommendation:** Replace all --cs-red-500 and --theme-error-500 references in _lexical-toolbar.scss with --color-error-500 (the established token from _themes.scss). The color-mix() call should become rgba(var(--color-error-500-rgb), 0.1) or a semantic token --cs-status-error-bg which already exists in _semantics.scss.

### [MINOR] Dashboard pulse cards only have two color variants (cyan / amber) — no success/error states  (content-modeling · trivial)
**Where:** `apps/cms/src/app/(payload)/styles/_dashboard.scss` — **What:** The .cs-dashboard__pulse modifier set defines only --cyan and --amber left-accent variants. If a future KPI card needs to signal a red/critical state (e.g. broken links found, lead queue stalled) there is no --red variant. Similarly there is no --green variant for a clearly-healthy metric, forcing everything positive to fall back to the neutral default. The system has the status tokens but they are not carried into this component. — **Recommendation:** Add --error (border-left-color: var(--cs-status-error)) and --success (border-left-color: var(--cs-status-success)) variants to the pulse card modifier set. Three lines each, zero design risk — they are already used in every other status-bearing component.

### [MINOR] Number input max-width: 120px is a global rule that will truncate any numeric field  (authoring-ux · small)
**Where:** `apps/cms/src/app/(payload)/styles/_density.scss` — **What:** The density partial caps all .field-type.number inputs to max-width: 120px with the comment 'Number fields with bounded ranges (level 1-6, etc.) shouldn't stretch full-width.' This is correct for a heading-level selector (1–6) but will also truncate numeric fields for things like word count targets, reading time estimates, or any integer that might reach 6+ digits (e.g. media file sizes, hit counts). There is no escape hatch in the rule. — **Recommendation:** Add a .field-type.number--full modifier or use a more specific selector (e.g. scope to fields known to be small like level/order/position) rather than all number inputs. Alternatively, add a data attribute to the field definition side and scope the CSS to that attribute.

### [MINOR] Sidebar nav min-height: 100vh forces a double scrollbar on short content  (visual-design · small)
**Where:** `apps/cms/src/app/(payload)/styles/_user-menu.scss` — **What:** aside.nav, .nav { min-height: 100vh } ensures the UserMenu always pins to the sidebar floor. However, this makes the sidebar itself as tall as the viewport, which means on short-content views (the dashboard) or narrow monitors the browser may render both a sidebar scrollbar and the main content scrollbar simultaneously. The sidebar has its own overflow scroll via .nav__scroll, so the nav rail and the page content both have their own scroll contexts. — **Recommendation:** Replace min-height: 100vh with height: 100% on the nav element and ensure the parent template wrapper provides a defined height (which _chrome.scss already does for dual-pane views via :has(.document-fields--has-sidebar)). A sticky bottom-pinned UserMenu can be achieved with the existing flex-column + margin-top: auto on .cs-user-menu without needing the nav itself to stretch to 100vh.

## UX Consistency, Component States & Interaction Patterns

**Score: 7/10**

The core design system is well-architected: a single `@cleanstart/ui` package exports six coherent primitives (Dialog, Drawer, Popover, Combobox, ConfirmDialog, Spinner, Toast) all built on native `<dialog>` for focus-trap and Esc handling, with DropdownMenu portaled to `document.body` to avoid stacking-context traps. The loading/error/empty state patterns are largely intentional — SavedStateIndicator has three distinct states, CmsListView has both "empty" and "empty-filtered" cases with copy tailored to each, and the HealthBadge and TestButton correctly distinguish idle/loading/ok/error inline. Accessibility groundwork is solid: Combobox implements full ARIA combobox pattern with `aria-activedescendant`, Spinner uses `<output aria-live>`, error toasts escalate to `role="alert" aria-live="assertive"`, and the Notice component chooses `role="alert"` vs `role="status"` by variant. The two main friction points are (1) a meaningful button-class split — the EmbedDialog uses undocumented `cs-embed-dialog__cancel / __confirm` button classes instead of the `cs-btn` system used everywhere else, and some Admin dialogs (DsarActionsPanel, DisableUserAction) fall back to `alert()` for error escalation — and (2) a genuine dual-toast-system problem where `ToastBus` (event: `cs-cms:toast` on `window`) and the `@cleanstart/ui` `ToastProvider` (event: `cs:toast` on `document`) coexist with different TTLs, different payload shapes, and different DOM homes, meaning a consumer calling `dispatchToast` vs `showToast` hits completely different stacks. These are real inconsistencies an editor-facing team will trip over when adding new flows.

**Strengths**

- Native <dialog>-based primitives give Dialog, Drawer, and CommandPalette correct top-layer rendering, focus trap, and ESC for free without a third-party modal library.
- ConfirmDialog correctly disables backdrop-click dismiss for destructive actions, enforcing deliberate intent before a destructive confirm.
- Empty-state copy is contextual throughout: CmsListView differentiates 'No blogs yet' (virginal) from 'No blogs match ...' (filtered) and offers a contextual action in each case, rather than a generic 'No results'.
- Loading states are incremental: Combobox shows an inline Spinner inside the input while results are fetching rather than replacing the whole list, and the SchedulePublishDialog keeps Upcoming Events visible while a delete is in-flight.
- CommandPalette is a standout: localStorage recent-history, per-item remove, fuzzy multi-token matching, live REST search with 220ms debounce, keyboard-only operable, and correct focus-return on close — all in a single self-contained component.
- SavedStateIndicator provides three distinct pill states (saving/saved/error) with correct ARIA roles for each, answering the editor's most common 'did it save?' question without requiring a separate toast flow.
- DropdownMenu portals to document.body to avoid stacking-context breakage from parent elements with backdrop-filter or transform.
- QuickCreateDialog's slug field auto-derives from the source field until manually edited, matching the full-form SlugField UX and providing availability checking with correct fail-open semantics.

**Findings**

### [MAJOR] Dual toast systems with incompatible APIs  (consistency-states · small)
**Where:** `apps/cms/src/payload/admin/components/ToastBus.tsx vs packages/ui/src/primitives/Toast.tsx` — **What:** Two completely separate toast stacks coexist. ToastBus listens for `cs-cms:toast` on `window` with a `{ message, type?, actionLabel?, actionId? }` shape, 2500ms default TTL, and a MAX_VISIBLE cap of 3 via FIFO eviction. Toast.tsx (ToastProvider) listens for `cs:toast` on `document` with a `{ title?, message, tone?, duration?, action? }` shape, 4000ms default TTL, no max-visible cap, and a different DOM mount point. SchedulePublishDialog and TestButton call `showToast` (ToastBus). Any future feature that mistakenly calls `dispatchToast` (ToastProvider) or vice versa silently hits the wrong stack. Two dismiss timers fight over the same visual space, and there is no deduplication across the two systems. The different event targets (window vs document) make it impossible to intercept all toasts from a single point. — **Recommendation:** Delete ToastBus entirely. Migrate all showToast call sites to the @cleanstart/ui dispatchToast / useToast API. Unify on a single event (cs:toast on document), a single TTL strategy, and a single DOM mount. The action-registry pattern in ToastBus (storing callbacks keyed by id in a module-level Map) should be absorbed into the ToastProvider's push() callback parameter, which already accepts an action object.

### [MODERATE] EmbedDialog uses bespoke button classes instead of the cs-btn system  (consistency-states · trivial)
**Where:** `apps/cms/src/payload/admin/components/Embed/EmbedDialog.tsx` — **What:** The EmbedDialog footer uses `cs-embed-dialog__cancel` and `cs-embed-dialog__confirm` as button classNames, requiring separate SCSS rules that must stay in sync with `cs-btn cs-btn--subtle` and `cs-btn cs-btn--primary` which every other dialog (ConfirmDialog, DsarActionsPanel, SchedulePublishDialog, QuickCreateDialog, ReassignContentAction) uses. If the primary button colour or padding tokens change, EmbedDialog will visually diverge. There is no `busy` prop passed to the confirm button either — it will remain interactive if the consumer's `onConfirm` is async. — **Recommendation:** Replace `cs-embed-dialog__cancel` with `cs-btn cs-btn--subtle` and `cs-embed-dialog__confirm` with `cs-btn cs-btn--primary`. Remove the redundant SCSS rules for those two button classes. No new API is needed.

### [MODERATE] alert() used for error escalation in DSAR panel and DisableUserAction  (consistency-states · trivial)
**Where:** `apps/cms/src/payload/admin/components/DsarActionsPanel.tsx, apps/cms/src/payload/admin/components/DisableUserAction.tsx` — **What:** DsarActionsPanel calls `alert('Find failed: ...')` and `alert('Delete failed: ...')` on fetch errors. DisableUserAction calls `alert('Failed to disable account: ...')` and `alert(err.message)`. These block the browser event loop, bypass the admin's theme (dark mode, brand colours), cannot be dismissed with the keyboard pattern the rest of the admin uses, and will look visually foreign to editors who have never seen a native browser alert in this context. Every other component in the codebase uses either the toast or Notice system for errors. — **Recommendation:** Replace all alert() calls with showToast({ message: ..., type: 'error' }) for transient errors, or render an inline Notice component with variant='error' inside the dialog body for errors that need to persist until the editor takes action. This brings these two components in line with every other error surface in the admin.

### [MODERATE] InlineImageInsertDialog re-implements dialog chrome instead of using Dialog primitive  (consistency-states · small)
**Where:** `apps/cms/src/payload/admin/components/InlineImage/InlineImageInsertDialog.tsx` — **What:** This dialog is built on a raw `<dialog>` element with a hand-rolled header (h2, × button), tab nav, and body, rather than the Dialog + DialogHeader + DialogBody primitives used everywhere else. The close button uses `×` (U+00D7 MULTIPLICATION SIGN) rather than the SVG X path that DialogHeader renders. The tab strip uses `<nav role='presentation'> <button role='tab'>` — nav wrapping a tablist is incorrect (should be a `<div role='tablist'>` without nav). The EmbedDialog, SchedulePublishDialog, DsarActionsPanel, and ReassignContentAction all correctly use Dialog + DialogHeader. — **Recommendation:** Refactor InlineImageInsertDialog onto Dialog + DialogHeader + DialogBody, replacing the raw <dialog> and hand-rolled header. Fix the tab nav: remove <nav>, use <div role='tablist'>, and add aria-controls on each tab pointing at the corresponding panel with role='tabpanel'. The browse tab opening a sibling MediaBrowseDialog while the parent dialog is 'open but hidden' is a pattern that should be documented or reconsidered (two simultaneous native dialogs in the top layer may conflict on some browsers).

### [MINOR] MediaBrowseDialog loading state shows plain 'Loading…' text rather than Spinner  (consistency-states · trivial)
**Where:** `apps/cms/src/payload/admin/components/MediaBrowseDialog.tsx` — **What:** When results are loading and the grid is empty, the component renders `<div className='cs-media-field__browse-empty'>Loading…</div>` — a plain text string inside a centred empty-state div. The Combobox, SchedulePublishDialog, and TestButton all render the Spinner component for loading states. The visual inconsistency is minor but breaks the loading-state grammar editors will develop across the admin. — **Recommendation:** Replace the 'Loading...' text node with <Spinner size='sm' label='Loading media' /> wrapped in the same empty-state container. Import Spinner from @cleanstart/ui.

### [MINOR] Notice component uses hardcoded hex colours instead of CSS custom properties  (visual-design · small)
**Where:** `apps/cms/src/payload/admin/components/Notice.tsx` — **What:** VARIANT_TONE is a plain object with literal hex strings: bg '#1a2a3a', ring '#3a6ea8', fg '#9bc4e8' etc. These bypass the --theme-* / --color-* custom property system that the rest of the admin uses (SeoHealthScoreField references var(--color-success-500), PublishChecklistBanner uses var(--theme-success-500), BodyAuditField uses var(--theme-elevation-100)). If Payload updates its CSS variable palette or the admin flips to a different theme, Notice will remain stuck on its hardcoded palette. The inline style={{}} approach also makes it impossible to override via CSS cascade. — **Recommendation:** Move the colour values into CSS variables via a .cs-notice--info / --success / --warn / --error variant class and corresponding SCSS rules that reference the shared --theme-* tokens. The component itself should only apply the BEM modifier class; the SCSS owns the colour.

### [MINOR] BodyAuditField and PublishChecklistBanner use inline styles and mixed token references  (visual-design · small)
**Where:** `apps/cms/src/payload/admin/components/BodyAuditField.tsx, apps/cms/src/payload/admin/components/PublishChecklistBanner.tsx` — **What:** BodyAuditField uses chipStyle as a const React.CSSProperties object with inline style={{ ...chipStyle, borderColor: '#2fae67' }} — mixing inline styles with BEM class names. PublishChecklistBanner applies style={{ borderLeftColor: summaryColor }} and style={{ color: ... }} inline. These components avoid the SCSS token system, can't be overridden via Cascade, and duplicate colour values already defined in the Notice and SeoHealthScoreField SCSS. The inconsistency becomes apparent when the audit chips sit next to the SEO health score, which correctly uses .cs-seo-health BEM classes. — **Recommendation:** Extract the audit chip styling into .cs-body-audit__chip--pass / --warn / --fail SCSS classes that reference shared tokens, removing the inline style overrides. Apply the same treatment to PublishChecklistBanner's coloured border and summary text. This is purely a maintenance/token hygiene fix — no behaviour changes.

### [MINOR] Spinner component uses <output> element semantically incorrectly  (accessibility · trivial)
**Where:** `packages/ui/src/primitives/Spinner.tsx` — **What:** The Spinner renders as `<output className='cs-spinner' aria-live='polite'>`. The HTML `<output>` element represents the result of a calculation — for example, the result of a form computation. Using it as a loading indicator is semantically incorrect. The correct element for an ARIA live region spinner is `<div role='status' aria-live='polite'>` (for polite loading messages) or a `<span>` with the same roles. ToastBus also uses <output> as its container (`<output className='cs-toast-bus' aria-live='polite'>`). The SavedStateIndicator correctly uses <output> but for actual output values (Saved X ago is the computed result of polling), which is semantically defensible. — **Recommendation:** Change Spinner from <output> to <div role='status' aria-live='polite'> or simply <span role='status'>. Change ToastBus's outer container from <output> to <div aria-live='polite' aria-label='Notifications'>. The ToastProvider in @cleanstart/ui already uses <section aria-label='Notifications'> which is correct.

### [MINOR] SchedulePublishDialog delete-in-progress uses '…' character instead of Spinner  (consistency-states · trivial)
**Where:** `apps/cms/src/payload/admin/components/SchedulePublishDialog.tsx` — **What:** When deleting a scheduled event, the delete button renders `{deletingId === row.id ? '…' : '×'}`. The rest of the admin signals in-progress operations either via a Spinner component, a busy label change on a button ('Deleting…'), or the SavedStateIndicator. A raw '…' character in a tiny table-action cell is ambiguous — it looks like part of the data rather than a loading state. The EmbedDialog and BulkActionBar buttons use label changes ('Sending…', 'Scheduling…') which is the established pattern here. — **Recommendation:** Replace the '…' with a small inline Spinner (size='sm') or change the button label to a spinner+text pattern. Also the disabled state during deletion should visually grey out the button to make it clear the row is locked — verify the cs-schedule__delete CSS handles disabled styling.

### [QUESTION] CommandPalette uses window.location.href for navigation instead of Next.js router  (value-vs-complexity · medium)
**Where:** `apps/cms/src/payload/admin/components/CommandPalette.tsx` — **What:** The activate() function does `window.location.href = action.href` — a full page reload — rather than client-side navigation. This is consistent with how other custom admin components navigate (BulkActionBar also uses window.location.href after bulk delete), so it may be intentional (the Payload admin is an MPA rather than a full SPA). However, if Payload's admin shell supports client-side routing, a hard navigation will flash and reset all scroll positions. The 220ms debounce on document search is appropriate but the search fires across 10 collections in parallel — on a large dataset this is 10 simultaneous REST calls per keystroke burst. — **Recommendation:** Confirm whether the Payload admin shell supports a stable client-side router API. If yes, replace window.location.href with that API. If no, document the intentional hard-nav in a comment so future contributors don't add router imports expecting them to work. Separately consider whether the fan-out search (10 parallel /api calls) should be replaced with a single Meilisearch call via the existing search infrastructure — it would return better-ranked results and cost one network round-trip.

## Microcopy, labels, help text & editor guidance/safety

**Score: 8/10**

The microcopy across this CMS is notably above-average for a custom Payload build. Field descriptions are substantive, not perfunctory — they explain why a field exists, what fallback chain kicks in if left empty, and what downstream consequence follows (e.g., JSON-LD, sitemap, GDPR). The banners and confirmation dialogs are written in plain language and distinguish between advisory and blocking states. The main weaknesses are tonal inconsistency (some descriptions read as developer notes leaked into editor-facing copy), a handful of missing descriptions on high-stakes fields, scattered use of raw developer jargon (schema.org @type, ISO 8601, AEO/GEO) in editor-facing text, and two places where the guidance is long enough to overwhelm rather than orient.

**Strengths**

- The PublishChecklistBanner uses a clear three-state summary (ready / warnings / blockers) with plain-language messages and collapsible detail — editors get an actionable at-a-glance signal before every publish without being overwhelmed.
- The LeadsImmutableBanner explains the why (GDPR audit trail) behind the read-only lock, and the separate LeadsCsvTruncationBanner gracefully handles the silent-truncation edge case with a specific row cap and actionable guidance.
- The DisplayPublishedAtField component has excellent contextual messaging: five distinct states (near-now, backdate-soft, backdate-hard, future-draft, future-published) each get a chip label plus a targeted warning paragraph, and the future-draft path even offers a direct 'Schedule publish…' action inline.
- The Integrations collection shows a strong two-audience approach: non-technical editors see plain-English group descriptions ('Ask your IT admin for each person's User ID', 'The connection credentials are already set up by the technical team') while the underlying secrets machinery is completely hidden.

## Accessibility posture of the CleanStart CMS admin

**Score: 6/10**

The CleanStart admin has a thoughtful accessibility foundation that is well above what most custom CMSes ship at this stage: native `<dialog>` for all modal surfaces gives focus-trap and ESC for free, the skip-link is wired and styled correctly, all interactive components have global focus-visible outlines in brand cyan, reduced-motion and prefers-contrast media queries exist and are non-trivial, and every custom widget (Combobox, DropdownMenu, TabsField, Tooltip) implements the correct ARIA pattern with keyboard navigation. However, several practical gaps keep this from a production-grade score. The calendar day-grid in DateTimePicker has no arrow-key navigation — it is 80 cells of individually tabbable buttons, which is inaccessible for keyboard users. The CommandPalette input is missing `aria-label`, the listbox it drives has no `role="listbox"` or live-region announcement, and the keyboard cursor ("activeIndex") is pure CSS rather than routed to `aria-activedescendant`. The media picker tile grid has no keyboard operability at all. The `×` dismiss character in Toast, DateTimePicker clear, and SchedulePublishDialog delete cells is a raw Unicode multiply sign with a visible-label only — screen-reader users hear "times" not "dismiss notification". The ContextMenu has no keyboard trigger pathway; it only opens on right-click, making it unreachable for keyboard-only users who never trigger a contextmenu event.

**Strengths**

- All modal surfaces (Dialog, Drawer, CommandPalette) use the native <dialog> element with showModal(), gaining browser-native focus trap, top-layer rendering, and ESC handling without any bespoke trap logic — the most important a11y choice in the codebase.
- Global :focus-visible ring is consistent at 2px cyan across every interactive element, with a dedicated prefers-contrast: more block that bumps it to 3px and removes the opacity dimming on labels.
- Reduced-motion query applies universally (0.001ms duration to every animation and transition), correctly covering both CSS animations and transitions.
- TabsField implements the full W3C tabs pattern: role=tablist, role=tab, aria-selected, aria-controls, roving tabIndex, and ArrowLeft/Right/Home/End keyboard navigation.
- Combobox correctly sets role=combobox on the input, role=listbox on the container, aria-activedescendant, aria-expanded=true, and aria-autocomplete=list — the ARIA combobox pattern is followed.
- DropdownMenu and ContextMenu both auto-focus the first enabled item via requestAnimationFrame on open and implement ArrowUp/Down/Home/End navigation across role=menuitem buttons.
- ToastProvider correctly uses role=alert plus aria-live=assertive for error toasts and role=status plus aria-live=polite for informational ones — the right urgency mapping.
- SkipLink is implemented via a MutationObserver that re-tags main on every route change, making it work in the SPA without relying on a static DOM structure.
- ConfirmDialog disables backdrop-dismiss (dismissOnBackdrop=false) by design so editors cannot accidentally discard a destructive confirmation by clicking outside — this is the correct UX pattern for irreversible actions.
- CheckboxField and RadioField both use real visually-hidden native inputs (not div role=checkbox), so browser-native checked state, focus, and form submission work correctly.

**Findings**

### [MAJOR] DateTimePicker calendar grid: no arrow-key navigation, 80+ tabbable cells  (accessibility · medium)
**Where:** `packages/ui/src/primitives/DateTimePicker.tsx` — **What:** The calendar renders 42 day-buttons (6 rows × 7 columns) each as an independent focusable `<button>`. A keyboard user must Tab through every cell to reach a date. The W3C date-picker pattern requires a roving tabIndex so only one cell is in the tab sequence at a time, with ArrowLeft/Right/Up/Down moving between days. No arrow-key handler exists in the component. Additionally, each day button uses `aria-pressed={selected}` which is the wrong role — it should be `aria-selected` inside a `role=grid` / `role=row` / `role=gridcell` structure, or at minimum the grid container needs a keyboard handler. — **Recommendation:** Implement a roving-tabIndex calendar: add `role=grid` to the grid container, `role=row` to each week div, `role=gridcell` to each day button; set `tabIndex={0}` only on the currently active day and `-1` on all others; add ArrowUp/Down/Left/Right/Home/End/PageUp/PageDown handlers on the grid. Replace `aria-pressed` with `aria-selected`. This is a contained, well-defined widget — follow the ARIA Authoring Practices Guide §Date Picker Dialog pattern exactly.

### [MAJOR] CommandPalette input has no aria-label; active item is CSS-only, not announced  (accessibility · small)
**Where:** `apps/cms/src/payload/admin/components/CommandPalette.tsx` — **What:** The `<input type=search>` in the palette has no `aria-label` attribute (it relies on placeholder only, which screen readers do not reliably announce as the label). More critically, keyboard navigation updates `activeIndex` state that adds a CSS class `--active`, but there is no `aria-activedescendant` on the input pointing to the active row's id, and no `role=listbox` on the results container. A screen-reader user using arrow keys gets no announcement of which item is highlighted. The results groups use `<div class='cs-cmdk__group-label'>` as section labels with no `aria-label` or `role=group` to associate them with the rows below. — **Recommendation:** Add `aria-label='Command palette'` to the input. Add `role='combobox'` and `aria-expanded={true}` with `aria-controls` pointing to the list div. Add `role='listbox'` to the list container. ### [MAJOR] ContextMenu has no keyboard trigger pathway  (accessibility · medium)
**Where:** `packages/ui/src/primitives/ContextMenu.tsx` — **What:** ContextMenu only opens on the native `contextmenu` event (right-click or long-press). Keyboard-only users on Windows can trigger the context-menu key or Shift+F10 to fire a contextmenu event, but this is not universal across platforms and browser implementations differ. The component is used for Lexical table cells and list-view rows, meaning cell-level actions (insert row, merge, delete) are completely inaccessible without a mouse. — **Recommendation:** For each surface that uses ContextMenu, provide a companion trigger button (kebab / '⋮' icon) that opens the same menu items on Enter/Space, with `aria-haspopup='menu'` and `aria-expanded`. The ContextMenu component itself can remain for mouse users; the companion button is the accessible entry point. ### [MODERATE] Toast, DateTimePicker clear, and schedule delete buttons use raw × character without screen-reader labels  (accessibility · trivial)
**Where:** `packages/ui/src/primitives/Toast.tsx` — **What:** Three separate places use the raw Unicode × character (`×`) as button content with only CSS for visual meaning: the Toast close button (`<button …>×</button>`), the DateTimePicker clear button, and the SchedulePublishDialog's 'delete scheduled event' button. ### [MODERATE] Popover has no initial focus management — keyboard user is stranded  (accessibility · small)
**Where:** `packages/ui/src/primitives/Popover.tsx` — **What:** The Popover component records the last-focused element on open and restores focus on close (restoreFocus=true by default), but it never moves focus INTO the popover when it opens. This means after a keyboard user presses Enter/Space on a trigger button, focus remains on the trigger while the popover is visually open. The user then has to Tab forward to land inside the popover. For `role='menu'` popovers (the `role` prop accepts 'menu'), this violates the ARIA menu pattern which requires focus to move to the first item on open. For `role='dialog'` popovers, focus should move to the first focusable element inside. — **Recommendation:** Add a `useEffect` in Popover that, on `open` becoming true, finds the first focusable child (via `floatingRef.current?.querySelector('[tabindex]:not([tabindex="-1"]), button, input, …')`) and focuses it via `requestAnimationFrame`. For `role='menu'` surfaces the consuming component (e.g., RelationshipField inline dropdown) should focus the first result row. Document the contract: callers that manage their own focus (like Combobox which uses `autoFocus`) can opt out.

### [MODERATE] TableGridPicker is mouse-only with 80 individually labelled but unkeyboard-navigable cells  (accessibility · small)

### [MODERATE] cs-skip-link uses transition: top which is suppressed by reduced-motion — skip link becomes inaccessible  (accessibility · trivial)
**Where:** `apps/cms/src/app/(payload)/styles/_a11y.scss` — **What:** The skip link hides at `top: -100px` and reveals itself on `:focus` by setting `top: 0`. The transition (`transition: top var(--cs-motion-micro)`) is used to animate it into view. The reduced-motion block in the same file sets `transition-duration: 0.001ms !important` globally — meaning under `prefers-reduced-motion: reduce`, the skip link transition fires at nearly zero duration, which is correct (it still works). However, the skip link also uses `outline: none` on `:focus-visible`, removing the global focus ring. The element is a link, not an input, so suppressing its outline means keyboard users who are supposed to be using this affordance receive no visual confirmation that it has focus — the link appears but has no ring. The brand cyan background provides some contrast, but the ring suppression contradicts the purpose of the element. — **Recommendation:** Remove the `outline: none` override on `.cs-skip-link:focus` and `.cs-skip-link:focus-visible`. The background colour already differentiates the visible state; the focus ring is an additional keyboard-navigation signal, not a redundant one. The skip link should follow the same 2px cyan ring as every other focused element.

### [MODERATE] Radio field focus ring missing: native radio visually hidden but focus-visible not forwarded to pill  (accessibility · trivial)
**Where:** `packages/ui/src/primitives/Combobox.tsx` — **What:** RadioField visually hides the native `<input type=radio>` via `.cs-radio-field__native` (position: absolute; 1px×1px; clipped). The styled pill receives no focus indicator — there is no CSS equivalent of `.cs-radio-field__native:focus-visible + ... .cs-radio-field__pill` to apply an outline to the pill container. In _ui-primitives.scss, only `.cs-checkbox-field__input:focus-visible + .cs-checkbox-field__visual` has such a rule; the radio pill has no equivalent. Keyboard users tabbing through radio options see no visible focus ring. The same pattern exists in SchedulePublishDialog's inline `radioPill` helper which reuses these classes. — **Recommendation:** Add `.cs-radio-field__native:focus-visible ~ span, .cs-radio-field__native:focus-visible + span` — or restructure the selector to target the pill label — to apply the same `outline: 2px solid var(--cs-cyan-500); outline-offset: 2px` ring that checkbox uses. Test in Chrome, Firefox, and Safari since the DOM structure (input preceding sibling spans within a label) affects which CSS selector works reliably.

### [MINOR] ConfirmDialog does not move focus to the cancel button on open  (accessibility · trivial)
**Where:** `packages/ui/src/primitives/ConfirmDialog.tsx` — **What:** ConfirmDialog tracks a `cancelRef` on the Cancel button but never calls `cancelRef.current?.focus()` on open. The native `<dialog>.showModal()` moves focus to the first focusable child by default, which for the dialog structure (header close button → Cancel → Confirm) means focus lands on the header's close button, not on Cancel. For a destructive confirm (tone='danger'), the conventional and safer default is to focus Cancel — the non-destructive choice — so that an accidental Enter does not delete the record. This is explicitly recommended in the ARIA dialog pattern and by major component libraries (Radix, Headless UI). — **Recommendation:** In Dialog.tsx (or ConfirmDialog.tsx), add a prop `initialFocusRef?: RefObject<HTMLElement>` that, when provided, calls `.focus()` on that ref after `showModal()` inside a `requestAnimationFrame`. In ConfirmDialog, pass `initialFocusRef={cancelRef}` for `tone='danger'` so focus starts on Cancel. For neutral tone, first-focusable-element (the confirm button) is acceptable.

### [MINOR] Combobox listbox and input share the same aria-label value — redundant label for the listbox  (accessibility · trivial)
**Where:** `packages/ui/src/primitives/Combobox.tsx` — **What:** Both the `<input role='combobox'>` and the `<div role='listbox'>` receive the same `aria-label={ariaLabel}` value. The ARIA combobox pattern says the listbox is associated with the input via `aria-controls`, so labelling both with identical text is redundant and creates a confusing announcement when screen-reader users navigate into the listbox directly: they hear 'Search documents listbox' when they already heard 'Search documents combobox' on the input. The listbox should either have no label (the input's label covers the relationship via aria-controls) or a more descriptive label like 'Results'. — **Recommendation:** Remove `aria-label` from the listbox div, or change it to a static descriptive label like `aria-label='Results'`. The association is already declared via `aria-controls={listboxId}` on the input.

### [MINOR] useAnchoredPosition fires a rAF loop indefinitely while open — impacts reduced-motion users  (performance-scale · small)
**Where:** `packages/ui/src/hooks/useAnchoredPosition.ts` — **What:** The hook runs `window.requestAnimationFrame(tick)` in a continuous loop for the entire duration any anchored element (Popover, DropdownMenu, Tooltip) is open, recalculating position on every frame. On a page with multiple open popovers this fires multiple rAF loops simultaneously. While not an a11y issue per se, it produces continuous layout measurements that can interfere with screen-reader virtual-cursor navigation (layout shifts during read) and burns CPU that affects reduced-motion users who may have performance-sensitive configurations. The hook was intentionally designed this way to handle anchor scrolling, but the scroll-event listener alone would suffice for most cases. — **Recommendation:** Replace the unconditional rAF loop with: a one-time position calculation on open, plus `scroll` and `resize` event listeners (with `{ passive: true }`). Only re-run the rAF loop if the scroll handler detects actual position drift. This is the pattern used by Floating UI / Popper.js. The current approach can cause visible jitter on scroll when the floating element re-positions every frame slightly behind the anchor.

### [MINOR] QuickCreateDialog required-field asterisk uses aria-hidden but blocking reason is only surfaced on submit-button title tooltip  (accessibility · trivial)
**Where:** `packages/ui/src/primitives/QuickCreateDialog.tsx` — **What:** Required field asterisks are marked `aria-hidden` (correct — asterisk meaning is conveyed separately). The `blockingReason` hint paragraph renders with `aria-live='polite'` (good). However, the Submit and Save Draft buttons use `title={blockingReason}` to surface why they are disabled, relying on the browser tooltip shown on hover. `title` attributes are not announced by screen readers in all assistive technology configurations and are not accessible to keyboard users who hover cannot trigger title tooltips. A disabled button with only a `title` explanation is a known a11y failure pattern. — **Recommendation:** Replace `title={blockingReason}` on the disabled submit buttons with `aria-describedby` pointing to the `cs-quick-create__hint` paragraph's id, so screen readers associate the blocking reason with the button directly when it receives focus. The hint paragraph already renders and has `aria-live='polite'`; wiring `aria-describedby` makes it work for both live announcement (on change) and focus context (when tabbing to the button).

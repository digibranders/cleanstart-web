02 · The central correction

HTML latency did not worsen three months straight

This is the report's load-bearing claim, stated twice: "the only number moving in the wrong direction three months running" and "the one metric that's worsened three months straight". It comes from calendar-month buckets. June contains 18 days before the migration and 12 days after, so the fast pre-migration days drag June's average down and manufacture a rising line.

Measured only on post-migration days, the shape reverses. July was a 46% improvement on June, and August, while a regression, still sits below June.

The true shape is a step change at migration, a partial recovery in July, and a partial regression in August. Current steady state is roughly 1,000ms, about four times the pre-migration baseline. That is worth fixing. It is not a metric in freefall.

03 · Claim by claim

The seven priority actions

1. Confirm the rendering modeMarked CriticalRefuted
As reported

"If the raw HTML is a near-empty shell and content only appears after rendering, Cleanstart is on client-side rendering with no pre-render step, the single biggest indexing risk a JS migration can introduce."

Verified false
DecisionClose it. No work required.

The site is server-rendered and prerendered. Content is present in the raw document with JavaScript disabled, and the H1 is in the source. This claim has now been raised three times from the SEO side. It was true once, caused by a root loading.tsx that streamed content into a trailing hidden container, and it was fixed on Aug 14 in commit 96137029.

/knowledge-hub/spdx-sbom x-nextjs-prerender: 1 22,764 chars with JS off /blogs x-nextjs-prerender: 1 10,446 chars with JS off /pricing x-nextjs-prerender: 1 3,709 chars with JS off hidden containers: 0 (one empty Suspense marker, carries no content)

2. Diagnose the Aug 17 to 18 latency spikeMarked CriticalConfirmed
As reported

"Pull server or function logs for the two days that produced 9.2s and 16.4s response times. This points at the origin render path, likely missing HTML caching, serverless cold starts, or an uncached data fetch on every request."

Confirmed, and already root-caused
DecisionCorrect instinct. The cause is documented in our own commit from that day.

Both spikes are real and the origin-path hypothesis is right. The specific mechanism was diagnosed on Aug 18: the CMS droplet saturates under the build's prerender burst, Cloudflare returns its own 52x origin errors, and the retry-with-backoff that absorbs them lengthens responses. Not cold starts, and not a missing cache.

commit 14a17c94, 2026-08-18 "the origin droplet saturates under the build's prerender burst" CMS fetch failed: 520 (unknown origin error) CMS fetch failed: 522 (connection timed out) x2 CMS fetch failed: 525 (SSL handshake failed) "it runs on ~2 GB while a build fans out across 531 pages"

3. Check indexing coverage before vs after Jun 19Marked HighWorth doing
As reported

"Compare indexed page count and the not-indexed buckets across the migration. A rising not-indexed count is the classic symptom of Google giving up on slow or JS-dependent pages."

Sound, with one caveat
DecisionDo it, but expect the not-indexed count to be large and mostly correct.

Reasonable diagnostic. Note that the site has 539 canonical indexable URLs against a discovered surface of roughly 1,300 to 1,400, and nearly all of that gap is intentional: trailing-slash twins that 308, around 200 redirects, 55 closed job pages that are deliberately noindex, and parameter variants that canonicalise correctly. A high not-indexed count is the expected shape here, not evidence of the failure mode described.

4. Verify migration URL hygiene and the sitemapMarked HighConfirmed
As reported

"Confirm 301 redirects exist for every URL that changed shape, check for a 404 rise since Jun 19, and confirm the XML sitemap was regenerated for the new framework and resubmitted."

Confirmed, and better aimed than they knew
DecisionAlready found and fixed, one day before this report.

The sitemap half is a genuine hit. The route carried no revalidate, so it was prerendered once per deploy and served unchanged in between: anything published between deploys never reached it. Found Aug 25, fixed in a2ed91fb, awaiting deploy. Redirect hygiene is sound, and unknown slugs now return a true 404 on all eight detail routes.

live sitemap: 537 URLs, newest lastmod 2026-08-24T13:55 (predates last deploy) CMS at the time: both missing docs returned correctly, 200 / index,follow after the fix: 539 URLs, both present, lastmod current

5. Confirm structured data survived the rebuildMarked MediumRefuted
As reported

"JSON crawl volume is still near zero (34 requests in August). If the old framework carried JSON-LD schema markup, verify it's actually rendering in the new templates."

Category error, and the premise is false
DecisionClose it. The inference does not hold, and the schema is present.

JSON-LD is inlined in the HTML document as <script type="application/ld+json">. It is never fetched as a separate file, so it can never appear in the JSON row of a crawl-stats report. The "JSON" file type counts .json requests such as manifests, which has no bearing on schema markup. Independently of the reasoning, the markup is live.

/knowledge-hub/spdx-sbom ld+json blocks: 2 graph 1: Organization, WebSite graph 2: BreadcrumbList, Article

6. Audit JS bundle crawl efficiencyMarked MediumRefuted
As reported

"Confirm hashed bundle filenames carry long-lived cache headers, and block publicly-exposed source maps in robots.txt, they add crawl volume with zero SEO value."

Both halves already satisfied
DecisionClose it. Nothing to change.

Source maps are not publicly exposed, so there is nothing to block, and chunks carry no sourceMappingURL pointing at one. Hashed bundles already send exactly the immutable header the report asks us to confirm.

/_next/static/chunks/17sc9pe9-mrrk.js 200 /_next/static/chunks/17sc9pe9-mrrk.js.map 403 sourceMappingURL references in chunk: 0 cache-control: public,max-age=31536000,immutable

7. Put HTML response time on a weekly watchMarked MediumAdopt, amended
As reported

"Track it weekly against a sustained-1,000ms alert threshold, and pull Core Web Vitals field data pre- and post-migration."

Adopt, but measure the median
DecisionTake it, with one amendment to the metric.

Good recommendation. Amend it to track the median rather than the mean. August's mean of 2,242ms is produced by two days; the median is 1,138ms, and excluding the three worst days the mean is 1,197ms. A mean-based threshold will fire on single-day origin events and stay quiet during genuine sustained drift.

04 · Figures restated

Two headline numbers that need qualifying

"HTML response time up 1,112% vs pre-migration"Corrected
As reported

185ms before the switch, 2,242ms in August. Baseline labelled "Pre-migration (May)".

Directionally right, materially overstated

The workbook begins on May 28, so the "May" column is a four-day, 97-request sample. The real pre-migration window runs to Jun 18 and covers 22 days and 764 requests, at a 240ms median. Comparing medians across the two full windows gives +375%. Still serious. Not 1,112%.

report baseline "May" n=4d req=97 mean=185ms true pre-migration window n=22d req=764 mean=255ms median=240ms August n=24d mean=2,242ms median=1,138ms

"8,462-request burst, almost certainly source maps"Corrected
As reported

"Almost certainly source maps, manifests or hashed chunk files the old site never had. A one-time discovery event, not a problem on its own."

Right that it was transient, wrong about what it was

Source maps are not served, so they cannot account for it. The signature matches Next.js ?_rsc= prefetch payloads, which are served as text/x-component and land in the "other file type" bucket. That was identified and blocked in robots.txt on Jul 9 in commit 3874b4b4, and the monthly figures track the fix precisely.

other file type Jun 9,014 -> Jul 481 -> Aug 212 burst detail Jun 19: 1,295 Jun 20: 7,167 avg 5,738 bytes/request robots.txt Disallow: /*_rsc= (live)

05 · Not in the report

What the data shows that the report did not look for

Every extreme spike falls on a deploy dayNew finding
Not examined

The report treats the spikes as an unexplained origin fault and recommends pulling logs.

Suggestive, stated with its limits

All four post-migration days above 2,500ms are days work landed on main, and the worst day on which nothing deployed reached only 2,125ms. Typical latency is unaffected: deploy-day and quiet-day medians are within 30ms of each other, so this explains the spikes, not the elevated baseline.

Being straight about the strength of this: with four spikes across 40 deploy and 25 quiet days, the chance of that split arising at random is 0.135. That is suggestive, not statistically significant on its own. It is convincing here only because commit 14a17c94 independently documents the same mechanism on the same dates.

deploy days n=40 median=1,075ms max=16,447ms quiet days n=25 median=1,105ms max= 2,125ms days >2500ms 2026-06-22, 2026-08-10, 2026-08-17, 2026-08-18 (all deploy days)

The CMS origin is uncached and undersizedAct on this
Not examined

The report does not look past the edge to the origin the pages are built from.

The most likely lever on the elevated baseline

The CMS collection API sends no Cache-Control header, so Cloudflare marks every response DYNAMIC and nothing is cached at the edge. Every page render, including all 531 during a build, reaches the droplet. That droplet has under 2 GB of RAM and runs the CMS, Postgres and Meilisearch together, which is precisely the saturation the Aug 18 commit describes.

cms.cleanstart.com/api/blogs cache-control: (none) cf-cache-status: DYNAMIC origin latency ~330ms warm, ~1,000ms cold droplet 1,967 MB total cms 321 MB · postgres 123 MB · meilisearch 145 MB

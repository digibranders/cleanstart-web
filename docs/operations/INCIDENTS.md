# Incident & Bug Log

A running, reverse-chronological log of production incidents and non-obvious bugs — what broke, the **root cause**, the fix, and the **reusable lesson**. The goal: next time (in this repo or another), we recognise the pattern fast instead of re-deriving it.

**When to add an entry:** any prod incident, any bug whose root cause was non-obvious, any "this looked like a one-liner but wasn't." Skip trivial typo fixes.

**Format:** newest first. Keep each entry tight. Mark **Status** honestly (`Fixed & verified`, `Fixed, verification pending`, `Mitigated`, `Open`). Call out the **Reusable lesson** — the part that generalises beyond this codebase.

> This log complements Claude Code's per-session auto-memory (`~/.claude/projects/<proj>/memory/`). The memory is auto-loaded each session for *this* repo; this file is committed so it travels with the code and is visible to every developer and every project checkout.

## 2026-07-21 — Lexical link editor: "Add link / Update does nothing" — three stacked root causes

- **Area:** `apps/cms` — CMS rich-text link popover (`LinkPopoverPlugin.tsx`, `_editor.scss`).
- **Symptom (reported on prod):** attaching an internal/external link to selected text does nothing — the popover sometimes shows **Update** instead of **Add link**, clicking it closes the popover, and the selection is never linked. This is the 2026-07-18 entry's "symptom 2", finally reproduced and root-caused (three distinct bugs stacked):
- **Root cause 1 — selection overlapping an existing link hijacked the save (reproduced live):** `openForCurrentSelection` set `editLinkKeyRef` whenever the selection merely *touched* any link, and `handleSave` checks that ref FIRST — so selecting a phrase that contains an already-linked word (routine in Webflow-migrated, link-dense bodies) silently `setFields`-updated the *inner* link and returned, never wrapping the selection. **Fix:** new `$findSingleEnclosingLink` — edit mode only when the entire selection sits inside ONE link; anything else is create, and `$toggleLink` correctly absorbs inner links into the new wrap. Popover mode/prefill is now derived from that same test, so the button label finally matches what the save will do.
- **Root cause 2 — click-to-edit was dead: Payload's stock editor CSS ships `.LexicalEditorTheme__link { pointer-events: none }`** so every click on a link landed on the parent `<p>`; our root click handler (`closest('a')`) never matched, and the popover never opened from a link click. Additionally the handler was bound via a one-shot `editor.getRootElement()` read that is `null` when the plugin's effects run (ContentEditable attaches later) — the listener never existed at all. **Fix:** `pointer-events: auto` override in `_editor.scss` + `editor.registerRootListener` (capture phase) + `preventDefault`/`stopImmediatePropagation` for plain left-clicks — required because restoring pointer-events awakens Lexical's stock `ClickableLinkPlugin` (registered by Payload with `newTab: true`), whose `window.open` ignores `preventDefault`. Cmd/ctrl-click still passes through to it deliberately (open-in-new-tab).
- **Root cause 3 — the 2026-07-17 anti-wipe re-assert could not survive the wipe it guarded against (reproduced live on a cold dev server, whose multi-second `getFormState` RTT mimics prod):** instrumentation showed the link IS created (`links in committed state = 2`) and then vanishes — a stale link-less `getFormState` lands *after* the fixed 1.5 s window, Payload's `Field.js` re-keys (re-mounts) the editor subtree, and the re-mount destroys the plugin instance **and the React ref holding the pending re-assert value**. **Fix:** pending commits moved to a module-scope map (survives re-mounts), keyed by `collection:id:fieldPath` (path alone repeats across documents), re-asserted until the server echo deep-equals the committed value (content-acknowledged, not time-boxed; 15 s TTL as a safety net), refreshed by any newer editor change, and a mount effect in the resurrected plugin instance pushes the pending value back into both the form value and the freshly mounted editor (`setEditorState`).
- **Verified live (local instrumented editor, port 3000):** create on plain text ✓ · create over a selection overlapping an existing link wraps the whole phrase as ONE link ✓ · click-a-link → popover opens in Update mode, no navigation ✓ · Update rewrites the URL ✓ · Remove unwraps ✓ · created link survives 8 s of stale `getFormState` churn ✓ · Save Draft → `_blogs_v` row carries the link ✓ · reload renders it ✓.
- **Diagnosis notes:** local CMS with `PAYLOAD_DB_PUSH=false` (push-mode was hanging ~4 min/request on an interactive drizzle rename-column prompt with no TTY — check this FIRST if every admin render mysteriously blocks with idle CPU); CSRF blocks admin mutations from non-allowlisted ports (run on 3000, not an ad-hoc port — a 403 "not allowed" with an admin role is the origin allowlist, not RBAC).
- **Status:** **Fixed & verified end-to-end locally.** On `development` at time of writing; retest the full matrix on prod after deploy.
- **Reusable lessons:** *(1)* an "edit the link under the caret" affordance must key off *the selection being entirely inside one link* — "selection touches a link" misfires on every overlapping selection; *(2)* any guard value that protects against a React re-mount must live OUTSIDE the re-mounted subtree — a ref inside it is destroyed by the very event it guards; *(3)* re-assert loops should be content-acknowledged (server echo deep-equals the asserted value), never purely time-boxed — latency will always outrun a fixed window.

## 2026-07-18 — Lexical link editor: clicking the internal-path suggestion makes the whole popover vanish

- **Area:** `apps/cms` — CMS rich-text link popover (`LinkPopoverPlugin.tsx` + `LinkInternalSearch.tsx`).
- **Symptom (reported on prod):** In the link popover, the editor pastes a URL / types a path, the "PATH /…" suggestion dropdown appears, and **clicking that suggestion dismisses the entire popover** (no link added). Reported alongside "pressing Add link directly shows submitting then the link isn't attached."
- **Root cause (confirmed by live instrumentation, not reasoning):** the popover's outside-click guard (`handleDocClick`, a `document` `mousedown` listener) dismisses the popover when the click target is neither inside `popoverRef` nor the editor root. Selecting a dropdown result calls `commit()` → `setOpen(false)`, which **synchronously unmounts that result** (React flushes the discrete `mousedown` update at the root delegated listener, which sits *below* `document` in the tree). By the time the `document`-level handler runs during the same bubble, `event.target` is **detached** (`target.isConnected === false`), so `popoverRef.current.contains(target)` is false and the guard treats an *inside* click as an *outside* click → `setState(null)` → popover gone. Instrumented log at the moment of failure: `DOCmousedown target=cs-link-popover__result connected=false inPopover(now)=false` immediately followed by `POPOVER -unmount`.
- **Fix:** in `handleDocClick`, `if (!target.isConnected) return;` before the `contains()` checks. A detached target was inside our tree when the click landed, so it is never a legitimate outside click. **Verified live** on a throwaway blog: click suggestion → popover stays open + path commits + Add link enabled → Add link → link node wraps the text (`link count 1→2`), popover closes cleanly.
- **On the second symptom ("direct Add link → submitting → not attached"):** could **not** be reproduced locally — the internal-path create+save path works end-to-end and the link persists (stable, no wipe). Its most likely prod cause is the documented `getFormState`-latency wipe from the 2026-07-17 entry below (the 1.5s re-assert window is fragile under prod round-trip latency), but it did not reproduce even with an injected 20s `getFormState` delay because a later with-link `getFormState` landed last and won. Left untouched rather than shipping a blind change (see 2026-07-16 lesson). Retest after this deploy; if it persists, the instrumentation harness (below) reproduces it.
- **Diagnosis harness (reusable):** local CMS on a spare port with `PAYLOAD_DB_PUSH=false`, authenticate via `fetch('/api/users/login')`, instrument the live editor via `root.__lexicalEditor`, a `MutationObserver` for popover mount/unmount, a `document` `mousedown` probe logging `target.isConnected`, and a `window.fetch` wrapper that tags + optionally delays Payload server actions (`getFormState`) to simulate prod latency. Coordinate mapping: computer-tool screenshot px ≈ `getBoundingClientRect` px × `1327 / window.innerWidth`.
- **Status:** **Symptom 1 fixed & verified live.** Symptom 2 unreproduced; monitoring.
- **Reusable lesson:** *(React outside-click pattern)* a `document`-level `mousedown`/`click` dismiss guard must treat a **detached** `event.target` (`!target.isConnected`) as *inside* — a click on any menu/dropdown item that unmounts itself synchronously will otherwise be misread as an outside click and close the parent. `contains()` alone is not enough.

## 2026-07-17 — Lexical link editor: links create but don't save (+ a runaway draft poll)

- **Area:** `apps/cms` — CMS rich-text editor (`LinkPopoverPlugin.tsx`), Payload `@payloadcms/richtext-lexical`; and `SavedStateIndicator.tsx`.
- **Symptom:** After the 2026-07-16 create fix, editors reported that adding a link (internal *or* external) still "showed nothing / didn't save" — the link would appear briefly then vanish, and reload showed no link.
- **This corrects the 2026-07-16 entry below**, which was marked *"Fixed & verified end-to-end."* That was premature: only the *create/render* path was fixed. Two further, distinct root causes remained. Both are now fixed and verified end-to-end on a fresh throwaway blog (create → Save Draft → reload → the link node wraps the text; DB draft-version row carries the link).
- **Root cause A — create was still flaky (selection restore not committed before dispatch):** the create path restores the selection captured on popover-open (`$setSelection`) in one `editor.update`, then dispatches `TOGGLE_LINK_COMMAND` in a separate call. Lexical did **not** always commit the selection update before the dispatch ran, so `$toggleLink` read the stale (collapsed, editor-blurred) live selection, extracted nothing, and created no link. **Fix:** pass `{ discrete: true }` to the selection-restore `editor.update(...)` so it flushes synchronously before the dispatch. Verified: `after restore, selText="…"` + post-dispatch link-count increments.
- **Root cause B — the link never reached the form value, and a stale `getFormState` wiped it:** our popover mutates the editor while focus lives in the popover (editor blurred). Payload's richtext `OnChangePlugin` gates out blurred-editor updates (`if (!tags.has("focus") || tags.size > 1)`), so the mutation never flows to the form `value` on its own. Worse, opening the popover blurs the editor, which fires a `getFormState` built from the **pre-link** body; that response lands *after* the link is created and overwrites the field value back to the server's link-less state, and `Field.js`'s `handleInitialValueChange` re-mounts the editor to that reverted value — wiping the link. **Fix (two parts):** (1) a one-shot `editor.registerUpdateListener` that reads the *post-commit* state (reading synchronously right after dispatch captures the pre-mutation tree — Lexical reconciles a tick later) and pushes it into the form value via `useField().setValue`, marking the field modified; (2) a bounded re-assert — stash the committed value and re-write it on every `initialValue` change for ~1.5 s (an `initialValue` reference change *is* the signal a `getFormState` landed), so a late stale response can't win. With this, `value` reliably carries the link, Save persists it, and reload renders it.
- **Root cause C (separate perf bug, found while debugging B) — runaway draft poll:** `SavedStateIndicator` polled `GET /api/<coll>/<id>?depth=0&draft=true` at ~7/s instead of every 30 s. `matchEditPath()` returns a **fresh object** each call and a 500 ms `detect` interval called `setEditPath(newObject)` unconditionally, so `editPath`'s *reference* changed every 500 ms → the fetch effect (`[editPath]`) re-ran and re-fired the fetch on every tick. **Fix:** only `setEditPath` when the collection/id actually change (compare values, keep the reference stable). Idle rate dropped from ~7/s to the intended 1 per 30 s. This wasn't the cause of B, but it was hammering the server on every open editor tab.
- **Known residual (cosmetic, data-safe):** between *Add link* and *Save*, the editor can transiently repaint blank (the re-mount fires before the value re-assert fully settles). The form value is correct throughout, Save persists the link, and reload renders it. An earlier attempt to also repaint the editor via `editor.setEditorState(...)` was removed — it was timing-inconsistent and faithfully restored a *malformed* committed state when a create misfired, i.e. more risk than the cosmetic flicker it fixed.
- **How it was diagnosed:** local instrumented editor (`root.__lexicalEditor`), console logging in the plugin, temporary logging in `node_modules` `Field.js` (needs a dev-server restart — Turbopack caches `node_modules` and won't HMR it), DB-truth checks against the **`_blogs_v` versions table** (drafts save there, **not** `blogs.body` — an early wrong "it didn't persist" read came from querying the published row), and network capture that surfaced the runaway poll. **Don't debug editor/form-state races blind — instrument and read the DB versions table.**
- **Status:** **Fixed & verified end-to-end** on a fresh throwaway blog (create + internal/external, Save, reload; DB draft version carries the link). On `development`, not yet deployed at time of writing.

## 2026-07-16 — Lexical link editor: new links silently do nothing

- **Area:** `apps/cms` — CMS rich-text editor (`LinkPopoverPlugin.tsx`), Payload `@payloadcms/richtext-lexical`.
- **Symptom:** In the blog/body editor, selecting text and adding a link (internal *or* external) via the popover did nothing — no link appeared, nothing "updated." Reported by editor.
- **Root cause:** The custom link popover steals DOM focus, so at **Add link** time the editor's live selection is no longer the picked text. The create path needs to restore the selection captured when the popover opened, then dispatch `TOGGLE_LINK_COMMAND`. The real defect was in *how* that restore was done: an intermediate fix called `selection.extract()` **in the same `editor.update` before dispatch**. `extract()` splits text nodes at the selection boundary and leaves the restored selection pointing at now-stale nodes, so Payload's `$toggleLink` — which runs its **own** `selection.extract()` — found nothing and wrapped no text. Net: no link created.
- **How it was actually diagnosed (the important part):** black-box reasoning was wrong **twice** (two bad deploys). What worked: stand up a **local** CMS I fully controlled (`PAYLOAD_DB_PUSH=false` to skip the schema-drift push prompt; seed a throwaway admin + blog), then **instrument the live Lexical editor from the page** (`root.__lexicalEditor`, wrap `editor.dispatchCommand`, read `editor.getEditorState()`). That revealed: (a) the stock `$toggleLink` *does* create links with a live range selection — proving it wasn't a selection-loss/early-return problem; (b) a same-tick `toJSON()` read after dispatch shows 0 links purely because Lexical commits async (timing artifact that caused a false "it no-ops" conclusion); (c) a `savedLinkCount:0` after Save that was actually an **autosave race** from doing two rapid edits in a test, not a persistence bug — a single clean link edit persists end-to-end.
- **Fix:** Snapshot the `RangeSelection` on popover open (`createSelectionRef = selection.clone()`), and on the create path restore it with `$setSelection(savedSelection.clone())` in one `editor.update`, then dispatch `TOGGLE_LINK_COMMAND` with `selectedNodes: []`. Let `$toggleLink` do its own `extract()` on the intact restored selection. **Do NOT pre-`extract()`** — that was the bug.
- **Commits:** `82a3a942` + `5950d508` were the two wrong attempts; **`b833d591` is the correct fix** (restore-only). All on `main` + `development`, deployed.
- **Status:** **Create/render path fixed** by `b833d591`. The "verified end-to-end" claim here was premature — persistence (Save + reload) and a still-flaky create were only actually fixed on **2026-07-17** (see the entry above). Treat this entry as the create-selection story only.
- **Reusable lessons:**
  1. *(Payload/Lexical)* A custom link/format popover that takes focus must restore the selection captured on open, then dispatch `TOGGLE_LINK_COMMAND` and let `$toggleLink` extract — **never** pre-mutate the tree with `extract()`/`splitText` before the command runs.
  2. *(debugging)* Don't fix editor bugs blind. Reading `editor.getEditorState().toJSON()` in the **same tick** as a dispatch reads pre-commit state — poll across ticks. And reproduce in an environment you can instrument (`root.__lexicalEditor`) rather than deploying on reasoning.
  3. *(local CMS)* `PAYLOAD_DB_PUSH=false` runs the dev server against the existing local DB without the interactive drizzle rename/create prompt that otherwise wedges boot.

## 2026-07-16 — Departmental users saw cross-domain nav, globals, and Dashboard content

- **Area:** `apps/cms` — new `hr` / `events` least-privilege roles (RBAC + admin nav scoping).
- **Symptom (staged, three sub-bugs):** (a) scoped users could be blocked from writing but still saw every collection in the nav; then after collection-nav hiding, (b) they still saw all **globals** (SEO defaults, Site settings, etc.); and (c) the custom Dashboard still showed cross-domain "Recent edits" and "New blog post" quick actions that 404'd on their access.
- **Root cause:** (a/b) `admin.hidden` scoping was applied to collections but not globals. (c) The custom Dashboard (`Dashboard.tsx`) queries content via the **local API with `overrideAccess`**, so it ignores the logged-in user's access and pulls everything.
- **Fix:** Centralised nav scoping in `apps/cms/src/payload/lib/wire-scoped-nav.ts` (`isScopedOnlyUser`, `wireScopedNav` for collections, `wireScopedNavGlobal` for globals), `.map()`ed over both arrays in `payload.config.ts`. Made the Dashboard role-aware via `scopedCollectionSlugsForUser(user)` — restricts counts, recent-edits, and quick-links to the user's own collections and drops leads/redirects cards. The Payload `/admin` root can't be removed from nav (login lands there), so scope its *content* instead.
- **Commits:** `853715ff` (globals hiding) + `30e21c94` (scoped Dashboard) — earlier collection RBAC + roles enum in `68e87a5d`/prior. Deployed.
- **Status:** Fixed & verified (nav confirmed scoped in-browser).
- **Open caveat:** content collections read via `publishedOrAuthenticated` = any logged-in user can still **read** other domains' drafts by direct API. Isolation covers write + nav + Dashboard, not draft read.
- **Reusable lesson:** In Payload, `admin.hidden` is a **nav-only** concern and must be applied to *both* `collections` and `globals`. Any custom Dashboard/home widget that uses `overrideAccess` will leak cross-tenant data unless you scope its queries yourself — hiding nav is not enough.

## 2026-07-16 — CI coverage gate (not lint/test) blocked the roles PR

- **Area:** `apps/cms` CI.
- **Symptom:** Local `pnpm --filter @cleanstart/cms test` passed (1746 tests) but CI failed: `Coverage for functions (87.5%) does not meet "src/payload/access/**/*.ts" threshold (95%)`.
- **Root cause:** New access helpers (`isAdminEditorOrHr`/`isAdminEditorOrEvents`) were untested. The 95% function-coverage gate on `access/**` is enforced only by CI's `test:coverage`, **not** by plain `test`.
- **Fix:** Added unit tests for the new helpers; re-ran `test:coverage` locally before pushing.
- **Reusable lesson:** For `apps/cms`, run `pnpm --filter @cleanstart/cms test:coverage` (not just `test`) when touching `src/payload/access/**` — plain `test` won't catch the coverage-gate failure.

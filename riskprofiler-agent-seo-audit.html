Executive Summary

RiskProfiler.io is built on a strong SEO foundation. Every working page has Open Graph metadata, Twitter Card metadata, canonical URLs, and rich JSON-LD structured data — including the @graph pattern with Organization, SoftwareApplication, and FAQPage entities on product pages, plus BlogPosting on articles. The site uses Framer with Cloudflare in front, with a valid robots.txt and a 145-URL sitemap. Cloudflare proxying provides automatic Markdown content negotiation for AI agents at no extra cost.

However, the audit surfaced two critical issues that are causing measurable SEO damage right now:

🚨

Issue #1 — 17 URLs in the sitemap return a soft-404 page. URLs like /cyber-threat-intelligence, /ai-agents, /comparison/bitsight-alternatives, and /blog/github-breach-ciso-playbook return HTTP 200 — but the HTML body is byte-for-byte identical (87,834 bytes) to a generic Framer fallback page. The titles, descriptions, and content of all 17 pages say "External Threats, Managed by AI Agents" — the homepage copy. Google sees 17 promised pages that duplicate the homepage; this is the classic soft-404 anti-pattern that Google explicitly penalizes.

🚨

Issue #2 — Every working blog post has broken BlogPosting schema. The schema contains unreplaced Liquid-style template variables: "{{author_name}}", "{{author_url}}", "{{author_image}}", "{{primary_topic}}", "{{mentioned_brand_1}}", and more. Google's Rich Results Test will fail validation; blog articles cannot earn Article rich snippets in SERPs. Additionally, BlogPosting.@id is incorrectly set to the Organization's @id URI, and mainEntityOfPage.@id is a bare slug instead of a full URL — both violate Schema.org specs.

The AI Agent Readiness score of 57/100 (Level 1) can be raised to Level 2 by addressing three agent-discoverability checks: Link headers, Content Signals in robots.txt, and DNS-AID. All three can be implemented through Cloudflare without any changes to Framer.

Audit scope

  • Direct HTTPS GET of 35 URLs with desktop Chrome User-Agent
  • Programmatic parsing of <meta>, <link>, and <script type="application/ld+json"> elements
  • JSON-LD validation to detect @type, @id integrity and unreplaced template variables
  • Byte-length analysis to detect Framer's soft-404 fallback fingerprint
  • Cloudflare isitagentready.com scanner output (content profile)
  • Coverage: homepage, 6 product pages, blog index, 5 blog posts, trust center, about, careers, team, partners, contact, book-a-demo, privacy, terms, 10 competitor comparison pages, 7 solutions sub-pages, robots.txt, sitemap.xml

🚨 P0 Critical — 17 Sitemap URLs Return Soft-404

❌ Critical SEO penalty risk  Effort: 2–4 hrs (audit + remediate)  Tool: Framer admin + sitemap regeneration
🚨

The problem: Of the 145 URLs in sitemap.xml, 17 return HTTP 200 but serve byte-for-byte identical fallback HTML (87,834 bytes) with the homepage's title, meta description, and content. The pages don't actually exist as published Framer routes — Framer's SPA fallback returns the homepage instead of a proper 404. Google calls this a soft-404 and explicitly states it harms site quality scores.

Blog posts (at least 2 confirmed — full audit needed across 120 posts)

/blog/github-breach-ciso-playbook /blog/anti-ransomware-day

Why this is critical, not cosmetic

  1. Direct ranking penalty. Google's documentation explicitly states soft-404s "negatively affect a site's reputation in Search". Pages returning HTTP 200 for non-existent content are treated as a quality signal.
  2. Crawl budget waste. Googlebot wastes crawl budget on 17 URLs that look identical, deferring crawls of pages that actually changed.
  3. Duplicate content signals. 17 URLs serving the homepage HTML appear to Google as 17 duplicates of the homepage. Risk of de-indexing.
  4. Lost competitor-comparison traffic. "Bitsight alternatives", "Recorded Future alternatives", "SecurityScorecard alternatives" are extremely high-intent commercial queries. The pages are advertised in your sitemap but don't exist — every click from a competitor query lands on a homepage that doesn't address what the visitor searched for.
  5. Lost product-page conversions. /cyber-threat-intelligence is a named main-nav product page. Anyone clicking the CTI nav link or finding it via "cyber threat intelligence platform" Google query lands on a homepage with no product-specific content.

How to fix — step by step

Inventory: which broken URLs were intentional vs. unintentional?

Open the Framer admin. For each URL in the list above, check: does the page exist as a Framer page (published, not draft)?

  • If the page should exist but doesn't — create it in Framer and publish. (Examples: /cyber-threat-intelligence and /ai-agents are clearly meant to exist — they're main-nav items and have JSON-LD content suggesting they were planned.)
  • If the page was intentionally removed or never built — remove it from sitemap.xml (see step 3) and set up proper 404 handling (see step 4).
Rebuild missing high-priority pages first

These three should be top priority because they are explicit product/nav destinations:

  • /cyber-threat-intelligence — main product page (has rich CTI content referenced in nav)
  • /ai-agents — the KnyX agent suite landing
  • /comparison/bitsight-alternatives — Bitsight is the largest competitor; this is highest-intent commercial keyword

Comparison pages can use a template — duplicate the working /comparison/cloudsek-alternatives page in Framer as a starting point.

Regenerate the sitemap to exclude any URL you decide not to rebuild

If sitemap.xml is auto-generated by Framer from published pages, simply un-publishing a page should remove it from the sitemap automatically. Verify after the next publish that no broken URL remains in sitemap.xml.

If the sitemap is hand-maintained or generated by an external script, edit it directly and remove the broken entries.

Configure proper 404 handling in Framer

Framer supports a custom 404 page. Make sure one is configured and that requests for non-existent URLs return HTTP 404 instead of 200 with homepage content. In Framer: Site Settings → Pages → 404 Page.

If Framer cannot return a 404 status code for non-existent routes (limitation of static-site builds), use a Cloudflare Worker as a fallback — see step 5.

Cloudflare Worker safety net for proper 404 responses

If you can't fix the status code at the Framer layer, use Cloudflare to detect the soft-404 fingerprint and override the status code:

cf-soft-404-fix.js
export default {
  async fetch(request) {
    const response = await fetch(request);
    const contentLength = response.headers.get('content-length');

    // Detect Framer's soft-404 fingerprint (~87,834 bytes)
    if (response.status === 200 && contentLength === '87834') {
      const body = await response.text();
      // Optionally serve a real 404 page from a CDN URL or inline HTML
      return new Response(body, {
        status: 404,
        statusText: 'Not Found',
        headers: response.headers
      });
    }
    return response;
  }
};

Wire this Worker to riskprofiler.io/* as a route. It only triggers on the specific 87,834-byte fallback; all real pages pass through unchanged.

Submit updated sitemap to Google Search Console + request re-crawl

Once the broken URLs are either fixed or removed:

  • Go to Google Search Console → Sitemaps → submit sitemap.xml again (forces re-processing).
  • For each URL you rebuilt: URL Inspection → Request Indexing.
  • For each URL you removed: Removals → New Request → Temporarily remove URL (until Google's natural deindexing catches up).
  • Monitor Coverage Report over 2–4 weeks — "Submitted URL not found (404)" errors should clear and "Soft 404" should drop to zero.
⚠️

Action required for blog posts: 2 broken blog URLs were confirmed in a sample of 5. The blog has 120 articles. Before submitting an updated sitemap, audit ALL 120 to find every broken post. Script: for url in $(curl -s sitemap.xml | grep -oE 'https://[^<]+blog/[^<]+'); do echo "$url $(curl -s -o /dev/null -w '%{size_download}' $url)"; done — any line where the second column is exactly 87834 is broken.

P2 — Fix: Content Signals in robots.txt

❌ Currently failing  Effort: 30 min  Tool: Cloudflare Worker

The IETF Content Signals draft lets you declare what AI systems may do with your content. Framer owns /robots.txt output and you can't edit it directly. A Cloudflare Worker intercepts the route and appends directives.

Steps

Cloudflare → Workers & Pages → Create Worker

Name: riskprofiler-robots

Replace default code with this
robots-worker.js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    if (url.pathname !== '/robots.txt') return fetch(request);

    const original = await fetch(request);
    const base = (await original.text()).trimEnd();

    const appended = base + `

# ── Explicit AI crawler rules ──
User-agent: GPTBot
Allow: /

User-agent: ChatGPT-User
Allow: /

User-agent: ClaudeBot
Allow: /

User-agent: anthropic-ai
Allow: /

User-agent: PerplexityBot
Allow: /

User-agent: Googlebot-Extended
Allow: /

User-agent: Applebot-Extended
Allow: /

User-agent: CCBot
Allow: /

# ── Content Signals (https://contentsignals.org) ──
# ai-train=no   : Do not use our content to train AI models
# search=yes    : AI search engines may surface our content
# ai-input=yes  : Agents may use our content as RAG context
Content-Signal: ai-train=no, search=yes, ai-input=yes
`;

    return new Response(appended, {
      headers: {
        'Content-Type': 'text/plain; charset=utf-8',
        'Cache-Control': 'public, max-age=3600'
      }
    });
  }
};
Save & deploy. Wire route

Worker → Triggers → Routes → Add Route: riskprofiler.io/robots.txt*

Verify

Visit riskprofiler.io/robots.txt. The original 3 Framer lines should still be there, followed by the AI bot rules and Content-Signal line.

⚠️

Choose Content-Signal values deliberately: For a security intelligence company, the recommended setting is ai-train=no (don't let competitors train on proprietary framing), search=yes (be visible in Perplexity / ChatGPT Search), ai-input=yes (be a citable RAG source). For a stricter policy — e.g. ai-input=no — change before deploying. This is a policy decision, not a technical one.

P3 — Enhancement: Explicit AI Bot Rules

⚠️ Passes but weak — wildcard only  Effort: 0 min (included in Fix above)

Currently robots.txt has a wildcard User-agent: * rule that applies to all crawlers. The scanner passed this check, but explicit AI bot user-agents are best practice — they show enterprise security maturity and allow allowing/disallowing specific bots independently in the future. The Worker in Section 09 already adds these — no extra work.

CleanStart.com — CMS architecture for the Next.js rebuild

Audit findings from the live Webflow workspace, the proposed Next.js + Payload content model with first-class SEO, and the locked-in single-droplet hosting plan at $12/month.

📅 April 30, 2026 · Greenfield · Next.js 16.2 · Payload 3 · ~$35/mo at launch

00Executive summary

CleanStart.com is a marketing-led B2B SaaS site for container security, currently on Webflow with 13 CMS collections, ~293 CMS items, and ~75 static pages (verified live 2026-05-04). The team is rebuilding it on Next.js with a self-hosted Payload CMS. This document is the architecture deliverable: the Webflow audit, the new content model (with explicit new SEO fields and pain-point fixes), the recommended stack, and the locked hosting plan.

Decision in one paragraph

Build the new site as a Next.js 16.2 + Payload 3 monorepo with two apps — apps/web (public marketing site) and apps/cms (Payload admin + REST API). Public site renders on Vercel Pro ($20/mo per dev — Vercel Hobby's ToS prohibits commercial use, including "advertising the sale of a product or service"; see §Hosting); everything else (Postgres 16, Payload admin, Meilisearch) runs on a single $12/mo DigitalOcean droplet via Coolify for git-push deploys, with a 2 GB swap file + explicit tuning spec (Postgres / Sharp / Meilisearch / kernel) so the 2 GB / 1 vCPU box doesn't OOM under upload bursts. Media and DB backups go to Cloudflare R2; failed lead writes also fall back to R2 with a 5-min drain cron so no lead is lost during a CMS outage. Email through Brevo free tier. Analytics start with Vercel Analytics free; Plausible Cloud added later when traffic justifies it. Mirror the 13 Webflow collections 1:1 in Payload (no merges — URL parity is preserved exactly), add 5 system collections (pages, forms, leads, media, redirects) for the page builder, lead capture, and URL rules, replace Webflow's flattened Q1/Ans1…Q5/Ans5 patterns with proper array fields, and add a comprehensive SEO field group (with auto-emitted JSON-LD per collection) plus a CRM-agnostic LeadHandler adapter.

Decisions locked Self-hosted Payload · DO $12 droplet (Bangalore) with 2 GB swap + tuning spec · Vercel Pro for the public site (ToS-compliant for commercial) · Postgres on the droplet · Meilisearch on the droplet · R2 for media + backups + lead-fallback queue · Brevo for email · Vercel Analytics free (defer Plausible) · Sentry free · BetterStack Uptime free · English only at launch · No ecommerce

Structural pain points (what the rebuild fixes)

Pain · Flattened repeating fields Webflow has no array-of-objects field, so the team manually repeats Q1/Ans1…Q5/Ans5, Article keyword 1…10, Article About 1…8, Article Mentions 1…10. Result: 48-field Guides collection with a real semantic count of ~12. Fix: proper Payload array fields for FAQs, sections, and citations; keywords becomes a per-document string[] array.
Pain · No SEO field group Only loose metaTitle + metaDescription. No OG image, no Twitter card, no canonical, no structured-data hooks, no per-page robots control. Fix: reusable seo group with full Open Graph, Twitter, JSON-LD, and indexing controls (see §SEO field group).
Pain · "Hustle 1–10 / Gallery 1–10" naming hack to fake drafts About Galleries has 20 items split by ad-hoc naming — verified live 2026-05-04: 9 of 10 Hustle items are Published (Hustle 5 is Draft, exception that proves the rule), all 10 Gallery items are Drafts. Hustle items were created March 2026; Gallery items October–November 2025. The naming pattern is a workaround because Webflow's draft workflow couldn't be relied on. Fix: kept as a real aboutGalleries collection in Payload with native _status: draft / published + drag-to-reorder. Editor workflow stays familiar; the naming hack goes away.
Pain · No real draft / preview workflow Editors use "duplicate to draft," which creates -copy sibling slugs that leak to prod (/about-copy, /pricing-copy in the live sitemap). Fix: Payload's drafts + versions + scheduled publish; token-gated shareable preview URLs for stakeholder review.
Pain · Resources are ungated Every PDF is a public direct URL — zero lead capture. Fix: per-resource gated toggle and gateForm relation so marketing can choose per asset.
Pain · Jobs are mixed CMS / ATS without a discriminator Some entries have jobDetails rich text; others use customLink as an ATS deep-link. Inconsistent rendering and tracking. Fix: explicit source: 'cms' | 'ats' discriminator with conditional fields.
Pain · Webflow Ecommerce was abandoned mid-activation Clicking the Ecommerce sidebar surfaces a blocking modal: "You are currently using Collection names and/or page slugs that Ecommerce requires. Please rename Categories." Activation was started, blocked, never resolved. Zero products. Fix: drop the Ecom module entirely from the new build.
Pain · Webflow staging subdomain is publicly indexable (duplicate-content risk) Verified live 2026-05-04: Webflow Settings → SEO has "Webflow subdomain indexing" toggled ON for the auto-generated triam-01-f9d7f3fff3153287c2b45cf073e213.webflow.io URL. Google has both URLs (production cleanstart.com + staging .webflow.io) competing on the same content — a duplicate-content signal that suppresses ranking on the canonical domain. Fix: add a T-24h cutover step (§Migration plan) to disable Webflow subdomain indexing; after cutover the subdomain becomes irrelevant. The new CMS architecture inherits no equivalent risk because Vercel preview deployments emit X-Robots-Tag: noindex on every preview URL by default.
Pain · 19 production forms with three groups of true duplicates + several campaign-orphaned forms Verified live 2026-05-04: Webflow Settings → Forms lists 19 forms in production. Three groups are true duplicates — same purpose, same fields, no functional differentiation, just historical naming drift:
  • 4 generic email/contact forms doing the same thing: Business Email, Email, Email Form, Send Message — all generic "send us a message" forms with identical field schemas
  • 2 Eventus partner-event forms: Eventus Form and New Year Event Eventus — both registration forms for events with the same partner brand
  • 2 Sysdig partner-event forms: Sysdig Form and New Year Event Sysdig — same as Eventus, but for the Sysdig partnership
The remaining 11 forms have distinct purposes and stay separate (Contact Form is the named "Contact us" page form; Sign Up is newsletter; Careers vs Job Application target different intents; the four CleanStart Survey variants have city/partner separation; Partners and Deal Registration are sales-pipeline forms; Resources Form will become live when gating ships). Fix: consolidate the 3 true-duplicate groups → 14 active Payload forms with a documented mapping (§Form migration inventory) that preserves sourceFormName on every imported lead so historical campaign attribution survives the merge.

03New CMS design

Collection mapping: Webflow → Payload (1:1)

Every Webflow collection maps to a same-named Payload collection — no merges, no discriminators, no source-field consolidation. This preserves URL parity exactly (/blogs/* stays /blogs/*, /webinar/* stays /webinar/*, /news-categories/* stays /news-categories/*) and avoids the conditional rendering / routing logic a discriminator-based model would require. Collections gain new fields (proper arrays, SEO group, computed values) — they don't merge with siblings.

Five additional system collections that don't exist in Webflow today:

  • pages — block-based page builder for static-but-editable pages (Pricing, About, Solutions, Audience, Company, Partners, Contact)
  • forms — admin-defined form schemas with field validation
  • leads — form submissions captured here before optionally syncing to a CRM
  • users — CMS login accounts (optionally linked to authors for "my drafts" filtering)
  • redirects — single source of truth for URL-rule redirects (vanity, retired pages, and slug-change auto-creates from a beforeChange hook on every publishable collection)
Why no merges Webflow today: 13 distinct collections, each driving its own URL prefix. Mirroring that 1:1 keeps the migration deterministic (every Webflow row maps to exactly one Payload document of the same kind), keeps URLs identical without rewrite rules, and lets editors continue thinking in the same content types they already use. Collections with overlapping shapes (categories ↔ newsCategories, events ↔ webinars) share field-group definitions in code, but remain separate collections in the admin and on the URL.
Code names vs. URLs — independent

Payload collection code names are normalised to a consistent convention (camelCase plural): blogs, news, guides, resources, events, webinars, jobs, authors, categories, newsCategories, jobLocations, aboutGalleries. The code name is what appears in the Payload admin sidebar, the REST endpoint (/api/webinars, /api/aboutGalleries, …), and the generated TypeScript types. It is a developer-side cosmetic.

Public URLs are frozen at Webflow's exact spelling — including its inconsistencies. The new site ships /blogs/* (plural), /guide/* (singular), /event/* (singular), /webinar/* (singular), /job/* (singular), /author/* (singular), /category/* (singular), /news/*, /resources/*, /news-categories/* — verbatim as Webflow currently exposes them. Next.js route files live at app/(website)/blogs/[slug], app/(website)/guide/[slug], etc., named to match Webflow exactly.

Collection code name and route segment are independent. Renaming webinars → liveEvents in code (admin label, REST endpoint, TS type) is allowed and has zero public-URL effect — the route file at app/(website)/webinar/[slug] keeps serving /webinar/*, just querying a differently-named collection internally.

Asset filenames, folders & URLs (images + PDFs + other files)

Every uploaded file — image or PDF or any other binary — is a media document; raw URLs never live in content fields. Each document carries a folder that drives both the R2 key prefix and the public URL, so assets are physically organised per source collection — cdn.cleanstart.com/web/blog/<file>.jpg, cdn.cleanstart.com/web/job/<file>.pdf, cdn.cleanstart.com/web/resource/<file>.pdf, etc. — without editors having to think about paths. The folder is derived from what the editor is editing, not from the file's mime type, so a PDF dropped on a job posting and an image dropped on the same job posting both end up in web/job/.

R2 bucket layout — co-existing with existing assets The R2 bucket is shared with other CleanStart assets (not exclusive to the website), so every website upload is namespaced under the top-level web/ prefix. Per-collection folders nest under it: web/blog/, web/news/, web/guide/, web/resource/, web/event/, web/webinar/, web/job/, web/author/, web/about/, web/page/, web/general/. The cloudStorage plugin is configured with prefix: 'web' and a per-document folder suffix from media.folder — the website never writes outside web/* and never reads other tenants' assets.
Accepted file types
  • Images: image/jpeg, image/png, image/webp, image/avif, image/svg+xml (sanitised), image/gif. Only image types get the thumbnail / card / hero / og derivatives.
  • Documents: application/pdf. Stored as-is, no derivatives, served with Content-Disposition: inline by default and Content-Type: application/pdf so the browser preview works.
  • Other: video/mp4 (case-study videos, kept rare), application/zip (rare). Editors can extend the allowlist via media collection config; uploads outside the allowlist are rejected by Payload before they reach R2.

Upload pipeline
  1. Editor drops a file into the Payload admin (or any → media relation field on blogs, news, guides, resources, events, webinars, authors, aboutGalleries, jobs, pages).
  2. A beforeChange hook auto-sets the folder field from the upload context — when the upload originates inside a blogs document edit, folder = 'web/blog'; when it originates inside guides, folder = 'web/guide'; etc. Standalone uploads default to web/general. Editors can override the folder via a dropdown on the media document.
  3. The same hook slugifies the filename and appends a content-hash suffix: lowercase, ASCII, hyphens for spaces, extension preserved, then -{contentHash8} suffix from SHA-256 of the file bytes (my-photo-a1b2c3d4.jpg). Replaces always get a new URL automatically — no manual CDN purge ever needed.
  4. Originals auto-resized to ≤ 2400 w via Sharp before R2 write — the original is the resized version, not the editor's 6000-wide phone shot. Saves R2 storage and clamps the worst-case download size; the card / hero derivatives are still generated below.
  5. Payload's @payloadcms/storage-s3 plugin streams the file to Cloudflare R2 using the R2 key {folder}/{filename} (e.g. web/blog/my-photo-a1b2c3d4.jpg). Same bucket already locked in for media + backups in §Hosting.
  6. Payload's image-resize plugin generates three derivatives at upload time — thumb (400 w, used by listing pages where 800 w wastes bytes and hurts LCP), card (800 w, used inside content), and hero (1600 w, used as feature/lead image). Each derivative is written into the same folder next to the original (web/blog/my-photo-a1b2c3d4-hero.jpg). The og derivative (1200×630) is generated lazily, only when a document promotes this asset to seo.ogImage or when the auto-OG fallback fires — keeps R2 storage and Sharp processing proportional to actual usage. Crop uses focalPoint for non-1:1 source aspects so the subject survives the OG crop.
  7. Filename-derived alt-text starter. For image uploads, the upload hook pre-fills the alt field with a humanized version of the slugified filename (sbom-101-diagram.jpg → "Sbom 101 diagram") — eliminates the blank-field problem with zero external API calls. The editor must still review and rewrite before publish (the alt-text gate still applies). Per W3C WAI-ALT-Decision-Tree, alt should describe the image's function in context, which a filename can't infer — only the editor knows the context. Editors who upload purely decorative images use the decorative toggle (skips the gate, renders alt="").
  8. The media document persists everything: folder, filename (with hash), url, sizes[].url (thumb / card / hero), dimensions, alt, caption, focal point, content hash.

Per-collection cache tags for ISR invalidation

ISR revalidation needs to know which routes to refresh after a content change. The launch design uses Next.js 16's native fetch-tag invalidation — the lowest-complexity option — rather than a separate graph table. Every fetch() in apps/web tags its data: 

// apps/web — typed fetch wrapper
fetch(`${CMS}/api/blogs/${id}`, {
  next: { tags: [`blogs:${id}`, 'blogs:list'] },
});

// apps/cms — afterChange hook on every publishable collection
const tags = [`${collection}:${doc.id}`, `${collection}:list`];
await fetch(`${WEB_URL}/api/revalidate`, {
  method: 'POST',
  headers: { 'X-Revalidate-Secret': process.env.REVALIDATE_SECRET },
  body: JSON.stringify({ tags }),
});

// apps/web — /api/revalidate handler
for (const tag of tags) revalidateTag(tag);

Cross-document invalidation (a media change → revalidate every blog that uses it) uses the broader blogs:list tag — slightly wider invalidation than a precise reverse-lookup graph would give, with negligible cost at ~290 documents. Slug changes revalidate {collection}:list across every collection that might link to the changed doc; this works because internal links are stored as {kind: 'doc', id} not URLs (so the link always resolves correctly post-rename — no stale URLs in content).

  • Internal-link integrity — Payload's native relationship integrity (onDelete: 'restrict') blocks deletion of a doc while inbound relations exist; for Lexical LinkNode references, an afterChange hook updates a single column media.referencedFromCount (a counter, not a graph) so editors can see whether an asset is in use before deleting.
  • "Find unreferenced media" — quarterly SQL query (SELECT * FROM media WHERE referenced_from_count = 0 AND created_at < now() - interval '30 days') surfaced as an admin view; no transactional graph needed.
  • Image sitemap (/sitemap-images.xml) — generated from the same query at build time.
Public URLs — invariants
  • R2 bucket is fronted by a Cloudflare custom subdomain — cdn.cleanstart.com. Cloudflare CDN handles caching; no Vercel egress.
  • Zero hot-linked URLs in content. Content fields and rich-text UploadNodes store media document IDs only. The frontend resolves the ID to the right URL (and the right derivative) at render time.
  • Lexical rich text embeds images as Lexical UploadNode with the media ID — the renderer resolves to <CmsImage> with the appropriate variant for the slot (e.g., card inside a 2-column grid, hero for a full-bleed lead image).
Frontend rendering (apps/web)
  • Single shared <CmsImage media={…} variant="card" /> wrapper around next/image — picks media.sizes[variant], falls back to original, applies media.alt, honors media.focalPoint via CSS object-position.
  • next/image handles AVIF / WebP negotiation, responsive srcset, lazy loading, and the LCP priority hint for hero images.
  • Cloudflare CDN is the canonical loader; we set images.remotePatterns in next.config.ts to allow cdn.cleanstart.com only.
Off-CMS / external image URLs

By design, every → media relation requires an asset that lives in our R2 bucket — no string-URL field on those slots. If a piece of content needs an image hosted elsewhere (a press logo, an embedded chart), the editor uploads a copy to media first. This keeps the asset library complete, dependable, and portable. The one exception is news.externalUrl (the press-pickup link), which is the article URL, not an image URL.

Canonical URL — default, override, validation, audit

Canonical URLs are the single highest-leverage SEO signal an editor can accidentally break. The design defaults to safe (self-referential, system-managed) and gates the override behind a deliberate toggle with plain-language warnings + save-time validation + an audit trail.

Render decision tree
if seo.indexable in ['noindex', 'noindex,nofollow']:
    EMIT NOTHING                                    // no canonical for noindex pages — Google guidance

else if seo.canonicalOverride is set:
    EMIT <link rel="canonical" href={canonicalOverride}>

else:                                                // ~99% case
    EMIT <link rel="canonical" href={baseUrl + path + slug}>
Editor UX — default flow (~99% of pages)
  • Editor opens any document; SEO panel renders the canonical as a read-only chip: "Canonical: https://cleanstart.com/blogs/sbom-101 (auto)".
  • No input. No edit affordance. Cannot break it.
  • If the editor changes the slug, the canonical chip updates live; on save, the URL is re-computed and the slug-change hook (§Drafts & versions) creates a redirect from the old path.
Editor UX — override flow (rare; ~1% of pages)
  1. Editor expands the SEO panel's Advanced disclosure (collapsed by default).
  2. Toggles "This content was originally published elsewhere (set custom canonical)".
  3. A confirmation dialog appears with the plain-language warning:
    Confirm cross-domain canonical ⚠️ This tells Google to credit a different URL for this page. Use only when you republished content from somewhere else. For duplicate pages on cleanstart.com, use a redirect instead.
  4. On confirm, the canonicalOverride URL input is revealed; editor pastes the original-source URL.
  5. Save runs validation (next subsection); on success, renderer emits the override URL.
  6. The SEO panel chip flips from "(auto)" to a yellow "(custom — overrides default)" badge so it's obvious at a glance on every future edit that this page has a non-default canonical.

Removed from the editor surface — derived in the renderer instead

Five fields the original spec exposed have been removed from the editor's SEO panel and moved to renderer-computed values. Each is either ignored by Google or has no decision for an editor to make:

  • seo.sitemapPriority and seo.sitemapChangeFreq — Google does not use sitemap <priority> or <changefreq> as ranking or crawl signals (Google Search Central, John Mueller, multiple confirmations 2017–2024).   • seo.ogType — derived from the collection in the renderer (article for blogs / news / guides; profile for authors; website otherwise). No editor decision; no editor field.
  • seo.twitterCard — derived from ogImage presence (summary_large_image when an image exists, summary otherwise). No editor decision; no editor field.

Pagination canonical strategy

Listing routes (/blogs, /category/[slug], /news, /news-categories/[slug], /resources) emit a self-referential canonical on every paginated URL. Validation, testing, and the publishing checklist gate

  • On every save — server-side validation of Layer-2 forms against schema-dts types: required-property validation. Errors block save inline. Structured forms can't produce malformed JSON, so there's no parse step.
  • On publish — recommended-property check from the same schema-dts validator. Missing recommendeds surface as amber warnings in the publishing checklist (don't block publish). No live Google Rich Results Test API call — it's rate-limited and flaky; Search Console post-launch is the canonical signal.
  • On every CI build — two-validator coverage — sample-page extraction: pull the rendered HTML for one document of each collection type, run all JSON-LD blocks through both (a) structured-data-testing-tool (programmatic, syntax + required-property checking against the schema-dts vocabulary), and (b) the W3C-blessed Schema Markup Validator (vocabulary recognition + property-type correctness). CI fails if either validator reports an error on a critical-page schema. ~30 s extra CI time, no maintenance overhead — the two validators catch complementary edge cases.
  • Production monitoring — Google Search Console's structured-data report is the source of truth post-launch. A weekly Cron pulls Search Console errors and posts to the Microsoft Teams channel.

    • Section requires at least one child block

Listing pages & dynamic content — automatic propagation

The site has two kinds of pages and they behave very differently. Listing pages (/blogs, /news, /resources, /event, /webinar, /job, /category/[slug], /news-categories/[slug], /author/[slug]) are fully automatic — new content appears within seconds of publish with zero editor action and zero deploy. Static pages (/about, /pricing, /solutions/*, /contact) are editor-curated via the page-builder (see §Page-builder blocks); content insertion there is explicit, not automatic.

How a listing page actually works (one trace, end-to-end)

Concrete example — a marketer publishes a new blog at /blogs/sbom-deep-dive:

  1. Editor clicks Publish in the admin → Payload writes _status: published and fires afterChange hooks.
  2. The hook POSTs to apps/web/api/revalidate with tags: ['blogs:sbom-deep-dive', 'blogs:list'] + the rotating X-Revalidate-Secret header.
  3. The handler calls revalidateTag('blogs:list') on Vercel — every page that fetched any blog data with the blogs:list tag is purged from the edge cache. That includes /blogs, /blogs?page=2…N, every /category/[slug] page, the "Latest from the blog" block on /about, and the homepage hero feed.
  4. Next visitor to /blogs triggers a single fresh render against ${CMS}/api/blogs?status=published&sort=-publishedAt&limit=12&page=1. The new article is at position 1.
  5. Result is re-cached at the edge with the same tags. Every subsequent visitor gets sub-millisecond CDN response.

Total wall-clock from Publish to "new article visible at /blogs": typically 5–15 seconds. The same flow runs for every collection — publish a webinar, it shows up at /webinar; publish a job, it shows up at /job. One pattern, ten routes.

A listing page with zero published items returns a friendly empty state ("No upcoming events — check back soon") but the route still renders 200 OK. Filter / facet UX on listing pages

  • Above the fold: filter chips for the collection's primary axis (resources by type; webinars by region / webinarType; jobs by department / locations). Chips drive query-string state (?type=whitepaper&region=apac) so filtered views are linkable and shareable.
  • Filtered URLs are still ISR-cached per query-string combination. The combinatorial explosion is bounded by closed-list filter values, so cache cardinality stays manageable.
  • Search box on listing pages routes to /search?collection=blogs&q=… backed by Meilisearch (see §Search index).
  • Sort dropdown exposes 2–3 options where relevant (newest / most-read / alphabetical on /blogs; upcoming / past on /event).

FAQ handling — collections, blocks, rendering

FAQs appear in three places in the new CMS, all sharing one shape and one renderer. Editors pick whichever surface fits the document; the frontend produces identical markup, identical accessibility, and a single FAQPage JSON-LD blob per URL.

Strategic framing — FAQPage in 2026 Google restricted FAQPage rich results to well-known authoritative government and health sites in August 2023; CleanStart's pages will not render FAQ snippets in classic SERPs. The CMS still emits the schema because it remains a meaningful signal for AI search ingestion (ChatGPT, Perplexity, Google AI Overviews, Claude with web search), voice assistants, and People-Also-Ask. Set editor expectations accordingly: FAQs are a GEO / AI-search asset, not a SERP-snippet play. The SEO panel surfaces this note inline next to the live JSON-LD preview so marketers don't chase a snippet that no longer renders.

Table of contents — auto-generated, sticky, scroll-spied

Long-form documents (blogs and guides) get a table of contents that the editor never types or maintains. A save hook walks the document's Lexical AST, collects H2 + H3 headings, assigns deterministic anchor IDs, and persists a flat array on the document. The frontend reads that array to render a sticky sidebar TOC with active-section highlighting via IntersectionObserver. Editor work: zero. Maintenance work: zero. Drift: structurally impossible — the TOC is regenerated on every save.

Field shape

// Computed field on `blogs` and `guides` — Auto, never editor-edited
tableOfContents: array of {
  level:    2 | 3                  // H2 or H3 only; H4–H6 are excluded
  text:     text                   // exact heading text (preserves casing + punctuation)
  id:       text                   // slugified anchor id, deduped within doc
  position: number                 // source-order index in the body
}

// Companion toggle on the same collections
showTableOfContents: boolean       // Auto-fill, default true

Stored as flat, not nested. The renderer infers H3-under-H2 nesting from the level field at render time — flat is simpler to build, simpler to diff in version history, and trivially sortable by position. Nesting in the data model adds complexity the renderer doesn't need.

Build hook — beforeChange on blogs + guides

  1. Walk the saved Lexical AST root, collect every HeadingNode with tag in {h2, h3} in source order.
  2. For each heading, compute the anchor id: lowercase, ASCII-fold non-Latin characters, replace whitespace with hyphens, strip non-alphanumeric except hyphens, collapse consecutive hyphens, trim leading/trailing hyphens.
  3. Dedupe ids within the doc by appending -2, -3, … in source order when the slug repeats. Stability invariant: a heading at position N keeps the same id across edits as long as its text + the headings preceding it don't change.
  4. Persist the flat array to tableOfContents; persist the resolved id back onto each HeadingNode as a data-anchor attribute so the body renderer doesn't need to recompute.

Same id pool feeds the FAQ deep-link anchors, the per-section "copy link" chip, and the JSON-LD SiteNavigationElement emission — one source of truth, one slugifier, no drift.

Min-headings threshold + opt-out

  • showTableOfContents is the per-document opt-out (default true) — useful for short posts that don't warrant a TOC even if the heading count would qualify.
  • The frontend additionally suppresses the TOC when fewer than 3 H2s exist (configurable via siteSettings.tocMinHeadings). The data is still saved (so it's available if the threshold changes); the renderer just doesn't draw the sidebar. NN/g guidance: TOCs on short documents are clutter, not navigation.
  • No editor warning when a doc falls below the threshold — short posts are normal; the threshold is a renderer-side decision.

Frontend rendering — <TableOfContents> component

  • Single shared server component, two visual variants:
    • variant="sidebar" — sticky floating sidebar at viewports ≥ 1024 px. Right-aligned, narrow column, position: sticky; top: var(--header-offset). Default for blogs and guides.
    • variant="inline" — collapsible accordion below the hero on viewports < 1024 px (mobile + tablet). Collapsed by default; one tap to expand. Avoids the visibility-vs-real-estate tradeoff sticky TOCs lose on mobile.
  • Active-section highlighting via IntersectionObserver with rootMargin: "-10% 0px -75% 0px" — a section becomes "active" when its heading enters the upper viewport quarter. Active item gets aria-current="location" and a left-border accent in the design system's accent color. No scroll-event listeners (poor performance, throttle-prone).
  • Smooth-scroll on click — clicking a TOC item updates window.location.hash (so the URL is shareable) and scrolls smoothly. Heading targets get scroll-margin-top: var(--header-offset) so they clear the sticky site header on landing.
  • Hash-jump on initial load — if the URL contains a matching #section-id on first paint, the page scrolls to that heading and the TOC entry is marked active. Works without JS for the initial scroll (browser-native hash behavior); the scroll-spy upgrades the experience once JS hydrates.
  • Reading progress — a thin 2-px progress bar above the sidebar TOC fills as the reader scrolls through the body. Pairs with readingMinutes to display "3 min remaining" below the TOC. Optional; controlled by siteSettings.tocShowProgress.

Per-heading "copy link" affordance

Every body heading with an auto-anchor renders a small # chip on hover (right of the heading text). Click copies the deep-link URL (https://cleanstart.com/blogs/sbom-101#what-is-sbom) to the clipboard with a "Link copied" toast. Same component reused across body headings and FAQ rows — one affordance, two surfaces, identical UX.

Accessibility

  • Wrapper is <nav aria-label="On this page"> — explicit landmark per the WAI-ARIA APG Landmark Regions guidance, so screen-reader users can jump straight to the on-page navigation. The label disambiguates this nav from the global site nav.
  • List is <ol> + <li> with <a href="#{id}"> children — semantic HTML, no ARIA gymnastics needed for the structure.
  • Active item carries aria-current="location"; CSS reads the attribute for the accent border so the visual and AT signals are tied.
  • Tab / Shift+Tab move between TOC links per browser-native focus order. Enter activates a link. No custom keyboard handlers — the simple semantic-link model gets it for free.
  • The site's existing skip-to-content link (in the global header) lands above the TOC; users who don't want the on-page nav can skip it cleanly.

Admin live preview

  • The Payload admin renders a read-only "On this page" preview panel above the body field whenever the document has ≥ 3 H2s. Updates on every autosave. Mirrors what'll render publicly so editors catch heading-hierarchy issues at edit time, not at publish time.
  • The preview also surfaces inline lint warnings the body editor's red-underline already shows: skipped levels (H2 → H4 with no H3), empty headings, headings > 80 chars (excessive for a TOC link).
  • showTableOfContents appears as a single toggle below the preview, defaulted to on — flipping it off explains the threshold rule in helper text.

SEO — SiteNavigationElement

  • The same tableOfContents array is serialized into a SiteNavigationElement JSON-LD blob alongside the document's Article / TechArticle emission, exposing the in-page navigation to crawlers and AI-search ingestion.
  • Anchor URLs in the JSON-LD are absolute ({baseUrl}/{route}/{slug}#{id}) for unambiguous cross-document linking when the page is excerpted by AI agents.

Why H2/H3 only (and not H4–H6)

Including H4 in the TOC produces visual noise — by the third indent level, the TOC competes with the article body for cognitive load. NN/g's longform-TOC research is unambiguous: 2 levels is the readable ceiling for sidebar TOCs. H4–H6 still get auto-anchor IDs (so deep links to them work via the "copy link" chip), they just don't appear in the navigation. siteSettings.tocMaxDepth can extend to H4 if a future content type genuinely needs it; default stays at 2.

Migration from Webflow

Webflow has no TOC concept — most posts ship without one, and the few that do use a custom embed. At cutover, every migrated blogs and guides document gets a TOC for free from the body's existing H2/H3 structure. No editor work; ~290 documents go from "no TOC" to "TOC on every long-form post" overnight.

Tables — rich text + page-builder block

Tables are supported in two complementary ways: as native nodes inside any rich-text body, and as a dedicated page-builder block for tables that need stronger editorial control. Both render through one shared <Table> component so styling and accessibility behave identically.

When to use which surface

Quick heuristic: ≤ 3 columns and ≤ 8 rows that flow with surrounding paragraphs → inline Lexical table. Standalone marketing comparison, pricing matrix, or feature grid → page-builder Table block. The block is purpose-built for B2B SaaS comparison content; the inline option is purpose-built for prose-adjacent data.

1 · Tables inside rich text (Lexical)

  • Lexical's official TableNode / TableRowNode / TableCellNode are enabled in every rich-text editor (blogs.body, news.body, guides.body, resources.body, events.body, webinars.body, jobs.body, authors.bioLong, FAQ answers).

  • Use case: short data tables interleaved with prose ("Comparison of TLS versions", "Image variant sizes").

Validation (save-time)

  • Cell-count match — every { cells } row must have cells.length === headers.length. Mismatched rows surface inline as red errors and block save.
  • Headers required — at least one header label must be non-empty.
  • Value cells required — when cell.type === 'value', content can't be empty (use cross for "no value" instead).
  • Highlight-column bounds — highlightColumn, when set, must be a valid 1-based index within headers.
  • Group-header limit — adjacent groupHeader rows are collapsed to one (empty-section guard).

  • Standalone marketing tables: no Webflow content currently uses the Table page-builder pattern — the block is a forward-looking addition for new pricing / comparison content on the rebuild.

Render rules (applied automatically by the Lexical → React renderer)

  • Every external link gets rel="noopener noreferrer" always. rel="nofollow" when the editor toggles the per-link Nofollow switch in the toolbar (used for paid placements, sponsored content, untrusted destinations).
  • Every off-cleanstart.com link defaults to target="_blank"; same-site links default to same-tab. Editors can override per link.
  • Internal-doc links resolve to the target's current URL at render time. If the target is unpublished or archived, the link renders as plain text and the source document gets a build-time warning + an admin badge ("3 broken links — fix before publish").
  • UTM and tracking parameters on external links are preserved; we don't strip them.
  • Internal links never get tracking parameters injected (clean URLs for SEO).

Integrity & broken-link checking

  • On save: Payload validates every internal-doc link points at an existing, publishable document. The editor sees inline warnings before publish — this is the launch-day mechanism.
  • Internal-link drift can't happen because slugs change → URLs auto-update; doc deletions are blocked while inbound internal links exist (onDelete: 'restrict').
  • External link health: the on-save check covers internal integrity. A daily HEAD-request crawler over external URLs is a v1.5 addition once the external-link count exceeds ~500.

Redirects (URL-level, not link-level)

  • One mechanism: the standalone redirects collection. Every redirect — slug-change, vanity, retired-page, or migration seed — lives there. See the full schema in §Per-collection schemas.
  • Slug changes auto-create a row. A beforeChange hook on every publishable collection detects a slug edit and writes a new redirects row with source: 'slug-change', from: oldPath, to: newPath, status: 301. Editors don't think about it; the redirect exists by the time the slug-change save returns.
  • Chain auto-flattening at write time. Creating a rule whose to matches an existing from rewrites the chain to a single hop — Google Search Central's redirects guide recommends single-hop chains (multi-hop chains lose link equity and slow Googlebot).
  • The collection feeds Next.js's middleware at request time. Hit counts persist so editors can prune obsolete redirects via the admin view sorted by lastHitAt.

What gets stripped on paste (intentionally)

  • Word's mso-* styles, <font> tags, <span style> color / font-size / line-height — typography is design-system-driven, not editor-driven.
  • Custom margins, padding, indents — flow defaults to our spacing tokens.
  • "Page X of Y" auto-text, header/footer artifacts, page-break markers.
  • Empty paragraphs and consecutive line breaks (collapsed to one).
  • Word smart-quote / em-dash characters are kept (typographic correctness); non-breaking spaces are converted to regular spaces.

Sanitization pipeline — defense in depth

Three sanitization layers run on every paste, per current best practice (cure53/DOMPurify guidance + LEXSS bypass research). No layer is alone sufficient:

  1. Browser-level paste handler — Lexical's built-in paste plugin filters obvious dangerous nodes before the AST is constructed.
  2. Server-side sanitize-html on the full clipboard HTML payload before the Lexical converter runs — strict allowlist (the tag set documented in §HTML semantics), all on* event handlers stripped, all style/class attributes stripped, all <script>/<iframe>/<object>/<embed> rejected. Server-side because the client can be bypassed.
  3. Lexical typed nodes — the Lexical → React serializer produces typed nodes from the audited tag set; raw HTML can never reach the rendered DOM.

SVG uploads pass through DOMPurify with a strict profile separately (no scripts, no event handlers, no external refs). The triple-layer pattern is what prevents serialization-roundtrip bypasses where one layer's "safe" output becomes another layer's input vector.

Plain-text paste NEW

File upload security — magic-byte validation + virus scan NEW

Per OWASP File Upload Cheat Sheet, never trust the client-provided MIME type or extension — both are easily spoofed. The upload pipeline (whether from paste, drag-drop, or Media admin upload) runs three validation passes before anything reaches R2:

  1. Magic-byte inspection via the file-type library — reads the first 4–32 bytes of the upload and matches against a binary-signature table. A file claiming image/jpeg whose first bytes don't match the JPEG FFD8FF signature is rejected with a clear error. Catches the "rename shell.php to image.jpg" attack class.
  2. Magic-byte vs declared extension/MIME match — Sharp / pdf-parse / equivalent runs a parse-pass on the file before R2 write. Any parse failure rejects the upload (corrupted file, polyglot file, executable disguised as image).
  3. ClamAV virus scan on PDFs, ZIPs, and other non-image binaries. ClamAV runs as a sidecar container on the droplet (free, open-source); virus signatures auto-update via freshclam daily. Image files skip ClamAV (low risk; Sharp re-encode strips most malicious payloads anyway).

SVG uploads additionally pass through DOMPurify's strict profile (already documented above — kept here for completeness). The fourth defence is the Content-Disposition header on served files — PDFs and other documents are served with Content-Disposition: attachment for non-image types except where inline preview is explicitly desired (the doc's existing PDF inline behaviour). Combined with X-Content-Type-Options: nosniff (already in the security-headers spec), this prevents browser MIME-sniff fallbacks from executing a misclassified file as something active.

Image paste — works mid-content, single or batched

Editors can drop an image at any cursor position — including between two paragraphs in the middle of a body — and it inserts inline as its own block without disturbing the surrounding text. Single clipboard image, drag-and-drop from Finder, or images embedded in a Word / Google Docs / Notion paste all flow through the same handler.

Sources the editor accepts
  • Clipboard image — screenshots (⌘⇧4 / Snip), copy-from-Preview, copy-from-Figma, right-click Copy image on a webpage, Copy image in Microsoft Teams / Slack / chat apps. Clipboard payload is binary image/png / image/jpeg.
  • Drag & drop from Finder / desktop / another browser tab — the file lands at the drop position.
  • Embedded in a Word / Docs / Notion paste — each <img src="data:…"> or <img src="blob:…"> in the clipboard HTML becomes its own block in document order.
  • Image URL dragged in (e.g. a tab URL pointing at example.com/photo.jpg) — the server fetches the bytes and uploads to R2 (no hot-linking).
What happens, step by step (mid-content paste)
  1. Cursor sits between paragraph N and paragraph N+1; editor pastes or drops the image.
  2. An upload-progress placeholder block appears at the cursor — surrounding paragraphs stay untouched, no caret jump, no flicker.
  3. The Lexical paste / drop handler decodes the binary, generates a slugified filename (pasted-image-2026-04-29-1432.png or derived from the source filename / figure caption), and reads the document's collection to set folder — paste into a blogs doc → web/blog/; into jobs → web/job/; into guides → web/guide/; etc.
  4. cloudStorage plugin streams the file to R2; image-resize plugin generates two derivatives (card, hero); a media document is created with the resolved url and sizes. (og derivative is created later, on-demand, if this asset is promoted to seo.ogImage.)
  5. The placeholder swaps for a Lexical UploadNode referencing the new media ID — rendered at view time as <figure><CmsImage variant="card" /></figure> on its own line, between the two paragraphs.
  6. A toast appears: "Image uploaded. Add alt text to publish." Click opens an inline metadata panel for alt, caption, credit, focalPoint — no full-page navigation, no leaving the editor.
  7. Publish is blocked until alt text is filled (a11y gate, configurable per collection).
Batched paste — image inside a Word doc

When an editor pastes a whole Word doc that contains multiple inline images, the sanitizer walks the source HTML in document order and emits one UploadNode per image at exactly the position it occupied in the source. So an image after paragraph 3 stays after paragraph 3 in the rich-text body. Each image uploads in parallel; per-image progress toasts surface as they complete.

Edge cases
  • Auth-protected source (e.g. a private Figma share) → fetch fails; toast asks the editor to download locally and re-paste.
  • Animated GIFs are accepted; the resize plugin keeps the original only (no animated thumbnails — large file, low value).
  • HEIC (iPhone screenshots) → Sharp converts to JPEG on upload server-side.
  • SVG uploads pass through DOMPurify with a strict profile (<script>, event handlers, external refs stripped).
  • Files > 25 MB → Payload rejects pre-upload; toast surfaces the limit; nothing written to R2.
  • Same image pasted twice → R2 dedup by content hash; both UploadNodes reference the same media document, no duplicate object in the bucket.

Link paste behaviour

  • Every <a href> in the pasted HTML lands as a LinkNode of {kind: 'url', href}.
  • The handler scans for known cleanstart.com URL patterns and offers one-click "Convert N links to internal doc links?" at the top of the editor. Accepting swaps each match for an internal-doc reference.
  • Word's "internal cross-references" (bookmarks, footnote anchors) flatten to plain text unless the bookmark target is in the same paste, in which case they become anchor links. When any reference is flattened, the editor sees a non-blocking admin toast counting the failures: "3 cross-references couldn't be resolved (target outside paste) and were flattened to plain text." Never silent — the editor needs to know why "See Chapter 5" lost its link.

What still needs an editor's hand after paste

  1. Alt text on every pasted image — a11y gate; publish blocked until filled.
  2. Internal-link conversion confirmation — accept or reject the auto-detect prompt.
  3. Heading hierarchy review — the level-shift is heuristic; if the source doc had multiple H1s as section titles, the editor confirms the resulting H2 structure.
  4. Tables wider than ~6 columns — preview on mobile; if cramped, switch to the page-builder Table block (§Tables) for richer control.
  5. Code blocks — set the language hint when pasting from Word (Docs / Notion auto-detect).

Recommended publishing workflow

  1. Editor pastes the entire Word doc body into the rich-text field (blogs.body, guides.body, etc.).
  2. Sanitizer cleans Word styles; images upload in the background; toasts surface as each completes.
  3. Editor accepts the "convert N URLs to internal links" prompt.
  4. Editor fills alt text on every image (admin highlights the missing fields).
  5. Editor reviews heading hierarchy and the auto-built TOC.
  6. Editor previews via the token-gated preview URL (Payload's draft + preview workflow).
  7. Editor publishes — JSON-LD, sitemap entry, ISR revalidation, redirect entries all flow automatically.
In short Paste-and-publish works for the body content. The editor's job after paste is the things a sanitizer can't infer: accessibility (alt text), link semantics (internal vs external), and a heading-hierarchy sanity check. Everything else — typography, spacing, link rel/target, image hosting, derivatives, JSON-LD — is automatic.

The renderer produces correct, accessible, SEO-clean markup with design-token typography, a single <h1> per page, no inline styles, no script vectors, and stable heading anchors. Same output every time, regardless of how the source content was authored.

  • Autosave on debounced keystroke. Drafts auto-save 800 ms after the last keystroke; explicit Publish is the only manual transition (draft → published). Scheduled publish

  • Editor sets status: scheduled and scheduledFor: <datetime>.
  • A Payload jobs cron runs every minute, finds any scheduled doc whose scheduledFor ≤ now(), and promotes it to published (sets publishedAt = now(), fires the same on-publish hooks as a manual publish).
  • Scheduled docs render in the admin with a clock icon + countdown. Editor can cancel by reverting to draft.

Concurrent-edit protection — stale-edit warning banner

Two editors opening the same draft will silently last-save-wins without warning unless we surface the conflict. For a 1–3 person team this is a real foot-gun (two marketers, one stand-up handover, twenty minutes of work disappears). Cheap fix: a non-blocking banner that detects the second editor and offers a recoverable reload.

  • On admin edit-screen load, capture the doc's updatedAt as the local baseline.
  • Poll updatedAt every 30 s. If the server value advances and the change wasn't from the current user, render a non-blocking banner above the form: "Jane edited this draft 12 seconds ago. Reload to see her changes (your unsaved edits will be preserved in a recovery draft)."
  • The banner's Reload button serializes the current dirty form state to localStorage._recoveryDraft_{collection}_{docId} before reload, then offers "Restore your unsaved edits" on the next load — so even mid-keystroke conflicts don't destroy work.
  • Banner shows the other editor's name + relative time + their avatar, never their cursor (no real-time collaborative editing at launch — that's a separate v2 effort).
  • The banner is non-blocking on purpose: an editor can finish a thought, save, then reload — versions give them the diff to merge by hand if needed.

Real-time multiplayer editing (Liveblocks / Yjs / Payload's experimental collab plugin) is out of scope at launch. Trigger for revisit: when concurrent-edit conflicts surface in editor support tickets more than once a quarter, OR when the editor count exceeds 3.

Slug-change cascade

When a document's slug changes (whether by editor edit or admin action), a single beforeChange hook orchestrates the full propagation so editors don't have to think about it:

  1. Auto-create a redirects row from the old path to the new path, with source: 'slug-change' and status: 301. Existing chains are auto-flattened (see §redirects collection).
  2. ISR-revalidate every back-referencing route by calling revalidateTag('{collection}:list') for every collection that may contain inbound links — internal links are stored as {kind: 'doc', id} not as URLs, so the link always resolves to the new URL on next render. Slightly wider than precise reverse-lookup invalidation but ~zero perceptible difference at this scale.
  3. Ping Google's Indexing API for the new URL so Googlebot recrawl is fast (within hours rather than days). The Indexing API is officially supported for JobPosting and BroadcastEvent; for other content types we still use it as a soft-recrawl signal — Search Console treats it as a hint.
  4. Update the sitemap cache key so /sitemap.xml emits the new URL on next request.
  5. Do not fire document.published — slug change is a URL event, not a publish event. Webhook consumers shouldn't see "published" twice for one piece of content.

Publishing checklist — what the editor sees before "Publish"

Payload's admin shows a live checklist on every draft, scoped to the document's collection. Items in red block publish; items in yellow are warnings; items in green are auto-completed by the system. The editor can publish without warnings being green; cannot publish if anything is red. Drafts can save with red items — gates apply only at the publish click. The DatoCMS-style draft-permissive / publish-strict separation keeps the editor in flow during writing while preserving editorial safety at the moment of going live.

Architecture — per-collection rule registry

The checklist is not a single universal table — different collections need different gates (events.startsAt required ≠ blogs.heroImage required ≠ jobs.atsUrl required-when-source=ats). Rules live in per-collection registries at apps/cms/src/payload/lib/publishing/rules/{collection}.ts; each collection's beforePublish hook composes its rule set. Rules are typed: 

// apps/cms/src/payload/lib/publishing/types.ts
type Severity = 'block' | 'warn' | 'auto';
type RuleStage = 'save' | 'publish';     // when the rule runs

interface Rule {
  id: string;                              // stable id, used in telemetry
  severity: Severity;
  stage: RuleStage;
  collections: string[] | 'all';           // which collections it applies to
  evaluate: (doc, ctx) => RuleResult;
}

interface RuleResult {
  passed: boolean;
  message?: string;
  fix?: { label: string; action: () => void };  // optional click-to-fix
}

Save-time vs publish-time split

Running every check on every autosave (every 800 ms after a keystroke) thrashes the database — a 30-internal-link guide would issue 30+ DB roundtrips per save. The rule registry differentiates:

  • Save-time rules run on every save (cheap, in-memory): field-presence, length counters, regex validation, basic field shape. ~5 ms per save.
  • Publish-time rules run only when the editor clicks Publish (full validation, including DB roundtrips, render simulation, external HEAD-checks): internal-link integrity, redirect chain check, JSON-LD validation, alt-text resolution across the media graph. ~200–500 ms per publish click — acceptable as a one-shot at the gate.
  • Diff-aware re-publish: on republish (an edit to an already-published doc), publish-time rules with stable dependencies skip — e.g. external-URL HEAD-check on a body-text-only edit reuses the cached result from the last publish (24-hour cache). Cuts republish friction by ~60% on minor edits.

Atomic check+publish

The publish action wraps the full publish-time rule evaluation + state transition in a single Postgres transaction with a row-level lock on the document. Prevents the TOCTTOU bug where checks pass at click, another editor's commit lands an invalid state, and the publish proceeds against the new state.

Skip-warning-with-reason

Every Warn item has a "Ship anyway" action. Clicking it asks for an optional one-line reason (no minimum length); the reason — when entered — is captured into the document version's commit message + the publish_friction row's override_reason field. Keeps friction tiny while preserving traceability.

Force-publish override (Admin role, Block items)

Block items can be bypassed via Force publish, available only to the Admin role. Requires a typed reason (any length, no minimum); writes a publish_friction row with outcome='force-published' + the bypassed rule(s) + the reason. No Teams ping, no 50-char minimum, no checkbox confirmation — keep the escape hatch lightweight so it's used when needed without ceremony. Provides the safety valve for false-positive Blocks (e.g. alt-text gate firing on an image awaiting a decorative=true toggle) without eroding the gate's value through adoption friction.

Alt-text click-to-fix affordance

When the alt-text gate fires, the checklist chip exposes a single button: "Add alt text to N images". Clicking opens an inline modal listing every image in the document with an empty alt field; editor fills them in one screen, presses Save, the gate clears. Single-rule click-to-fix at launch — alt-text is by far the highest-frequency Block trigger and the highest-leverage fix surface; broken-link / heading-hierarchy / OG-image auto-fix flows can ship later if their friction is real (none currently is).

Forms & leads — dual-write, CRM-agnostic, marketer-self-serve

Marketers define forms in the admin (no engineering needed). Submissions hit a single /api/leads endpoint that runs a dual-write pipeline: DbLeadHandler always writes the lead to the CMS Postgres database first (and is the source of truth); then any CRM handlers configured on the form (HubspotLeadHandler, SalesforceLeadHandler, ZapierLeadHandler, etc.) fire in parallel as best-effort secondaries. CRM failures never lose the lead — the row is already persisted in our Postgres and visible in the admin Leads view; the failure is logged in leads.syncedTo[].status with a retry queued.

Why dual-write
  • Sales gets leads in the CRM in real time (HubSpot / Salesforce / etc.).
  • Marketing keeps a complete, searchable, page-attributed record in the CMS — independent of CRM uptime, retention policies, or vendor lock-in.
  • If the CRM ever changes, the historical record stays put and migrates with the CMS.
  • GDPR DSAR (export / delete-by-email) runs against our DB — the canonical store — and propagates downstream by triggering matching deletes in every syncedTo[] handler.

// /api/leads dual-write pipeline (pseudocode)
async function handleSubmission(form, payload, ctx) {
  // 1. PRIMARY: write to Postgres. Source of truth.
  //    If this throws, the visitor sees an error — the lead is NOT lost in a half-state.
  const lead = await dbHandler.submit(form, payload, ctx);

  // 2. SECONDARIES: fire every configured CRM handler in parallel (best-effort).
  //    Each one's outcome is appended to lead.syncedTo[] for audit + retry.
  const crmHandlers = form.crmHandlers.map(name => registry[name]);
  await Promise.allSettled(
    crmHandlers.map(async h => {
      try {
        const r = await h.submit(form, payload, ctx);
        await appendSyncedTo(lead.id, { handler: h.name, status: 'ok', externalId: r.id });
      } catch (err) {
        await appendSyncedTo(lead.id, { handler: h.name, status: 'failed', error: err.message });
        await enqueueRetry({ leadId: lead.id, handler: h.name }); // exponential backoff
      }
    })
  );

  return lead;
}

Lead durability — surviving CMS outage

Form submissions normally write to Payload via /api/leads on the public site, which calls the CMS API on the droplet. If the droplet is unreachable (outage, deploy, OOM), naive code loses the lead silently — the highest-cost failure mode in this stack. Mitigation: every failed write falls back to a durable JSON object in R2, drained automatically when the CMS recovers.

Flow
  1. Form posts to /api/leads on Vercel.
  2. Function attempts the Payload API call with a 3-second timeout.
  3. On any failure (timeout, network error, non-2xx), write the lead JSON to web/_pending-leads/{ISO-timestamp}-{uuid}.json on R2.
  4. User always sees "Thanks, we'll be in touch" — identical UX to the success path.
  5. Drain cron on Payload (every 5 min): list _pending-leads/, ingest each file through the same LeadHandler adapter chain (consent + spam + CRM sync), delete on success.
Why R2 specifically
  • Independent infrastructure (Cloudflare) — survives full DO regional outage.
  • Already in the stack for media + backups; no new vendor.
  • Egress-free; storage cost negligible (a lead JSON is ~2 KB; 1,000 stuck leads = 2 MB).
  • Vercel already holds R2 credentials for signed URLs — no new secret to manage.
Alerts (BetterStack)
  • _pending-leads/ count > 10 → P2 warn (drain may be slow).
  • Oldest file in queue > 1 hour → P1 page on-call (drain isn't running).
Admin surface

A "Pending leads" badge in the leads list view appears when the queue is non-empty, showing count and oldest age, so editors know there's a backlog and roughly how stale it is — without having to check R2 directly.

Same adapter chain — no second code path Drained leads run through the exact same LeadHandler registry as the live path (DbLeadHandler → secondary CRM handlers). Consent snapshots, spam checks, and CRM sync behave identically; the queue is just a delay buffer, not a parallel pipeline.

Performance budgets and security headers below tell you the site is fast and safe; this subsection tells you what happens when it isn't. Structured logging

INP-specific guidance (the 2024+ playbook)

INP became a Core Web Vital in March 2024. Unlike LCP (which is mostly an image-bytes problem), INP is a main-thread problem — long tasks block input handling. The patterns:

  • React 19 Concurrent + RSC — server components ship zero JS for static content; useTransition wraps non-urgent state updates so input handlers stay responsive; the React Compiler handles memoization automatically (no manual React.memo/useMemo ceremony).
  • scheduler.yield() — break long synchronous tasks into chunks. The single most effective INP fix per web.dev. Used in any client-side handler that does meaningful work (form validation, search filtering, large-list interactions).
  • Hydration cost discipline — every interactive component is a hydration cost. The page-builder block library favours server components; only the FAQ accordion, table-of-contents scroll-spy, and form widgets ship JS to the client.
  • Long-task spotting — Lighthouse CI's TBT (Total Blocking Time) is the lab proxy for INP; tracked but not gated (TBT correlates poorly with field INP, so the budget is RUM-based).

Production monitoring — RUM + alerting

  • Vercel Speed Insights — real-user CWV per route, per device. Free-tier sampling rate is ~1 % of traffic. Alert thresholds account for the sampling — don't fire on a single event spike.
  • Alert routing: Speed Insights → Sentry → #perf-alerts Teams channel. SLO: 24-hour engineer triage (acknowledge + initial assessment within 24 h; fix or accept-and-document within 1 week).
  • Alert rules: fire when 7-day rolling p75 mobile breaches Mobile p75 target by > 10 % on a route with > 100 sessions/week (low-traffic noise filter).

  • Review cadence: monthly engineering review — one slide showing per-template p75 trends (mobile + desktop), with annotations for any deploys that correlated with shifts.

Regression triage runbook

When Lighthouse CI fails on a PR, or when Speed Insights / CrUX shows a production regression, the engineer's playbook lives in docs/PERF-RUNBOOK.md in the repo. Outline:

  1. Identify the metric and the route — which CWV metric on which page template is regressing?
  2. Reproduce locally with the same Lighthouse version and run profile. Variance > 5 % between runs = noise; investigate further.
  3. Bisect against the last green main-branch baseline; identify the responsible commit.
  4. Fix or revert — fix in PR if cheap; revert if not. Production CWV regressions take precedence over feature work.
  5. Override path — for legitimate cases where the metric is correct but the gate is wrong (e.g. a new route template is genuinely heavier and needs a higher budget): rebaseline the budget in lighthouserc.json, document the change in the PR description, get a second engineer's review.
  6. Post-mortem on any production regression that took > 1 week to resolve — written up in the engineering monthly.

ISR + Cloudflare CDN handles the LCP / TTFB story for cached requests. Image weight is bounded by the two-derivative cap (card 800 w, hero 1600 w) + AVIF / WebP via next/image. CLS is held at zero by reserving space for every UploadNode at render time using media.width / media.height.

CSP nonce + ISR — architecture decision

Per-request nonces conflict with ISR caching (each request needs a fresh nonce, which would normally force dynamic rendering). The chosen pattern: middleware injects the nonce per request into the response stream (it's not part of the cache key); the static HTML body cached by ISR contains a placeholder; Next.js's edge-streaming response substitutes the nonce on its way to the client. This keeps ISR cacheability while providing per-request nonces. Alternative (rejected): hash-based static CSP — works but breaks any time a new inline script is introduced, requiring a re-deploy to update the hash list.

CSP rollout — short Report-Only burn-in

For a fresh Next.js launch with intentional, vendor-allowlisted directives, the spec is built up-front rather than archaeologically reconstructed from existing site behaviour. Burn-in window: Week 1 post-launch ship as Content-Security-Policy-Report-Only; monitor Sentry's CSP-violation feed for any unexpected hits; Week 2 switch to enforcing Content-Security-Policy. Keep Report-Only active in parallel for ongoing observability — both headers can co-exist.

Subresource Integrity (SRI)

Every external <script> tag (Vercel Analytics, Sentry, Cloudflare Turnstile) emits an integrity="sha384-…" attribute pinned to the vendor's published bundle hash. If a CDN gets compromised and the script changes, the browser refuses to execute it. Integrity hashes update via Renovate-bot PRs against the vendor's current bundle — ~5 hours/year of maintenance across the three vendors, a price worth paying given CleanStart's product positioning as a container-security vendor (the marketing site's security posture is brand-credibility surface).

Sitemap & robots.txt — exact contents

/sitemap.xml

  • Generated at request time by app/sitemap.ts, ISR-cached for 1 hour, instantly invalidated on any document publish/archive.
  • Includes: every _status: published document from blogs, news, guides, resources, events, webinars, jobs, authors, categories, newsCategories, pages.
  • Excludes: drafts, scheduled, archived; anything with seo.indexable set to noindex or noindex,nofollow; aboutGalleries (data, not pages); media (assets indexed via image sitemap, see below); users, forms, leads, redirects (system collections).
  • Per-row: <loc>, <lastmod> (= updatedAt for detail pages). Listing pages (/blogs, /news, /category/[slug], /news-categories/[slug], /resources) report <lastmod> = MAX(updatedAt) across their currently-published children — so when an item underneath changes, Googlebot is signalled to recrawl the listing without waiting for the listing's own metadata to change. <changefreq> and <priority> emitted as renderer-computed per-collection defaults (blogs/news weekly 0.7, guides monthly 0.8, jobs daily 0.5, pages monthly 0.6) — not editor-overridable, since Google does not use either as a ranking or crawl signal (Search Central). Kept in the XML for crawlers that still parse them; not surfaced as editor fields.
  • Splits at 45,000 URLs into a sitemap index (we're nowhere near, but the implementation is forward-compatible).

/sitemap-images.xml

  • Image sitemap listing every media referenced from a published document, with image:title = media.alt and image:caption = media.caption.

Pagination indexing strategy

  • Pages 1–5 of every paginated listing (/blogs?page=N, /news?page=N, /category/[slug]?page=N, etc.) are indexable with self-referential canonicals.
  • Pages 6+ emit <meta name="robots" content="noindex,follow"> — preserves crawl budget on long archives without losing the link-graph for crawlers walking through. Threshold configurable via siteSettings.paginationIndexableDepth (default 5).
  • Each paginated page also emits a self-canonical (Google Search Central guidance since the March 2019 deprecation of rel="next"/"prev").

Soft-404 prevention

  • Listing pages (/category/[slug], /news-categories/[slug], taxonomy archives) that have zero published children return 410 Gone instead of 200 OK with empty content — Google treats empty 200s as soft-404s and demotes them.
  • The category/taxonomy admin shows a warning chip when a category has zero published items: "This category has no published items — its listing page will return 410 Gone until at least one item is published."
  • Detail pages (/blogs/[slug], /news/[slug], etc.) for archived documents return 410 Gone unless an explicit redirects rule overrides to 301 (the archive flow's default behaviour).

/sitemap-news.xml NEW

  • Google News sitemap per Google's news-sitemap spec — separate file, only articles from the last 2 days (Google's window), max 1,000 URLs.
  • Per-row tags: <news:publication> with name=CleanStart + language=en; <news:publication_date> in W3C ISO 8601 format from news.publicationDate; <news:title> from news.title.
  • Auto-prunes daily — items older than 2 days are removed from this sitemap (still in /sitemap.xml).

/llms-full.txt — concatenated full-content variant

Same standard, but contains the full body markdown of every page listed in llms.txt, concatenated into a single document. Some AI agents prefer this for one-shot ingestion (instead of following links one at a time).

  • Built at request time by walking each page in seoDefaults.llmsTxt, fetching its document, running its body Lexical AST through the markdown serializer (the same one used for content negotiation, below), and concatenating with H1 page headers as separators.
  • ISR-cached for 1 hour · invalidated when any listed document publishes or when seoDefaults.llmsTxt changes.
  • Size bound: typically 50–200 KB · still 10× smaller than the equivalent rendered HTML.

Markdown content negotiation — Accept: text/markdown

When an HTTP request includes Accept: text/markdown in its preference list, every public content route returns the page as markdown instead of HTML. Standard since Cloudflare's 2026 "Markdown for Agents" launch; Claude Code, Cursor, and OpenCode send this header by default, and ChatGPT browsing increasingly does too. ~99% payload reduction for AI consumers compared to fully-rendered HTML. 

// apps/web/middleware.ts
const acceptsMarkdown = req.headers.get('accept')
  ?.toLowerCase()
  .split(',')
  .some(t => t.trim().startsWith('text/markdown'));

if (acceptsMarkdown && isPublicContentRoute(req.nextUrl.pathname)) {
  // Route handler runs the rendered Lexical AST through react-to-markdown
  // serializer and returns Content-Type: text/markdown; charset=utf-8
  return rewrite(`/api/markdown${req.nextUrl.pathname}`);
}
  • Scope: blogs/*, news/*, guides/*, resources/*, events/*, webinars/*, jobs/*, authors/*, category/*, news-categories/*, pages/*. /preview, /admin, and /api are excluded.
  • Markdown shape: page title as #, abstract as a blockquote intro, body Lexical AST serialized to standard CommonMark, FAQs as ## sections per question, JSON-LD mentions[] + about[] as a YAML frontmatter block at the top.
  • Vary: Accept response header so CDNs cache HTML and markdown variants separately under the same URL.
  • Link: rel="alternate" response header on HTML responses pointing at the markdown variant: Link: <https://cleanstart.com/blogs/sbom-101>; rel="alternate"; type="text/markdown" — explicit discoverability for agents that don't speak content negotiation.

Cloudflare Content Signals

Since CleanStart is on Cloudflare (CDN + WAF), the team enables Content Signals at the edge — a 2026 Cloudflare-proposed standard for declaring per-page AI usage permissions: noai (don't train), noimageai (don't train on images), search (search indexing OK), ai-inference (inference / answer-generation OK).

  • Default policy: search + ai-inference = allow · noai + noimageai = allow training (the team's strategic posture is content marketing → AI-search visibility wins).
  • Per-document override: a seo.contentSignals field (Cond., advanced toggle) lets the marketer override defaults on specific docs (e.g., a customer story whose subject doesn't want their data trained on).
  • Renderer: emits the content-signal HTTP header per route based on the resolved policy.

Discoverability headers

  • Link: <url>; rel="describedby"; type="application/ld+json" — points at the page's JSON-LD blob (which is also embedded in the HTML <head>); explicit second discovery path for crawlers that only read response headers.

Why GTM-first (single-script architecture)

Loading every marketing tag directly in apps/web would mean: a new <Script> tag per vendor, a new CSP script-src allowlist entry per vendor, a new code review per pixel, a new performance budget hit per script, a new cookie-consent integration per vendor. That's slow, brittle, and pushes marketing decisions through engineering.

  • One script in the root layout (the GTM container loader, ~30 KB async) — every other tag fires through it, lazy-loaded on demand.
  • One CSP entry in script-src: https://www.googletagmanager.com — additional vendor domains are auto-allowlisted by GTM's iframe sandbox.
  • Marketer-self-serve: GA event setup, Meta Pixel events, conversion goals, scroll-depth tracking, custom-dimension config — all done in the GTM portal without filing engineering tickets.
  • Centralized cookie-consent gate: when the Klaro CMP ships in v1.5 (per §Privacy & GDPR), it gates the GTM container itself — declined consent = zero marketing tags fire site-wide. With per-tag direct loading, you'd need per-vendor consent integration.
  • 30-second rollback for misbehaving tags: a noisy Meta Pixel rule disables in GTM in seconds without an engineering deploy.

ISR revalidation handshake

On every publish / unpublish / archive in apps/cms, an afterChange hook calls apps/web's revalidation endpoint with the document's tag set. apps/web revalidates only the affected routes — never a full rebuild. 

// apps/cms — afterChange hook on every publishable collection
const tag = `${collection}:${doc.id}`;
const collectionTag = `${collection}:list`;

await fetch(`${WEB_URL}/api/revalidate`, {
  method: 'POST',
  headers: {
    'X-Revalidate-Secret': process.env.REVALIDATE_SECRET, // shared, rotated quarterly
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ tags: [tag, collectionTag] }),
});

// apps/web — /api/revalidate route
export async function POST(req: Request) {
  if (req.headers.get('X-Revalidate-Secret') !== process.env.REVALIDATE_SECRET) {
    return new Response('Forbidden', { status: 401 });
  }
  const { tags } = await req.json();
  for (const tag of tags) revalidateTag(tag);
  return Response.json({ revalidated: tags, at: Date.now() });
}
  • Pages are tagged at fetch time: fetch(url, {next: {tags: [`blogs:${id}`, 'blogs:list']}}).
  • Failure handling: if revalidation fails (network blip, secret mismatch), the cms hook logs to Sentry and queues a retry via Payload's jobs queue. ISR cache will eventually hit its own TTL (24h default) so failure is recoverable.
  • Asset moves (folder rename / re-key) trigger revalidation for every consuming document via the media.afterChange hook (see §Assets).

Backup & restore runbook

Backup contents

  • Postgres — full pg_dump --format=custom nightly. Retained: 7 daily, 4 weekly, 3 monthly. R2 path web/_backups/postgres/{YYYY-MM-DD}.dump.
  • Meilisearch — meili-dump nightly. Retained: 7 daily. R2 path web/_backups/meili/{YYYY-MM-DD}.dump.
  • R2 media — Cloudflare R2 versioning enabled with 30-day retention; restore-from-version is built-in to R2.
  • Cross-cloud backup mirror NEW — nightly cron (03:30 IST) syncs the previous day's web/_backups/ prefix from R2 to a secondary S3-compatible bucket (DigitalOcean Spaces, ~$5/mo for 250 GB included). Cross-cloud means a Cloudflare regional outage doesn't take the backups offline at the same time the production droplet is unaffected. Restore from the secondary mirror is documented in docs/runbooks/restore-from-secondary.md and tested in the monthly drill (rotated quarter-by-quarter: Q1 from R2, Q2 from Spaces, etc., so both restore paths get exercised at least twice a year). Without this, R2 is a single point of failure for the entire backup chain (DB dumps + media + lead-fallback queue all live there).

Restore procedure (RTO < 30 min, RPO < 24 h)

  1. Provision a fresh DO droplet (or use the standby snapshot). Apply the §droplet tuning spec (Postgres / Sharp / Meilisearch / swap / sysctl) before bringing services up.
  2. Pull the latest pg_dump from R2 → pg_restore --clean --if-exists into a fresh Postgres 16.
  3. Skip the Meilisearch dump restore — drop the search index entirely and rebuild from Postgres via the existing afterChange indexers (typically < 2 min for ~290 docs). The meili-dump from a non-atomic snapshot can be inconsistent with Postgres; rebuilding from the restored DB is the only safe path. The Meilisearch dump remains in R2 only as a dev-time convenience.
  4. Re-deploy apps/cms via Coolify pointing at the restored DB; run payload migrate to ensure schema parity.
  5. Update DNS at Cloudflare (TTL is 60 s) → admin.cleanstart.com points at new droplet.
  6. Trigger an ISR purge from apps/web (full revalidate).
  7. Drain any leads sitting in the R2 fallback queue (see §Lead durability) — the 5-min cron picks these up automatically once the CMS is back, but verify the queue empties before declaring restore complete.

Smoke test (run after every restore — pass-or-fail checklist)

  1. Admin login succeeds; render one document from each of the 13 collections without error.
  2. Trigger one search query → confirm Meilisearch returns the expected hit (rebuilt index is populated).
  3. Confirm the Payload jobs queue worker is alive (last processed-job timestamp < 5 min ago).
  4. Walk the redirects table → 5 random rows return the correct HTTP status when fetched.
  5. Walk the media table → 10 random asset URLs return 200 from R2 (no orphaned references).
  6. Submit a synthetic test lead end-to-end → confirm it lands in leads and any configured CRM handler logs success in syncedTo[].
  7. Submit a synthetic lead with the CMS deliberately stopped → confirm it lands in web/_pending-leads/ on R2 and is drained when the CMS is restarted.

Restore drill

  • Monthly manual drill — every month, an Admin runs the restore procedure end-to-end against a throwaway droplet and runs the full smoke checklist above. Result + wall-clock timing logged in docs/RESTORE-LOG.md. The first drill must complete before the migration cutover, not after — an untested runbook is not a runbook.
  • Inverted heartbeat: BetterStack is configured to alert when the backup-cron heartbeat is missing (no ping in 25 h), not just when a backup succeeds. Alert-on-success masks silent cron failure for days; alert-on-missing catches it the morning after.
  • RTO target: 30 minutes from "droplet down" to "site serving from restored stack." Drill must hit this number — if it doesn't, fix the runbook before trusting the SLA.
  • RPO target: 24 hours (since backups are daily). Tighten by adding hourly WAL archival to R2 if the data-loss window becomes unacceptable.

Signing — Standard Webhooks format

Outgoing webhooks sign the concatenation of deliveryId + timestamp + body with HMAC-SHA-256 (per the Standard Webhooks spec) and emit:

  • webhook-id — unique per delivery (UUIDv4)
  • webhook-timestamp — Unix seconds at send time
  • webhook-signature — base64 HMAC-SHA-256 of {id}.{timestamp}.{body} using siteSettings.webhooks[].secret

Quarterly secret rotation. Receivers that support verification (the lead-handler `/api/leads`, the ISR `/api/revalidate` endpoint, any custom Zapier/n8n consumer) must short-circuit on duplicate webhook-id via a 24-hour Postgres dedup table — Standard Webhooks expects receiver-side idempotency because retries are normal and a successful processing whose ACK was lost will be redelivered. Teams / Slack don't verify signatures themselves; the header still goes out for downstream-automation forwarding.

Retry & dead-letter policy NEW

All outbound webhook deliveries (document.published, lead.submitted) and all CRM-handler retries inside the LeadHandler pipeline (the enqueueRetry() call in §Forms & leads) use a single, explicit retry policy:

Failed deliveries beyond 5 attempts move to webhooks_dead_letter (or leads_dead_letter for LeadHandler failures) — never silently dropped. The dead-letter row carries the full original payload, the target URL, every retry's HTTP status and error message, and the final deliveryId so engineers can correlate against Sentry breadcrumbs.

Admin surface — "Failed webhooks" view
  • Sorted by failed_at desc; columns: target URL, event type, payload preview, last error message, attempt count.
  • Each row has two actions: Retry now (re-attempts immediately, fresh 5-attempt clock) and Dismiss (mark as intentionally abandoned; row stays for audit but exits the active list).
  • Editors with Publisher role can manually retry; Admins can also delete dead-letter rows.
  • Bulk action: Retry all from {target host} for the post-outage scenario where a downstream CRM had a maintenance window and hundreds of leads piled up.

Why 5 attempts at immediate / 5m / 15m / 1h / 6h (not infinite retries): the spread covers transient downtime (network blip, CRM rate-limit), a CRM API maintenance window (typically < 4 h), and same-business-day failures. Beyond 6 h, the receiver has a real outage that needs human intervention; auto-retry just generates noise and pollutes the receiver's metrics. The dead-letter pattern matches AWS SQS DLQ semantics + the Standard Webhooks recommendation for consumer-driven idempotency.

Earlier "exponential backoff 1 s / 5 s / 30 s / 5 min then drop" — superseded

The earlier draft of this section described a faster, drop-on-failure retry. That version is replaced by the dead-letter policy above: more spread (covers maintenance windows), no silent drops, explicit admin recovery surface. Sentry still logs every retry with the deliveryId for cross-correlation; the dead-letter table is the source of truth for "did this lead/event ever land at the receiver."

Localisation posture (localized: true from launch)

Every translatable text field (title, abstract, body, seo.title, seo.description, FAQ question/answer, block headlines, etc.) is configured localized: true in Payload at launch with English (en) as the only configured locale. Adding a second locale becomes a config change in payload.config.ts, not a destructive schema migration over published content.

The cost at launch is zero — Payload stores English under the en locale key with no behavioural difference. The cost of not doing this is a multi-week migration when a second locale ships, plus risk of data loss for any English content edited during the migration window. Schema-clean i18n is a one-line decision today and an irrecoverable one tomorrow.

Slug normalisation: every slug is generated via an ASCII transliteration pipeline (Über uns → ueber-uns, not %C3%9Cber-uns) so URLs remain ASCII-clean across locales. Per-locale reading-time formulas (English: words ÷ 200; CJK: characters ÷ 500) live in a per-locale config table — placeholder for English-only today, ready for any second locale.

hreflang strategy (documented in advance for the second-locale ship)

When the second locale ships, the spec is locked in advance to avoid migration churn:

  • URL structure: subdirectory per locale — cleanstart.com/de/…, cleanstart.com/fr/… etc. No subdomains (subdomain-per-locale fragments authority); no ccTLDs (cost + complexity unjustified at this scale). The English default stays at the root (cleanstart.com/blogs/…) with no redundant /en/ prefix at launch.
  • <link rel="alternate" hreflang="…"> on every page, listing every locale variant of that document plus an x-default pointing at the English version. Self-referential entry included (Google requirement).
  • Sitemap: per-URL <xhtml:link rel="alternate" hreflang="…"> annotations in /sitemap.xml (the alternative is a separate sitemap per locale; xhtml:link annotations are simpler and Google-recommended).
  • JSON-LD: inLanguage set per-document; workTranslation[] array on the canonical document referencing locale variants.
  • Indexable matrix: a localized seo.indexable override per locale is supported — useful for shipping a draft locale that's not yet ready (set noindex on the locale until content quality clears review).

Experimentation posture (A/B testing)

A/B tests run at the rendering layer, not the content layer. Implementation: Vercel Edge Middleware reads a flag service (Statsig, GrowthBook, or LaunchDarkly — selection deferred), exposes flag values to page-builder blocks via React Context. Variant content lives in code/config, not in the CMS.

Reasons for the split (Statsig and LaunchDarkly published guidance both align): variants are short-lived; cleanup must be aggressive; CMS-stored variants accumulate forever and pollute the publishing workflow. Editors writing copy don't think about experiments; experimenters defining variants don't think about content versioning. Two separate concerns, two separate tools.

At launch this section is a posture statement, not built infrastructure — the first experiment to ship pulls in the chosen flag service. The architecture decision is locked; the vendor is not.

Droplet tuning spec — required for 2 GB / 1 vCPU

The 2 GB / 1 vCPU droplet runs Postgres + Payload + Meilisearch + Sharp + Coolify + OS. With factory defaults each component assumes it owns the whole machine; they will fight for memory and OOM-kill under upload bursts or initial Meilisearch indexing. The five tweaks below make the workload fit cleanly with ~500 MB headroom, plus 2 GB swap as a panic buffer.

1 · Postgres 16 (postgresql.conf)

shared_buffers = 128MB        # NOT the 25%-of-RAM default — that rule assumes a dedicated DB box
work_mem = 4MB
effective_cache_size = 1GB
max_connections = 20          # Payload pool sized to ~10
maintenance_work_mem = 64MB

Total Postgres footprint: ~250 MB idle, ~400 MB peak.

2 · Sharp (apps/cms/src/lib/sharp-config.ts)

import sharp from 'sharp';
sharp.cache(false);          // disable 50 MB pixel cache
sharp.concurrency(1);        // one core, deterministic memory
// All image processing runs through Payload's jobs queue, one job at a time
// — never Promise.all over multiple uploads.

Worst-case spike per upload: ~50–150 MB transient (vs ~600 MB with defaults under concurrent uploads).

3 · Meilisearch (systemd service args)

meilisearch \
  --max-indexing-memory 512Mb \
  --max-indexing-threads 1 \
  --http-addr 127.0.0.1:7700

Bulk reindex jobs are scheduled at 03:00 IST only — never on-demand during business hours. The --max-indexing-memory flag is best-effort (multiple open issues on meilisearch#3725, #4764; LMDB can briefly exceed the cap), which is why swap (#4) and the alarm (#5) exist.

4 · Swap file (2 GB) + kernel tuning

fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# /etc/sysctl.d/99-cleanstart.conf
vm.swappiness = 10              # use swap only as last resort
vm.vfs_cache_pressure = 50      # protect FS cache (Postgres relies on it)
sysctl --system

Swap is a panic buffer, not an extension of usable memory. With swappiness=10 the kernel only touches swap when RAM truly runs out. Sustained swap usage is itself an alert (see #5).

07Migration plan

Hard constraint #1 — URL preservation All existing URLs ship from Webflow to the new site verbatim. No character changes, no plural-vs-singular standardization, no slug rewrites, no case changes. Existing prefixes are preserved as-is: /blogs/* · /guide/* · /event/* · /job/* · /webinar/* · /author/* · /news/* · /resources/* · /category/* · /news-categories/*, plus every individual document slug. Next.js route segments are named to match the live site exactly. ~368 total URLs ship 1:1 (293 CMS items across 13 collections + ~75 static pages, verified from Webflow Backups metadata 2026-05-04); SEO equity carries cleanly.
Hard constraint #2 — Zero data loss No published content, no asset, no lead, no editorial-state metadata is lost in the migration. Every claim of "0 % loss" below is enforced by an automated verification gate that blocks cutover if the criterion isn't met:
  • 0 % published-content loss — pre-cutover row-count assert: count(Webflow.published) === count(Payload.published) per collection. Mismatch blocks cutover.
  • 0 % asset loss — every unique asset referenced from any published doc is re-uploaded; SHA-256 checksum of the original (downloaded from Webflow) must match SHA-256 of the re-uploaded copy (fetched from R2). Mismatch blocks cutover for that asset until resolved.
  • 0 % indexed-URL loss — every URL in Webflow's sitemap.xml resolves with HTTP 200 on staging before DNS swap. Any 404 blocks cutover.
  • 0 % editorial-state loss — _status, publishedAt, scheduledFor, author bylines, category assignments, FAQ entries, and rich-text body content are preserved field-for-field. Diff verification (expanded — see below) blocks cutover on any unexplained delta.
  • 0 % lead-capture loss — Webflow forms set to "submission email-only" mode during freeze; new /api/leads endpoint live before DNS swap; cross-check email backups vs leads table after T+24h. Any submission unaccounted-for triggers a manual reconciliation pass.
  • 0 % rollback loss — if rollback fires, leads captured on the new system between DNS swap and rollback are exported as JSON and re-imported into the marketing team's email queue, so the rollback window itself loses zero data.
  • 0 % body-text URL drift — every uploads-ssl.webflow.com / uploads.webflow.com reference in any rich-text body is rewritten to the new R2 URL during ETL; post-import grep for legacy domains must return zero rows. Otherwise content ships with broken images the moment Webflow's CDN is decommissioned.
Achieving 0 % loss is the discipline of the verification gates below — not a wish. Every gate has an explicit pass/fail criterion and an explicit owner.

Body-text URL rewriting (zero-tolerance rule)

Every reference to uploads-ssl.webflow.com or uploads.webflow.com in any rich-text body is rewritten during ETL to point at the asset's new R2 URL (cdn.cleanstart.com/web/{folder}/{filename}) — via the asset checkpoint table so the rewriter knows which Webflow asset became which R2 asset. Without this rewrite the Webflow CDN URLs in body text 404 the moment the Webflow workspace is shut down.

  • Image <img src> in bodies → resolved to media ID and rendered as a Lexical UploadNode
  • PDF / file <a href> in bodies → resolved to media ID and rendered as a Lexical LinkNode of {kind: 'media', mediaId}
  • Internal Webflow CMS-document-ID links (https://www.webflow.com/cms/...?id=abc123) → resolved to the new collection + slug if the CMS-doc-ID maps to a known migrated document; otherwise rewritten as a plain external URL with a fallback warning logged
  • Audit: post-ETL grep across all migrated bodies for any remaining Webflow CDN domain → must return zero

Asset re-upload — resumable

  • Per-asset checkpoint table migration_progress in the staging Postgres: { source_url, status: 'pending' | 'downloading' | 're-encoding' | 'uploading' | 'done' | 'failed', media_id?, sha256?, error?, attempts: number }
  • Script restart-safe: skips assets in 'done' state, retries 'failed' with exponential backoff up to 5 attempts, surfaces any attempts > 5 as a manual-review item
  • SHA-256 checksum verification: original (downloaded from Webflow) and re-uploaded (fetched from R2 post-upload) must match → only then mark 'done'
  • Webflow API rate limit: token-bucket throttle at 50 req/min (10 below the 60/min token limit, leaves headroom for retries)
  • Estimated runtime for ~1.5 GB / ~600 unique assets: 30–60 min on staging dry-run; same on production

The dry run is the migration; cutover day is just the rerun. If the dry run doesn't achieve 100 % of the acceptance criteria, the cutover is postponed. Non-negotiable.

  1. Fresh Webflow export on staging: full export of all collections + assets, run identical scripts to what'll run on cutover day.
  2. Full ETL run on staging: dependency-ordered import with body-text URL rewriting, asset checkpointing, schema-parity audit re-validated.
  3. Acceptance-criteria gate: all 9 criteria from the table above must pass on staging. Failure of any criterion = postponement.
  4. Stakeholder spot-check: marketing, sales, support, and any executive sponsors get a 24-hour staging URL to spot-check their important pages. Bugs filed in JIRA project MIG; resolution required before cutover.
  5. Rollback drill: practice the rollback procedure (below) at least once on staging — not for real, but with the same DNS-revert mechanics, the same comms script, the same decision authority on the call. The first time the team executes the rollback should not be at 2 AM under pressure.
  6. Sign-off: dry-run report (docs/migration/dry-run-{date}.md) signed off by Engineering Lead + Marketing Lead + CTO before Phase 4 begins.

Rollback procedure

Rollback is invoked when the migration is provably worse than reverting. The trigger criteria are objective; the decision authority is named.

AspectSpecification
Trigger criteria (any one fires the rollback)
  • Sentry error rate > 5× the 7-day baseline for > 30 min
  • Smoke-test 404 rate > 10 distinct URLs in the first 30 min post-DNS-swap
  • Lead-capture endpoint /api/leads returns 5xx on > 5 % of submissions for > 15 min
  • Stakeholder spot-checks reveal a critical content / data loss issue not caught by the diff verification
  • CTO judgement: "this is broken in a way the runbook didn't anticipate"
Decision authorityCTO has the call. Engineering Lead can recommend; Marketing Lead can recommend; final go/no-go is the CTO. Decision logged in #migration-cutover with a one-sentence reason.
Rollback mechanics
  1. DNS revert: cleanstart.com CNAME flipped back to Webflow's original CDN. TTL = 60 s; full propagation in < 5 min.
  2. Webflow workspace permissions reverted (editors can publish again).
  3. Any leads / form submissions captured on the new system between DNS swap and rollback are exported as JSON from the new Postgres → uploaded as a CSV to the marketing team's drop folder, so no lead data is lost from the rollback window.
  4. Comms: rollback announcement to all stakeholders; post-mortem scheduled for within 48h.
Post-rollbackThe migration is rescheduled only after the root cause is found, fixed, validated on staging again, and re-rehearsed. No second cutover attempt within 7 days of a rollback — the team needs the calendar buffer to address whatever broke without pressure.
Data-loss budget on rollback0 leads lost (captured leads exported and re-imported into Webflow's email queue). 0 published-content changes lost (Webflow was read-only during the freeze, so nothing changed there).

Phase 5 · Verify + stabilise (T+0 to T+7d)

Elevated monitoring window

  • 404 monitoring: alert threshold tightened to "5 distinct 404s in 5 minutes pages oncall" (vs the normal 90-day analysis cadence). Reverts to normal at T+7d.
  • Sentry error rate: alerts on any 2× baseline spike (vs the normal 5× threshold).
  • Speed Insights: alerts on any 25 % p75 regression on key routes (vs the normal 10 % threshold) — accounts for the cold-cache + recrawl noise.
  • Search Console Coverage report: monitored daily for the first 14 days; weekly thereafter for the first 60 days. Indexed-URL count change > 5 % triggers investigation.

SEO acceleration (T+30m through T+7d)

  • Sitemap submission: /sitemap.xml + /sitemap-images.xml + /sitemap-news.xml submitted to Google Search Console + Bing Webmaster Tools at T+30m.

  • Indexing API: every JobPosting URL pinged via Google's Indexing API (officially supported for jobs).
  • Manual Search Console URL Inspection on the top 20 highest-traffic URLs at T+24h to force a crawl request.

Edge cases handled explicitly

  • Webflow scheduled publishes: any in-flight scheduled-but-unpublished items are queried during Phase 1 audit. Each is either (a) promoted to published before freeze (if the scheduled time is < T-2h), or (b) migrated as _status: scheduled with scheduledFor preserved to the new system. Zero loss.
  • *-copy and doubled URLs: every URL currently live and indexed in the Webflow sitemap — including /about-copy, /pricing-copy, doubled webinar / news slugs — ships verbatim. They render in Payload as their own documents (own slug, own row). The new draft / preview workflow prevents the same accident recurring; consolidation is a post-launch editorial decision, not a migration concern.
  • Internal CMS-doc-ID links in Webflow rich text → resolved during ETL via the source-Webflow-doc-ID → Payload-doc-ID map; rewritten as Lexical LinkNode of {kind: 'doc', collection, id} when target is a known migrated document; otherwise rewritten as plain external URL with a warning logged for editor review.
  • Webflow date format → ISO 8601: every datetime field normalised during ETL to ISO 8601 with timezone offset (Webflow's API returns ISO already, but some date fields ship as strings — the ETL coerces).
  • Slug character-set normalisation: any URL-unsafe characters in Webflow slugs are URL-encoded as-is to preserve the indexed URL exactly. No transliteration / normalisation that could drift the URL.
  • Empty fields that are required in Payload: surfaced during Phase 1 audit; either Payload schema relaxes to allow null, or a default value is set during ETL, or the Webflow document is flagged for editor cleanup before cutover.
  • Author byline missing on some posts: ETL maps to a placeholder author system with a Payload authors row pre-created; editor can reassign post-launch.

Route segments are immutable post-launch

Renaming a Payload collection in code (e.g. webinars → liveEvents, aboutGalleries → aboutImages) is allowed at any time and has no effect on public URLs — the Next.js route file is the contract. Renaming a Next.js route segment (e.g. app/(website)/webinar/[slug] → app/(website)/webinars/[slug]) is forbidden post-launch: it breaks every external backlink and every indexed URL. Any route-segment change requires (a) explicit approval, (b) a redirects collection row covering the entire old prefix → new prefix, and (c) a Webflow-vs-new sitemap diff confirming no other URL drifted. Per-document slug changes are still allowed and handled automatically by the slug-change beforeChange hook (auto-creates a redirects row).
